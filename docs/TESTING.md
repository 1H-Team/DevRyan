# DevRyan Testing

## Commands

| Command | Use |
| --- | --- |
| `bun run validate` | The local gate before every push and release tag. Diffs against the upstream branch (override with `VALIDATE_BASE`) and runs only what the change touches. |
| `bun run validate:full` | Lint, import boundaries, the browser graph, unreached browser files, declaration parity, type-check, `docs:validate`, build (once), `bundle:check` and `test:full`. CI runs these same checks across its build and test lanes. |
| `bun run test:startup` | Curated startup and user-data contract. |
| `bun run test:full` | Scripts and every package suite, as one bounded concurrent pool (`node scripts/test-full.mjs [--suite=web,ui]`). |
| `bun run docs:validate` | Markdown links and inline-code paths, and drift against package manifests, source exports and environment-variable names. |

`bun run validate` runs:

- oxlint on changed `.ts`/`.tsx` files inside the directories `bun run lint` covers (the targets of each workspace's oxlint `lint` script, today `packages/ui/src` and `packages/web/src`), so fast and full lint check the same files (everything when shared configuration changes);
- type-check of changed packages and their dependents (everything when root `package.json`, `bun.lock`, `patches/`, `.oxlintrc.json`, `tsconfig.json` or `.opencode/opencode.json` change). Any `packages/ui/src` change also type-checks web, whose tsconfig includes the UI source, and a `scripts/opencode-v2-native/*.ts` change type-checks web, whose runtime-host tsconfig includes those files;
- tests of changed packages and their dependents: any file under `packages/ui/src` runs the UI suite, any `packages/web` file (server, bin, src, the Vite and Vitest configuration, test setup) the web suite, any `packages/agents-core` file the agents-core suite and its web dependent;
- every suite in `FULL_TEST_SUITES` when root `package.json`, `bun.lock`, `patches/`, `.nvmrc` or `bunfig.toml` change (so a patch edit runs `scripts/opencode-v2-native/mcp-client-patch.test.mjs`);
- `test:scripts` when `scripts/`, `.github/`, `.opencode/agents|plugins` or `packages/web/runtime/reviewed-inputs` change (their Markdown and text included, since the reviewed-inputs manifest hashes every file), and `bun run catalog:check` (which fetches the live catalog) when the reviewed model catalog changes;
- `docs:validate` for every change: besides Markdown it reads package manifests, source exports and environment-variable names, so a code-only change can make docs stale;
- import boundaries and the browser graph when package code changes (every importer when a package manifest, `scripts/import-boundaries.json` or a checker changes); unreached browser files for the same changes, any test file, `scripts/unreached-files.json` or its checker; declaration parity for any JavaScript or declaration file, package manifest, `scripts/declaration-parity.json` or its checker;
- the Rust ledger core check, `node scripts/build-ledger-core.mjs --verify` (format, clippy, `cargo test` and a byte-for-byte rebuild of the tracked module), with the script tests that read the crate, when `packages/harness-runtime/native/ledger-core/`, `scripts/build-ledger-core.mjs` or the tracked `packages/harness-runtime/lib/native/ledger-core.*` change; only these changes need the pinned Rust toolchain, and without it the check fails with the command that installs it ([harness runtime](../packages/harness-runtime/DOCUMENTATION.md#rust-ledger-core)). A tracked module change also runs the harness suite;
- the native ledger check, `node scripts/build-ledger-native.mjs --verify` (format, clippy and `cargo test` of `packages/harness-runtime/native/ledger/`, the same lint for x86_64 Linux when that target is installed, then the JavaScript lock and atomic writes against the Rust ones), with the script tests that read the workspace, when one of its inputs changes: the files `scripts/ledger-native/inputs.mjs` lists (that workspace, the ledger core's crate, `packages/harness-runtime/lib/atomic-file.js` and every local module the verify loads); it needs the same pinned toolchain and the network for `cargo fetch` ([harness runtime](../packages/harness-runtime/DOCUMENTATION.md#native-ledger-io));
- the Cargo workspace check, `node scripts/check-native.mjs` (the licence check of `scripts/check-native-licenses.mjs` against the allow list in `deny.toml`, `cargo fmt --check`, clippy with warnings denied and `cargo test`, locked), with the script tests that read the workspace, when `packages/native/`, `scripts/check-native.mjs` or `scripts/check-native-licenses.mjs` change; without the pinned toolchain it fails with the command that installs it ([packages/native](../packages/native/DOCUMENTATION.md#gates)). Nothing in the workspace reads the server's sources, so a change under `packages/web/server` runs no native check. The `devryan-config-text` crate is held to tracked vectors that its generators write with the installed `jsonc-parser` and `yaml`; `scripts/check-native.test.mjs` regenerates them in memory without Rust, in its own process (about 1.7 s of CPU, measured at load average 37 on an 8-core Apple M-series machine) and fails with the command to rerun a generator, so a `bun.lock` change that alters either package's behaviour fails the scripts suite. Its differential probe and planted bugs are run by hand ([packages/native](../packages/native/DOCUMENTATION.md#devryan-config-text)). Recording and comparing traffic is not part of it: that will be a separate package, whose recordings stay in a run's scratch ([packages/native](../packages/native/DOCUMENTATION.md#devryan-front));
- `test:startup`, always: each startup group whose owner suite already runs in the same plan runs there instead of twice.

Fast mode narrows `test:scripts` to the script tests whose closure holds a changed file (`scripts/test-select.mjs`). The closure follows each test's imports, resolved as `scripts/check-import-boundaries.mjs` resolves them, and every file its scripts and tests name by path or file name (a spawned script, a `Bun.build` entry, a read fixture); shipped package code reaches files only through its imports and module URLs. Only a file that puts the scripts suite in the plan (under `scripts/`, `.github/`, `.opencode/agents|plugins` or the reviewed inputs) can widen the run: such a non-code file (workflow, fixture, JSON, shell) selects the tests naming it or its outermost directory (`.github` for workflows), and the whole suite when none does. Other changed files, such as package code, only add the script tests that reach them. A file under `packages/harness-runtime/native/ledger-core/` or `packages/harness-runtime/native/ledger/` also selects the script tests that read that whole tree (`TREE_READERS`: `scripts/build-ledger-core.test.mjs`, `scripts/build-ledger-native.test.mjs`), and a file under `packages/native/` selects `scripts/check-native.test.mjs`. Markdown and text files never enter the graph: any Markdown change other than `CHANGELOG.md`, alone or beside code, runs `scripts/release-docs.test.mjs`, which reads every tracked Markdown file for the published-release rule `docs:validate` does not check; Markdown under one of those trees also runs that tree's tests (the workspace's contract checks what its `DOCUMENTATION.md` says); and no script test reads tracked `.txt` files. Changes to the selector, its resolver, the suite runners (`validate.mjs`, `test-scripts.mjs`, `test-runner-utils.mjs`, `test-full.mjs`, `test-ci-lanes.mjs`, `test-pool.mjs`), the suite contract, reviewed inputs or the toolchain run the whole suite, and a changed test file also runs the inventory's tests. A change to a test file of any package, even one that does not put the scripts suite in the plan, also runs `scripts/test-suite-contract.test.mjs`, which inventories every test file. `scripts/test-select.test.mjs` checks on this checkout that every file in every script test's import and name closure selects that test. `validate` prints the selection and why the rest were skipped; a subset leaves the startup scripts group in `test:startup`. `validate:full` and CI always run every script test.

A change confined to the `version` fields that `scripts/bump-version.mjs` writes (package manifests, workspace versions in `bun.lock`, the legacy Tauri `tauri.conf.json`, `Cargo.toml` and the `devryan-desktop` entry in `Cargo.lock`) runs `node scripts/release.mjs check-versions` (every version file and `bun.lock` workspace agrees) instead of every package's lint, type-check and tests. Any other change to those files keeps the full shared-configuration plan. CI still runs everything for the bump commit before release admission.

Independent static checks run concurrently and all report, and any failure stops before tests. In `validate:full` the build and bundle budgets then run in order beside the test pool, and `scripts/built-web-assets.test.mjs` (the only test that reads the build output) runs after the build; `validate` (fast) runs no build. Test commands run as one weighted pool of independent processes within a capacity of `DEVRYAN_TEST_CONCURRENCY` (default: half the cores, between 2 and 4). A unit reserves its `weight` (default 1): the Vitest `web` project and the harness suite start their own workers and weigh 2. Local runs split the serial `node --test` script batch into three timing-balanced shards and the web runtime-host project into two (`localTestUnits` in `scripts/test-ci-lanes.mjs`; CI lanes use their own inventory). While the host's 1-minute load average is above its core count, the pool starts no further unit (one always runs), so concurrent runs on one machine (other worktrees, a build) queue instead of driving timeouts; `DEVRYAN_TEST_LOAD_LIMIT` sets the ceiling as a multiple of the cores and `0` disables it. Every unit has a wall-clock budget (`DEVRYAN_TEST_UNIT_TIMEOUT_MS`, default 20 minutes) after which its process group is killed and it fails as timed out; script `node --test` files also get `--test-timeout=300000` and `--test-force-exit`. Each Bun package run gets the cores the pool leaves it (`--parallel=<cores / DEVRYAN_TEST_CONCURRENCY>`, at least two, scaled by a heavy unit's weight; `DEVRYAN_TEST_WORKERS` overrides), each unit's output printed whole when it ends, a heartbeat naming running units every minute, every unit run to completion and every failure listed. Native graph test files share one exclusive pool resource: they build and spawn the pinned runtime, and the shared fixture's browser OAuth callback binds localhost:1455. Independent units keep running alongside them. Interrupting stops every owned process group and removes the run's scratch. Both modes end with per-command and slowest-unit timings.

`scripts/check-import-boundaries.mjs` resolves static, re-export, `require` and literal dynamic imports between packages. Application packages (web, Electron, legacy desktop) expose only their `main`/`exports`; a package that declares `exports` exposes only those targets, by package name or relative path. Tests (`*.test.*`, `*.spec.*` and files under a `tests/` directory) may import another package's private files, since parity and integration tests exercise both sides; they are still refused a package-name import that the target's `exports` omit. Each temporary exception in `scripts/import-boundaries.json` (production code only; currently none) is one exact importer/target pair with the plan stage that removes it (`unscheduled` when none does yet); an exception that no longer matches fails, so the list only shrinks. No exception covers a package-name import of a subpath the target's `exports` omits, because Node refuses that import at runtime. `scripts/check-browser-graph.mjs` walks the web Vite entry points with the build's aliases and fails on Node builtins, `adm-zip`, or a web-server, Electron or Node-only shared-runtime file.

`scripts/check-unreached-files.mjs` walks the same graph, with the same resolver, from the web entry points and the service worker (`packages/web/src/sw.ts`), and again from every tracked test file (a server test contributes its own imports; the walk stops at privileged files as the browser graph does). Every code file under `packages/ui/src` and `packages/web/src` that neither walk reaches fails, unless `scripts/unreached-files.json` lists it with a kind (`awaiting-removal` for dead code a later phase deletes, `hand-run` for a tool run by hand and kept on purpose) and a reason; it also prints, as information, how many files only tests reach (`--verbose` names them). Two known limits: a file reached only through `import type` counts as reached, and helpers under a `test/` directory inside `src` count as tests, so they are not checked. The server packages are out of scope: their string-built dynamic imports make a file-level check noisy. `scripts/check-declarations.mjs` pairs every first-party hand-written declaration with its JavaScript twin (`x.d.ts` with `x.js`, `x.d.mts` with `x.mjs`, and the `types`/`default` pairs of package manifests) and fails when the declaration exports a value the implementation does not; type-only exports need no implementation, relative re-exports are followed on both sides, and exports the implementation has without a declaration are information (`--verbose` lists them). Vendored reviewed inputs and the frozen legacy desktop package are skipped. A pair it cannot compare (a CommonJS implementation, or one that re-exports a package) fails too. `scripts/declaration-parity.json` lists known mismatches and uncomparable pairs, each with its reason, and, separately, `transformExports`: permanent exemptions for names a native build transform adds to the bundled copy of an implementation only (the browser and document-reader plugins), each naming its transform; such an exemption fails when the transform's source stops exporting the name or the shipped implementation starts exporting it. The other lists only shrink: an unlisted finding fails, and an entry that no longer matches (the file is now reached or deleted, or the declaration was fixed) fails until it is removed. `--prune` on either checker removes stale entries and never adds one; fix the finding instead of listing it.

A docs-only change runs only `docs:validate`. Both validate modes fail if the run left new entries in `.cache/` (see [STORAGE_CLEANUP.md](STORAGE_CLEANUP.md)).

## CI

`.github/workflows/ci.yml` runs on every main push and pull request. Every job starts at once; none waits for another and no artifacts move between them:

- `static` (Ubuntu): `node scripts/validate.mjs static` — lint, import boundaries, the browser graph, unreached browser files, declaration parity, type-check and `docs:validate`, run concurrently. Then, on every push and on a pull request that changes the ledger core's crate, build script, tracked module or `ci.yml`, it installs the pinned Rust and runs `node scripts/build-ledger-core.mjs --verify`, whose rebuild must match the module built on macOS byte for byte. A second step does the same for the native ledger (the inputs `scripts/ledger-native/inputs.mjs` prints, or `ci.yml`) and runs `node scripts/build-ledger-native.mjs --verify` on Linux; the system-call traces in it need macOS and report themselves skipped there. On every push, and on a pull request that changes `packages/native/`, `scripts/check-native.mjs`, `scripts/check-native-licenses.mjs` or `ci.yml`, it installs the pinned Rust and runs `node scripts/check-native.mjs`, licence check included, then the RustSec advisory check `node scripts/check-native.mjs --advisories` with cargo-deny 0.20.2 kept in GitHub's cache; a new advisory not ignored, with its reason, in `deny.toml` fails the job ([packages/native](../packages/native/DOCUMENTATION.md#gates)).
- `build` (Ubuntu): `node scripts/validate.mjs build` — the build, bundle budgets and the tests of the built assets (`BUILD_JOB_TESTS` in `scripts/test-ci-lanes.mjs`, such as `scripts/built-web-assets.test.mjs`).
- `tests` (two Ubuntu lanes): `node scripts/validate.mjs ci:<lane>` with the normal scratch guard.
- `native-tests` (three macOS lanes): build and verify the native v2 runtime in-lane (cheaper than shipping it between jobs), then run their lane. Lane `native-1` then runs the native ledger verify on macOS, filtered like the Ubuntu step, even when its suites failed: the macOS-only code, the sync chain and the system-call traces are tested there. GitHub Free runs five macOS jobs at a time and a release holds two while it waits for CI, so three is the most CI may use.

`scripts/test-ci-lanes.mjs` expands the full suite into files before assigning platforms; it keeps macOS sandbox, native binary, case-insensitive filesystem and platform-gated checks on macOS. Units are packed onto lanes longest first from the recorded durations in `scripts/test-unit-timings.json` (a unit without a recording costs the median); the web runtime-host Vitest project runs as two shards. Every lane uploads its unit timings as the `test-timings-<lane>` artifact; refresh the recordings with `bun run test:timings:update <files...>`. The native-stream file has two disjoint case shards (ordinary local runs register every case); `test-suite-contract.test.mjs` checks the complete inventory and shard union, and that a case-sharded file registers every test through its shard filter. CI runs Bun package suites in randomized order seeded with the workflow run number (`DEVRYAN_TEST_SEED`). Main-push concurrency is unique to the commit SHA and never cancels a different main commit; superseded PRs still cancel. Release preparation overlaps CI, but publication requires the exact main-push workflow to pass. `bun run validate:full` remains the equivalent complete local gate. `release-cache.yml` is manual-only; see [Release pipeline](RELEASE_PIPELINE.md).

Measured and deliberately not adopted (2026-10): caching `tsbuildinfo` or the Vitest module cache in CI (TypeScript 7 type-checks every package in about 26 s run one after another, measured 2026-11, and transforms are 1–2% of Vitest time), parallel `node --test` for the script suite (no speedup; deadline-sensitive tests fail under contention), and moving hazard-free web tests to `bun test` (they rely on Vitest APIs such as `vi.waitFor`, and parallel Vitest already runs them in under a minute).

## Startup contract

`scripts/test-startup-contract.mjs` runs the startup and user-data tests: runtime bundle startup, selection and upgrade, ledger and session integrity, Retry, cancellation, delayed bootstrap, event subscription, and Electron startup and ownership. It uses disposable fixtures only: no installed-app data, live accounts or OS service registration. `STARTUP_CONTRACT_GROUPS` names each group's owner suite (`electron`, `scripts`, `shared`, `harness`, `ui`, `web`); `--covered-by=<suite,...>` skips groups already covered elsewhere in the same run.

## Suites and runners

`test:full` runs every suite below, including the bundled Plan Mode contract in the frozen legacy Tauri package. Cargo tests are not run because they require native build assets. `FULL_TEST_SUITES` in `scripts/test-full.mjs` is the inventory. The pool splits three suites without changing what they run: one process per script Bun test file, the two Vitest projects of the web suite (`test:vitest --project=web|web-runtime-host`) beside its Bun native files (`test:native`), and the harness suite with Bun file workers (`bun test --parallel=4`). `scripts/test-suite-contract.test.mjs` checks every split runs each file exactly once.

Set `DEVRYAN_TEST_TIMINGS=<file.json>` to record each unit's duration and status. Set `DEVRYAN_TEST_SEED=<n>` to run Bun package suites in randomized order (`--randomize --seed=<n>`); a failure reproduces with the same seed. Tests must not depend on the order of other tests: reset shared stores, module-level mocks and globals in `beforeEach`, not only `afterEach`.

Expensive invariants are tested at the smallest size that crosses the boundary. Production limits that tests must exceed (ledger install batches, the change-store listing bound, the admission dedupe cache) are constructor options with unchanged defaults, so a test crosses them with a few hundred records instead of tens of thousands. Create test Git repositories with `initGitRepository()` from `scripts/test-git-template.mjs` (a copied template, about ten times faster than `git init`).

| Suite | Command | Runner |
| --- | --- | --- |
| Scripts, `.opencode/agents` and `.opencode/plugins` tests, reviewed runtime inputs | `bun run test:scripts` | `scripts/test-scripts.mjs`: files importing `bun:test` run one per `bun test` process (never sharing Bun's resolver), the rest in one `node --test` run, all through the bounded pool. `DEVRYAN_SCRIPT_TEST_CONCURRENCY` sets Node concurrency (default: one file at a time inside the outer pool). |

Native host scripts: `bun run --cwd packages/web test:native-host`. |
| Electron | `bun run --cwd packages/electron test` | `scripts/test-electron.mjs` routes by import, in the isolation guard's environment: `node:test` to Node (concurrent files, with the isolation `--import`), `bun:test` to one `bun test --parallel` run; any other framework is refused |

Runner and discovery changes belong in `scripts/`. Feature tests live beside their source unless a contract spans packages.

## Test isolation

No test process may read or write the real home folder, DevRyan, OpenCode or Git configuration. `scripts/test-isolation-guard.mjs` builds a private environment, and `scripts/test-isolation-check.mjs` checks it inside every test process.

The environment (`createTestIsolation`): one private root per run, `<os tmpdir>/devryan-test/run-*`, holds `HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME` and a private `GIT_CONFIG_GLOBAL` with a test identity (`GIT_CONFIG_NOSYSTEM=1`, `GIT_TERMINAL_PROMPT=0`). Every inherited variable that selects a location, endpoint or credential is removed, not re-pointed: `DEVRYAN_*`, `OPENCHAMBER_*` and `OPENCODE_*` names ending in a location, URL, host, port, binary, token, secret, password, key or identifier suffix (for example `DEVRYAN_DATA_DIR`, `DEVRYAN_RUNTIME_BUNDLE_ROOT`, `OPENCODE_CONFIG_DIR`, `OPENCODE_DB`, `OPENCODE_BINARY`, `DEVRYAN_SESSION_TMP`, `DEVRYAN_SERVER_URL`, `OPENCODE_PORT`, `OPENCODE_SERVER_PASSWORD`), plus `CLAUDE_CONFIG_DIR`, the Meridian, Cursor and `gh` locations, the `GIT_DIR`/`GIT_CONFIG_*` family and `SSH_AUTH_SOCK`. Each root then resolves to its default under the private `HOME`, exactly as in CI, which sets none of them. Product behaviour switches, limits and timeouts pass through (`PASSED_THROUGH` in the guard); `scripts/test-suite-contract.test.mjs` fails when product code reads a `DEVRYAN_*`, `OPENCHAMBER_*` or `OPENCODE_*` name that is in neither list. `TMPDIR` is left as the runner sets it. The root is removed when the run passes, fails or is interrupted (kept with `--keep-artifacts` or `DEVRYAN_KEEP_ARTIFACTS=1`), and a runner started inside an isolated environment reuses it. Bun's runtime transpiler cache (`BUN_RUNTIME_TRANSPILER_CACHE_PATH`) stays at its existing location: it holds only transpiled sources.

The check (`scripts/test-isolation-preload.mjs`) runs before any test: the Bun `preload` of the root `bunfig.toml` and of every package that runs `bun test` except the frozen `packages/desktop`, the `--import` of node:test runs, and the web Vitest global setup and setup file. It requires the home directory, the XDG folders, the Git configuration and every stripped variable that is still set to lie inside the private root named by `DEVRYAN_TEST_ISOLATION_ROOT`. What happens without that environment depends on the runtime:

- Node (`node --import=…preload --test`, Vitest): the process builds the environment itself, before any test or product module loads, because Node's `os.homedir()` follows `HOME` on every call; Vitest's workers inherit it. These direct runs are isolated.
- Bun: `bun test` reads `HOME` once at startup and its preload sees neither the command line nor the filters (`process.argv` holds only the test file; `ps` loses quoting, and with `--parallel` the preload runs in each worker), so it can neither move the process nor run it again. A bare `bun test` stops before any test with `DevRyan test isolation: refusing to run tests against the real home folder.`, the reason and the command that runs one file in that folder.
- A bare `node --test` without the `--import` loads nothing of the guard (Node reads no configuration file by default) and is not isolated.
- A `bun test` started inside a source subfolder (for example `packages/web/server` or `packages/ui/src`) reads no `bunfig.toml`, so the preload never runs. The shared test setups that such files import (`packages/ui/src/test/mountedDom.ts`, `packages/harness-runtime/test/session-mutations-fixture.js`, `packages/harness-runtime/test/session-change-fixture.js`) stop the file with the same explanation; other files run unguarded. Start `bun test` from the package folder.
- `packages/desktop` is frozen: its one contract file is isolated when a runner (`test:full`, `validate`, CI) starts it, not when it is run directly.

| `packages/web`, Vitest | `bunx vitest run <path>.test.js` |

`bun run --cwd packages/web test <file>` is not a single-file command (the file reaches only the last of its two steps), and the Electron runner ignores file arguments. `node scripts/test-isolation-guard.mjs <command> [args...]` wraps any command. Every repository runner builds the environment for its own processes: `bun run test:full`, `node scripts/test-scripts.mjs`, `bun run test:startup`, `bun run validate`, the CI lanes (through `prepareScriptTestEnvironment` in `scripts/test-scripts.mjs`), the built-asset tests (their `--import`), and the package `test` scripts (`node ../../scripts/test-isolation-guard.mjs bun test`, and the UI and Electron runners).

Each runner collects an isolation canary (`scripts/test-isolation-canary.test.mjs`, `scripts/test-isolation-canary-bun.test.mjs`, an `isolation-canary` test in every package, one in each web Vitest project) that takes the home folder, the DevRyan data root, the runtime-bundle root and the OpenCode config and data folders from the product modules that resolve them, derives the OpenCode state and cache folders and the DevRyan log folder from `XDG_*` and `HOME` as the bundled OpenCode host and Electron do (neither exposes an importable resolver), checks the Git identity, and requires each inside the private root. `scripts/test-isolation-guard.test.mjs` runs every canary and shows each Bun runner refusing and each Node runner isolating itself without the guard's environment; the suite contract fails when a runner, unit or package test script starts tests without the preload, the import or the environment.

What stays real, on purpose: `PATH` and the tools on it (Git, Xcode command-line tools, `codesign`, `sandbox-exec`, `openssl`), `USER`, `TMPDIR`, loopback ports, `BUN_INSTALL` and the Bun transpiler cache. The private home also gets a copy of the ripgrep binary the installed Cursor SDK ships at `.cache/opencode/bin/rg`, where OpenCode's ripgrep lookup lands when `rg` is not on `PATH`; without it, tests that build that layer would download ripgrep from GitHub. Vitest stores its own startup token under the home folder before any setup runs, so a direct Vitest run still writes `Library/Application Support/vitest` in the real home.

## Policies enforced by lint

Module-graph rules that used to be source-text tests (a component must not import an eager dialog, a removed surface, or a heavy renderer; a file must not own timers) live in `.oxlintrc.json` `overrides` as path-scoped `no-restricted-imports` and `no-restricted-globals` rules, so `bun run lint` enforces them once instead of a test reading the source. Tests assert behaviour: rendered markup, calls and state, not the text of the implementation. Keep a source read only for a genuine text contract (CSS rules, generated assets, documentation).

## Test-suite contract

`scripts/test-suite-contract.test.mjs` fails when a test file is not discovered by its package runner, when a deterministic test uses `skip`, `todo` or `only` (`test.skip(`, `{ skip: … }`, `.todo(`, `.only(`), when a conditional skip is not inventoried, or when the feature matrix is stale. Do not silence a scenario: delete tests for removed behavior or rewrite them for the current contract. Opt-in gates below are reported as not run, never skipped.

For the web package it lists what Vitest collects (`vitest list --filesOnly`, nothing runs) and checks that `notVitest` in `packages/web/vitest.config.ts`, apart from the reviewed inputs, names exactly the `test:native` targets of `packages/web/package.json`, that every entry exists, and that every web test file runs under exactly one of a Vitest project and `test:native`. `scripts/test-conditional-skips.json` inventories every test file that can skip a test or return early from one on a condition (platform, a built launcher, a full Xcode, System Integrity Protection, a captured install, the Node version, an opt-in variable). Each entry names the CI job that runs the file (`tests`, `native-tests` or `build`, checked against the lane inventory) and each guard its mechanism, its exact source text, the condition in words and whether CI satisfies it (`ci`: `yes` or `no`). The contract fails when a `skipIf(…)`, `runIf(…)` or `t.skip(…)` call, or any reference to `test|it|describe.skip|todo|skipIf|runIf` without a call (an alias such as `process.platform === 'darwin' ? test : test.skip`), is not covered by one of its file's guards, or when a guard's text, its condition's `definition` or the file is gone. It prints every guard CI never satisfies: those tests never run in CI. The pool summary still counts a unit whose tests all skipped as passed, because it keeps no unit output.

`scripts/feature-test-matrix.mjs` maps feature families to source and test anchors; the contract test checks that every anchor exists. Add a row when you add a feature family. ## Ledger dual-run harness

`scripts/ledger-dual-run/` checks one implementation of the session mutation ledger against another before any of it is ported (plan row L0). It changes no product file. It records a scenario through the product host (`createSessionMutationHost`, worker thread and all) with a tap on the host's `Worker`, so every message that crosses `packages/harness-runtime/lib/session-mutation-host.js` is logged. A replay posts the recorded `call` messages to another implementation on a fresh twin of the fixture, behaves as the recording's host behaved (the recorded answers to input functions, observer callbacks answered as the host answers them, `abort` and `stream-return` where the host sent them, deadlines re-based on its own clock), and logs the same messages. Every judgement is made from outside the implementation: what it returns over the protocol, what it leaves on disk, what Git reads from its repository, and what the harness itself observes about its files, its clock and its ref moves.

| Command | Use |
| --- | --- |
| `node --import=./scripts/test-isolation-preload.mjs --test scripts/ledger-dual-run/dual-run.test.mjs` | Self-test (in the scripts suite): the identifier site table, the comparer's undefined/null, background-callback, stamp and time checks, and one small recording replayed against the product worker (no difference allowed) and against two planted differences (JSON key order; stamps cut to microseconds), each reported by its own check |
| `node scripts/ledger-dual-run/dual-run-harness.mjs` | Full run: every scenario against the worker-thread and the stdio-process implementation, cross-reading, the aged-profile corpus read and mutated, every planted difference seeded and unseeded, crash points with recovery, lock contention between implementations, and the coverage report. `--suite=`, `--scenario=`, `--implementation=worker,process,native:<path>,native-unseeded:<path>`, `--allow-inconclusive=<scenario>,…`, `--json=<file>`, `--keep-artifacts`. Every row ends **passed**, **failed**, **inconclusive** or **info** (a characterisation). | Order of `verified-objects.v1` lines | compared as a multiset of lines |
| Git index files | compared by entries through Git, not bytes |
| Receipt pages and receipt results, whose order follows `files/<sha256(id)>` key order | compared as written when both runs follow the identifier protocol, else as rows ordered by path |
| Unreachable objects, loose/packed split | compared with the identifier protocol outside concurrent scenarios, else reported; every reachable object and every historical state tree always |
| `drain`'s list of settled background work, `git/info/refs` ids, pack names | whether it settled; ref names only; not compared (pack bytes follow object content) |

### The native ledger interface

A native ledger is driven with `--implementation=native:<path>` (it follows the identifier protocol) or `native-unseeded:<path>` (it does not; list orders that follow random identifiers are then compared by path, and the planted-difference suite shows which checks still hold). It must:

1. Start as `<path>` with no arguments and the arm's environment (`HOME`, XDG folders, `TMPDIR` and Git configuration inside the stage; `PATH` starting with the git shim). Exit when stdin closes.
2. Read one JSON line per host-to-ledger message on stdin, the first `{"type":"init","workerData":{"directory":<storage>,"maintenance"?,"batching"?,"complexity"?,"stallClock"?,"observers":{"onChange":bool,"onMaterialize":bool,"onDiagnostic":bool,"onLockTiming":bool,"onWorkerStall":bool}}}` (a worker thread also gets `lockPort`, a channel beside the seam on which it names its owner-lock tokens so its host can remove a lock it leaves when the thread dies; a ledger process never gets it and is not recorded with it: its locks name its own pid, which the lock protocol recovers when the process dies), then `call {id, method, input, context}`, `abort {id, reason}`, `callback-result {id, failed, value|error}`, `pull {stream}`, `stream-return {stream}`.
3. Write one JSON line per ledger-to-host message on stdout and nothing else: `ready {methods}` first, then `result {id, failed, value|error, steps}`, `report {id, record}`, `progress {id, waiting}`, `observe {observer, payload, cause}`, `callback {id, target:{call, fn}|{observer, cause}, args}`, `chunk {stream, done, value|error}`. Field meanings as in `session-mutation-worker.js`; values as in `session-mutation-wire.js` (function, stream and error markers). `context.deadline` is an absolute wall-clock time in milliseconds.
4. Encode values as `dual-run-codec.mjs` does: `{"$dr":"bytes","base64"}`, `{"$dr":"undefined"}`, `{"$dr":"number","value":"NaN"|"Infinity"|"-Infinity"|"-0"}`, `bigint`, `date`, `map`, `set`, and `escape` for an object that has a `$dr` key. Key order of objects is significant.
5. Move ledger refs with the `git` on its `PATH`, spawned directly by the ledger's own process (not through `sh -c`, whose pid the shim would see instead) as `git --git-dir <root>/git update-ref <ref> <new> [<old>]` or `update-ref -d <ref> [<old>]` (`--git-dir=<root>/git` also works; `GIT_DIR`, `-C` and `update-ref --stdin` are not read), as today's ledger does: the lock oracle, the lock bytes, the ref history, the commit order and the outside crash points observe those moves. A ledger that moves refs without the Git executable shows as making no moves, a difference.
7. Write `owner.lock` exactly as the JavaScript does (file 26 §3b): the bytes above, written to a temporary and linked, removed only by its owner.
6. Persist, return and call back exactly what the JavaScript ledger does (file 26 §4b and §4c): the same records byte for byte, the same summary steps, journal records, observer payloads and callbacks in the same order per call.

#### Identifiers and time

Identifiers. With `LEDGER_DUAL_RUN_IDS=<seed>` in its environment, a ledger draws every random identifier from the protocol instead of its random source (`dual-run-ids.cjs`): the nth draw (from 1) at site *S* during seam call *C* is `sha256("<seed>:<C>:<S>:<n>")` in hex, laid out as `8-4-4-4-12` with the version nibble set to `4` and the variant nibble to `8`. *C* is the `id` of the `call` message whose work draws it (work a call started counts for that call even after its result was sent; anything else is `background`). The harness gives each process generation its own seed (`<seed>:<generation>`). The sites are names, not source positions:

| Site | Names |
| --- | --- |
| `lease` | a lease token (`views/<token>`, `refs/devryan/leases/<token>`, `leases/<sha256(token)>.json`) |
| `document` | a file document ID (`files/<sha256(id)>.json`) |
| `operation` | an operation ID: publications, reconciled outside changes, direct receipts |
| `materialization` | a materialization intent (`materializations/<id>/`) |
| `transaction` | a revert, redo or file-restore transaction ID |
| `hold` | a native admission hold ID |
| `removal` | a native removal intent ID |
| `standby` | a parked or discarded view folder (`view-standby/<id>`) |
| `temporary` | any temporary file name, never left at rest |
| `lock-owner` | the `ownerToken` of a cross-process lock file, never left at rest |

Order within a site. *n* counts the draws of one site in one call, so where a call draws more than once at a site the order is part of the protocol. Measured over every scenario (`LEDGER_DUAL_RUN_ID_CENSUS`):

| Site | Draws per call (max seen) | Reference order | Reaches disk? |
| --- | --- | --- | --- |
| `lease`, `transaction`, `hold`, `removal`, `standby`, `materialization` | 1 | one per call | the value does; no order within the site arises |
| `document` | up to 297 | the order in which the call records paths it has no document for: an observation or warm in the order of its path list, a publication in the order of the lease's changed paths (each loop is sequential in `session-mutations.js`) | **yes**: the ID decides `files/<sha256(id)>`, whose key order numbers reconciled operations (`published.sequence`) and orders lease base lists and receipt rows. Under the protocol a native must draw in this order to compare byte for byte; a correct ledger that draws in another order runs as `native-unseeded:`, where documents are paired by `published.path` and those orders are compared by path |
| `operation` | 2 | one per external change, in the same path order as `document` | **yes**, as for `document` |
| `temporary`, `lock-owner` | 1,776 and 4 | whatever the JavaScript does (eight installs run at once) | **no**: never at rest, each site counts separately, and the lock token is replaced before lock bytes are compared; a different order or number of these draws never fails a run |

The JavaScript ledger is mapped to these names by the source text around each draw (`ID_SITES`), so moving a line or adding a comment keeps the name; a draw no entry names is logged through `LEDGER_DUAL_RUN_ID_LOG`, a protocol difference, and the self-test fails when any `randomUUID(` in the ledger's files has no name.

Time. A ledger reads the system clock; nothing is injected. The harness makes the time comparable instead: it takes its own wall-clock window around every group of calls it issues (from before the first is posted to after the last returns) and lets the clock move on by at least one millisecond between windows, so every stored time falls in exactly one window or gap; a time is compared by that window. A deadline crosses the seam as an absolute time, so a replay posts it the same distance from its own posting time as in the recording.

Optional, JavaScript only: `LEDGER_DUAL_RUN_CRASH` and `LEDGER_DUAL_RUN_AUDIT` (`ledger-preload.cjs`) add crash points at the JavaScript ledger's own file operations and notes on them; a native ledger is crashed from outside by the git shim instead. A crash point either kills the process, ends only the ledger's worker thread (`exit-thread`), throws an uncaught error in it (`throw`), or blocks it (`hold`) for the caller to kill or terminate; `scripts/harness-session-mutation-host.test.mjs` uses it to end the product's worker at each stage of its owner lock.

### Native ledger module tests

Before a native ledger exists, its parts are compared with the JavaScript module by module through test-only probes. The first is the lock and the atomic writes (`scripts/ledger-native/`, run by `node scripts/build-ledger-native.mjs --verify`; [harness runtime](../packages/harness-runtime/DOCUMENTATION.md#native-ledger-io)). The shared specification runs each scenario on both sides through a recording file system and requires equal results, codes, call traces and trees. Processes of both languages contend on one counter and reclaim each other's killed holders. On macOS a test-only interposer (`trace-interpose.c`, built with `cc` into the run's scratch) compares the system calls of `writeFileAtomic`, lock publication, `copyfile` and the sync chain between Electron's Node and the Rust, and fails `fsync` to compare how both fail. Every JavaScript arm runs on the reference runtime, the Node inside Electron (`scripts/ledger-native/reference-runtime.mjs`), or on the Node running the tests where Electron's binary is absent; the run prints which. The lock bytes are held to the same `LOCK_FORMAT` as the harness's lock audit. `scripts/build-ledger-native.test.mjs` runs the specification against the JavaScript alone in the scripts suite.

The object database (`ledger-io::git::odb`) is compared with Git, the oracle, through the test-only `odb-probe` (`scripts/ledger-native/odb-differential.mjs`, in the same verify). Git runs with a private `HOME`, no system or global configuration and no inherited `GIT_*` variables, in the run's scratch. It covers:
- seeded sha1 and sha256 repositories in eight pack layouts (loose, `repack -d`, `repack -a -d`, two packs and loose objects, no `.rev`, a 120-deep delta chain, REF deltas, 64-bit offsets) and three ref styles, compared with `cat-file --batch-all-objects --batch` and `--batch-check`, `cat-file --batch` of every id and `<tree>:<path>` name, `ls-tree -r -l -z` whole and by prefix, and `for-each-ref`, byte for byte;
- every "ask Git" case in its own repository;
- writes: Rust-written objects pass `fsck --strict --full` and are read by Git, by the JavaScript store and by its direct listings, and JavaScript-written objects are read by the Rust; both writers' call sequences, retries and failures are equal;
- reads during `repack` and `prune`, which must never give a wrong object or a false "absent";
- a crafted pack whose REF deltas have their base loose or in another pack, which Git reports missing and the Rust must ask Git about;
- corrupted packs, indexes and loose objects (seeded; half the rounds in the gate, all in the extended run; `LEDGER_NATIVE_ODB_FUZZ_SCALE` multiplies them), which must give the right object or "ask Git", never a panic, and stay within a memory bound.

Two longer runs stay outside the gate. The extended run, `node scripts/build-ledger-native.mjs --extended`, is the whole verify with every fuzz round, plus `scripts/ledger-native/odb-real-ledgers.mjs`: the aged-profile corpus and every dual-run scenario recorded, each ledger compared as written and repacked. It fails rather than skips when Electron's Node, the Linux lint target or a scenario is missing (`LEDGER_NATIVE_ODB_SCENARIOS` is refused). Run it after a change to the ledger's writers or the dual-run fixtures, which do not rerun the gate. `node scripts/ledger-native/odb-planted.mjs` plants twenty-one bugs in a copy of the Rust and requires each to be caught by the unit or differential tests.

| `node scripts/client-conformance/record.mjs --toys --check` / `--toys --update` | Records the toy corpus and compares it with `toy/expected` byte for byte, or records it twice and rewrites `toy/expected` only when both recordings agree. With `--out=<new or empty dir> [--port-map=] [--families=] <test file or directory>…` it writes containers for any test files; it refuses a directory that already holds files, so a stale container never sits beside fresh ones. Such a recording first runs the files without the recorder: a test whose outcome differs (`plain-differs`, such as one that fails plain on an unhandled rejection the recorder observed and marked handled) makes it inconclusive, so a recording is never the reference of a test that fails on its own. `stability.mjs` with test files does the same. `parity.mjs` stays the full check of harmlessness (assertion counts and output too) |
| `node scripts/client-conformance/vectors.mjs --check` / `--write` | Checks, or regenerates, `vectors.ndjson`: the codec cases (single values and identity scopes of several slots) a reader in another language must read and write back byte-equal |

**Exit codes**, the same for every tool (`record.mjs`, `parity.mjs`, `stability.mjs`, `vectors.mjs`; `compare.mjs`, `mutants.mjs` and the rest are libraries with no command line): 0 only for a complete run with no difference; 1 differences; 2 unstable cases; 3 inconclusive, with a message naming what is missing; 64 a usage error, an unknown or misspelled option included, and then the tool writes nothing. A run is inconclusive when it recorded nothing, when a family of the port map (all of them, or those named with `--families=`) has no case, when a test file the targets name (found with Bun's own test-file pattern) has no recording or no reported test, when the recorder saw another number of tests than junit lists, on any recorder error, when a test failed (its cases are `inconclusive`, never a reference), when any case is unrecordable, when an engine effect or input arrived after its file's recording was written (`unplaced`), when a test's outcome without the recorder differs from its outcome with it (`plain-differs`, product recordings), when the recorder ran two test files in one process (bun without `--parallel`: a recorder error), and when bun exits with an error (a bun killed by a signal counts as 128 plus the signal's number). There are no waivers yet, so every unrecordable case makes a product recording inconclusive. The toy fixtures (`toy-unrecordable.toy.mjs`, `toy-concurrent.toy.mjs`) are the one exception, and only for the toy tools: `TOY_UNRECORDABLE` in `record.mjs` lists each of their cases that must come out unrecordable with exactly one flag, and a listed case that does not, or any other unrecordable case, leaves the toy recording inconclusive; `TOY_UNPLACED` likewise names the fixture (`toy-unplaced.toy.mjs`) whose recording must count exactly one unplaced input. An inconclusive recording wins over instability: comparing it proves nothing. The last line of `record.mjs` and `stability.mjs` counts the case outcomes (recorded, unrecordable, inconclusive) and the problems; that of `parity.mjs` counts the differences and the inconclusive problems; that of `vectors.mjs` the vectors.

**Codec** (`codec.mjs`). A JSON tree in which objects tagged `"$dr"` carry what JSON loses: `undefined` against `null`, `-0`, NaN and the infinities, bigint, Date, Map and Set in insertion order, sparse-array holes (walked by own keys, so a far index costs nothing), arrays and typed arrays with a subclass or extra members, objects without a prototype, with a constructor-less chain or with a `$dr` key of their own, symbols, own symbol keys, functions (with the port name when the recorder wrapped them), class instances by constructor name, boxed primitives, errors with name, message, cause and an AggregateError's errors (never the stack or JavaScriptCore's line, column and source URL), DOMException with its name, message and code (so `AbortError` and `TimeoutError` differ), AbortSignal with its reason, bytes, ArrayBuffer and DataView, RegExp, URL, URLSearchParams, Headers, and Response and Request by status, URL and headers (never their bodies). A Proxy the recorder did not make is written as opaque and makes the case unrecordable, since its traps would run. An own accessor is written as `{"$dr":"accessor"}` and never called, and it marks the case unrecordable. Identity: a value is taken (`snapshot`) when it is seen and emitted later (`emitSlots`) together with the other slots of its scope, which is one case line; an object reached more than once anywhere in the scope gets `{"$dr":"id","n":k,"value":…}` at its first appearance in each slot (with its content when that slot was taken) and `{"$dr":"ref","n":k}` after that in the same slot, k numbered by first appearance in written order. So "returns its argument" and "returns a copy", and aliasing between arguments, results and states, record differently, and every slot still decodes alone. The scope is one family's line of one case: an object two families see in the same case is numbered separately in each family's container, and the two numbers say nothing about each other. Members keep the engine's own order (integer-like keys ascending first), strings are written as `JSON.stringify` writes them (lone surrogates as `\udXXX`), platform state is read through intrinsics captured when the codec loads, and the decoder refuses a tree that is not in canonical form. `decode(encode(v))` re-encodes to the same bytes.

**Container** (`container.mjs`). One NDJSON file per test file and family, named from the repository-relative test path (`/` as `~`, any other byte outside `[A-Za-z0-9._-]` as `%XX`, so two paths never share a name; a case-insensitive collision is an error, never an overwrite). A header (format, codec version, `recording`: the recorder's semantics version, bumped by hand whenever what a recording says changes; the port-map digest; `modulesDigest`: a digest of the sources of the family's module and its port modules, so a recording of older product code is told apart; the test file and its digest; the family: no tool version, path or time), a value table keyed by the first 16 hex digits of each value's SHA-256, then one line per case in file order. Slots `"=<hash>"` sit only in a case's value parts (entry state, steps, end state, context). The reader is strict: every line must be canonical JSON, every value must match its hash, and the table must hold exactly the referenced values in order of first reference. A case has its id (`<file>:<line> <describe> > <name> #<occurrence>/<family>` from Bun's junit report; `<file> #hooks:<k>/<family>` for what ran after the k-th test and before the next, k = 0 being module load and the first `beforeAll`; `<file> #concurrent:<k>/<family>` for an overlapping test, which is never named by order), its kind, the test's status, the outcome (`recorded`; `unrecordable` with its flags and a reason; `inconclusive` for a failed test), the random seed, entry state and nominal time, the steps, end state and time (taken when the test ends), and the test-originated context. A step is one input (`call`, `new`, `timer`, `settle` of a port answer, `callback` into the engine) with its nominal `now`, `during: n` when it arrived synchronously inside step n's port call, `caller` when another family's engine called this entry as its port, and `late: true` when it arrived after the case's test ended; the effects in observed order (`port` with arguments and answer, `new`, `read` and `set` of a port object's data, `timer.set`, `timer.clear`, `clock` and `draw` with their values, `settled` for a promise the engine returned; an effect that arrived after the test ended in a step opened before is marked `late: true`); and for calls the return or thrown value, the arguments after the call and, for draft-mutating entries, the change set (every container path, Map keys included, whose object identity changed). Engine port calls and timers are numbered per family and case; the test's own are `t1`, `t2`, …

**Recorder** (`recorder.mjs`, a `bun test --preload`). Layers, all on by default (`DEVRYAN_CONFORMANCE_LAYERS`):
- *clock*: timers keep real scheduling; `Date.now()`, `new Date()`, `Date()` and `performance.now()` read a nominal time that starts at 1,700,000,000,000 ms and moves, when any timer fires, to that timer's nominal due time, never backward; `performance.now()` moves only with the schedule. `setSystemTime`, `jest.setSystemTime` set the nominal time (and `setSystemTime()` returns to it); under fake timers the fake clock, started at the nominal time, is read, so `advanceTimersByTime` moves `Date.now()` and `performance.now()` as it does without the recorder. A clock stub the test installs (`Date.now = …`, `spyOn(Date, 'now')`, `spyOn(performance, 'now')`) answers, and its answers are recorded.
- *random*: `Math.random`, `crypto.getRandomValues` and `crypto.randomUUID` draw from a stream seeded by the test file and test ordinal (hooks cases by their position), the stream of the case whose code draws; every draw is recorded with its call site, a stub's answer included.
- *globals*: accessor properties on `globalThis` for `fetch`, the four timer functions, `WebSocket`, `EventSource`, `Date`, `performance`, `crypto`, `localStorage`, `sessionStorage`, `document`, `window` and `navigator` (and on `Math`, `crypto` and `performance` for the clock and random functions), so a stub a test assigns is wrapped as it is set. Bun's `spyOn` refuses accessors and installs nothing through a Proxy, so `bun:test` is re-exported (and `jest.spyOn`, `vi.spyOn` patched) with a `spyOn` that lowers the accessor to a data property around the call, spies on the object a recorder Proxy wraps, and re-arms the accessor right after. A test's own definition of one of these globals is never silent: a data property holding something the recorder did not wrap, or an accessor the test defined, hides what the engine does through it, so every case in which such a definition stands is flagged `global-defined:<name>` and is unrecordable. The globals are checked after every `Object.defineProperty`, `Object.defineProperties` and `Reflect.defineProperty` on their holder (observed through a Proxy of the native function) and at every test boundary, before the re-arming (the closing case) and after it (the opening case). A data property is re-armed at the next boundary; an accessor the test defined is never re-armed (its getter is the test's), so every later case is flagged until the test restores the recorder's own accessor. `packages/ui/src/sync/event-pipeline.test.ts` defines `navigator` that way, so its cases will be unrecordable once a family reads `navigator`.
- *mock-module*: `mock.module` is wrapped, so the exports of every module a test mocks are recorded as ports; last call wins and the factory runs when Bun runs it.
- *entries*: the families of the port map (`DEVRYAN_CONFORMANCE_PORT_MAP`, format in `port-map.mjs`). A family's module loads through a facade (a Bun plugin) whose entry exports are wrapped and whose port modules' exports are recorded; nothing is imported earlier than the test imports it, so a test's own `mock.module` of a dependency still applies. An export may be one family's entry and other families' port: a call from those families is their port call and the entry family's input. A module port is a port only for the families that list it. Objects handed in (`injected`) and answers that have methods or iterate (an SDK, an async iterator, a Response) become port objects: method calls are effects and data reads are inputs. A port's promise answers are seen as they resolve only when the map says `wrapAnswers` (on `globals.fetch`, on a module port, or on an `injected` item): what they resolve to then becomes a port object too when it has behaviour or a member with behaviour (`{ items: <async iterator> }`), so each item of a stream is a `settle` input of its own; the engine gets a derived promise, one microtask later. Without it the answer's resolved value is recorded as data, and a stream it carries is not seen.

Attribution follows design §2.4: a step is one input with everything the module did because of it, and a continuation belongs to the input whose delivery made it runnable. An `AsyncLocalStorage` store names the chain that runs (family, case, step); an entry call, a port answer settling, an engine timer firing and a callback the engine handed out being invoked each open a step, and every effect goes to the step of the chain it runs in, not to whichever step opened last. An input delivered to an existing chain (the answer to its port call, the firing of its timer, a callback it handed out being invoked later) moves that chain to the new step. An `await` resumes in the store it was registered in, so a promise that another input resolves (a gate a later call opens, a timer one call set that releases another call's waiter) needs more: with a port map, `globalThis.Promise` is a Proxy whose `new Promise` and `Promise.withResolvers` hand out resolve and reject functions that run the real ones inside a release window. Marker jobs are queued just before and after the real resolve, so the jobs between them are exactly the reactions it made runnable; each generation re-queues its markers, so the window follows every job those reactions queue in turn, until 64 generations pass with no engine code (`SILENT_GENERATIONS`). Engine code inside a window belongs to the resolving step, and its chain moves there (only forward). A reaction registered on such a promise after it settled (`then`, which `catch`, `finally` and the adoption of a returned promise call) by a chain older than the release joins the release too. A continuation that test code released (a promise the test resolves and the engine awaits), that port code released (a stub's own timer resolving a promise it handed the engine inside an answer), or that another family's or case's input released, was caused by no input of its family: its case is flagged `released` and is unrecordable. A port answer is a step of its own (`settle`, opened by a reaction registered before the engine's), so a port whose promise the test or the port itself resolves is unaffected. A window ends after 64 silent generations, but it is remembered: a chain of its family and case (or any chain, for a test's or port's release) that then wakes still in a step older than the window's, idle since before the window opened, may be a continuation the window lost (a waiter that awaits 65 more times, or 33 awaited helpers, after its gate opened), so its case is flagged `release-expired` instead of being misplaced. That check is conservative: a chain woken by something no window follows (a native promise, such as a raw `Response` body) after such a window expired is flagged too.

Engine code the test runs is an input of its family. What an entry hands back to the test is wrapped when it holds engine code: a function (an unsubscribe closure) is the entry `<entry>#<n>`, an object with engine methods or getters, an iterator or async iterator (a generator's `next`, `return` and `throw` run its body) and a thenable are wrapped so that each method call (`<entry>#<n>.<member>`) and each read of an engine getter (input kind `get`) opens a step, and whatever those return, and members that hold engine code, are handed out the same way, so `un()`, `for await (const item of entry())` and `await thenable` are recorded as steps. One wrapper per object keeps `toBe` between two handings of the same object; platform methods an engine object inherits are called on the object itself, so brand checks hold; what the test passed in or a port answered is never handed back out as engine code. `returns: "entry-object"` also wraps a result that is plain data, and an async entry's resolved value (through a derived promise, one microtask later). What cannot be wrapped soundly is refused: reading engine code from a non-configurable, non-writable member (a frozen object) flags the case `unwrappable`. Engine code that still runs with no engine chain (a function deep inside returned data, one the engine passed to a test's callback, module load) is flagged `outside-chain`, by two detectors: any call of a family's port (a module port, or a member of a port object of particular families) with no chain running is flagged whoever makes it, a test calling that port itself included, because JavaScriptCore's proper tail calls remove the frame of `() => port(…)` and the stack cannot tell the test from engine code; and any other effect with no chain running (a timer, a clock read, a draw, a global port) is flagged when a frame of a family's own module is on the stack, which is best effort (a tail call or code in a module the family imports leaves no such frame). What an engine timer, port answer, callback or resolve does after its test ended is recorded in that test's case, marked `late`, because cases are written only when the file ends; anything that arrives after the file's recording was written is counted as `unplaced` and makes the recording inconclusive. A call with no engine store came from the test and is recorded as context, never compared, unless one of the detectors above finds engine code running (then the case is `outside-chain`); code running inside a port (a test's stub) records nothing of its own. Tests that overlap (`test.concurrent`) are detected when a test starts while another is open: every case current during the overlap, hooks included, is flagged `concurrent` and unrecordable. Output goes to `DEVRYAN_CONFORMANCE_OUT` (a raw file per test file, never overwritten; the record tool names the cases from junit and writes the containers), and recorded paths are relative to `DEVRYAN_CONFORMANCE_BASE` (default: the repository); without an output directory everything runs and nothing is written.

One attribution gap remains, and it is deterministic (it depends on the number of awaits, not on timing): an engine chain that, still in an old step, awaits (`await`, not `then`) a promise another input already resolved (`const g = gate.promise; await null; await g` with the gate opened synchronously in between) resumes in its own step, since a native `await` registers no observable reaction. The continuation more than 64 generations from its release is no longer a silent gap: it is flagged `release-expired`.

**What a replayer must do** (C0d and every later reader of these recordings). Deliver each step's input, then run the engine to quiescence (no runnable job and no due timer left of that step) before delivering the next, and compare each step's effects after its quiescence. Delivering the inputs in their recorded synchronous bursts would reproduce the gap above as a pass; delivered one at a time to quiescence, a module that misattributes it records differently and fails the closure check. Deliver `during` inputs synchronously inside the port call of the step they name, `late` inputs and effects in their own case after its test ended, and handed-out entries (`<entry>#<n>…`, `get` inputs) on the value the named earlier step returned. Treat every case that is not `recorded` as no reference.

What the recorder changes that a test could observe, none of which a sync test depends on (pass-set parity): wrappers are Proxies, so a wrapped function or object is not identical to what was assigned and its `toString` reads as native code, and a stub assigned to a clock or random function reads back as its wrapper, so `expect(Date.now).toHaveBeenCalled()` on the assigned mock would fail (a spy's own handle works); `Object.defineProperty`, `Object.defineProperties` and `Reflect.defineProperty` are Proxies of themselves; with a port map, `globalThis.Promise` is a Proxy (`p.constructor === Promise` is false for every promise, an async function's included; `instanceof` holds) and `Promise.prototype.then` is a Proxy of itself, and release windows queue no-op jobs between the program's own, never reordering them; an absent global such as `window` becomes an accessor that answers `undefined`, so `'window' in globalThis` is true; a promise the recorder observes (a port answer or an entry's result) gets a reaction, so a rejection the engine leaves unhandled no longer surfaces (the plain run of a product recording catches a test that depends on it); a port listed with `wrapAnswers`, and an async `entry-object` entry, answer through a derived promise, one microtask later; engine code handed to the test is a Proxy, so a test that compares it with a reference it got another way (not through an entry) sees a different object; with a port map, an effect of test code with no engine chain captures a stack, and every resolve by test or port code opens a window (at least 130 no-op jobs); busy work timed with `performance.now()` reads 0 ms; and a trap that answers the same number for two timers makes a later clear of that number ambiguous (recorded as such).

**Self-test corpus** (`toy/`). A copy-on-write reducer, a debouncer with timers and an interval, a WebSocket and fetch client with an injected async stream and a logger port, a flow module whose inputs' consequences interleave (a port answer, a microtask continuation, an awaited timer, a re-entrant callback, a thrown DOMException, an argument returned against a copy) and that calls a guard family through its port, a gate module whose waiters other inputs release (a later call's signal, a timer an earlier call set, one signal releasing two waiters, a waiter many promise generations from its gate, a release inside another release's window, a `Promise.withResolvers` gate, a port answer delivered during a later call, negative controls that do not wait or yield twice first, and a timer that fires after its test ended while the next test touches no family), that hands the test engine code (a closure, an async generator looped over with `for await`, a class getter, a thenable), drains a stream an injected port answers (`wrapAnswers`), and checks that the program's own microtask order is the one bun gives without the recorder, a clock module that every kind of stub is installed for (assigned `Date.now`, spies on `Date.now`, `Math.random`, `crypto.randomUUID` and `fetch`, `setSystemTime`, fake timers, a stub that sets its own timer, a stubbed `navigator`, a skipped test), and hooks at module load, in `beforeAll` and in `afterAll`; every case of these is recorded. The fixtures must come out unrecordable as `TOY_UNRECORDABLE` lists: an accessor in a value, a `fetch` defined as a data property (and one defined and restored inside one test, and the next test re-arming it), a `navigator` defined as an accessor and standing into the next test, continuations released by the test, by a port's own timer, by another family's entry (a closure it handed out) and by the next test (whose effects stay in the waiter's case, marked late), a waiter that acts 66 generations after its release (`release-expired`), engine code deep inside returned data and a family's port the test calls itself (`outside-chain`), a frozen object's member (`unwrappable`), and overlapping `test.concurrent` tests; `toy-unplaced.toy.mjs` makes an engine call after its file's recording was written. Tests are named `*.toy.mjs` so no suite discovers them; `toy/port-map.json` maps them and `toy/expected/` holds their tracked recordings, which product edits never touch. Planted differences (`mutants.mjs`, built in the run root by exact anchored replacement): the nine of the first build, the 38 of the first review, thirteen that pin its fixes, ten of the second review's, sixteen that pin the second review's fixes, the eleven of the third review and ten that pin its fixes, 107 in all, each of which must be reported by its own check: the vectors at that vector, pass-set parity naming the toy test, the corpus comparison at the container, case, check and step (or a named problem of the toy recording, such as `unplaced-expected`), stability at the case, or a named tool check on fixed inputs. A planted difference may change a toy module itself (the gate that does not wait). The self-test records only the toy files a planted difference targets. The corpus and stability ones record together in one bun process (six workers; each test file gets a realm of its own, and a generated preload points it at its planted copy's recorder), beside an unchanged copy of the whole toy set that must equal `toy/expected` or the batch proves nothing; the others run six at a time beside it, and parity's plain runs of unchanged toy files are shared.

Every tool's scratch is `<os tmpdir>/devryan-client-conformance/run-*`, removed on pass, failure and interruption unless artifacts are kept (`--keep-artifacts`). Every `bun test` it starts runs inside the test isolation guard with `TZ=UTC` and the C locale.
