# DevRyan Testing

## Commands

| Command | Use |
| --- | --- |
| `bun run validate` | The local gate before every push and release tag. Diffs against the upstream branch (override with `VALIDATE_BASE`) and runs only what the change touches. |
| `bun run validate:full` | Lint (TypeScript and JavaScript), import boundaries, the browser graph, unreached browser files, declaration parity, type-check, `docs:validate`, build (once), `bundle:check` and `test:full`. CI runs these same checks across its build and test lanes. |
| `bun run test:startup` | Curated startup and user-data contract. |
| `bun run test:full` | Scripts and every package suite, as one bounded concurrent pool (`node scripts/test-full.mjs [--suite=web,ui]`). |
| `bun run docs:validate` | Markdown links and inline-code paths, and drift against package manifests, source exports and environment-variable names. |

`bun run validate` runs:

- oxlint on changed `.ts`/`.tsx` files inside the directories `bun run lint` covers (the targets of each workspace's oxlint `lint` script, today `packages/ui/src` and `packages/web/src`), so fast and full lint check the same files (everything when shared configuration changes);
- the JavaScript lint (`node scripts/check-js-lint.mjs --files <changed>`, see [JavaScript lint](#javascript-lint)) on the changed `.js`, `.mjs`, `.cjs` and `.jsx` files, deleted ones included so their baseline entries are found stale; every JavaScript file when `.oxlintrc.javascript.json`, `scripts/js-lint-baseline.json` or the checker changes, and through `bun run lint` when shared configuration changes;
- type-check of changed packages and their dependents (everything when root `package.json`, `bun.lock`, `patches/`, `.oxlintrc.json`, `tsconfig.json` or `.opencode/opencode.json` change). Any `packages/ui/src` change also type-checks web, whose tsconfig includes the UI source, and a `scripts/opencode-v2-native/*.ts` change type-checks web, whose runtime-host tsconfig includes those files;
- tests of changed packages and their dependents: any file under `packages/ui/src` runs the UI suite, any `packages/web` file (server, bin, src, the Vite and Vitest configuration, test setup) the web suite, any `packages/agents-core` file the agents-core suite and its web dependent;
- every suite in `FULL_TEST_SUITES` when root `package.json`, `bun.lock`, `patches/`, `.nvmrc` or `bunfig.toml` change (so a patch edit runs `scripts/opencode-v2-native/mcp-client-patch.test.mjs`);
- `test:scripts` when `scripts/`, `.github/`, `.opencode/agents|plugins` or `packages/web/runtime/reviewed-inputs` change (their Markdown and text included, since the reviewed-inputs manifest hashes every file), and `bun run catalog:check` (which fetches the live catalog) when the reviewed model catalog changes;
- `docs:validate` for every change: besides Markdown it reads package manifests, source exports and environment-variable names, so a code-only change can make docs stale;
- import boundaries and the browser graph when package code changes (every importer when a package manifest, `scripts/import-boundaries.json` or a checker changes); unreached browser files for the same changes, any test file, `scripts/unreached-files.json` or its checker; declaration parity for any JavaScript or declaration file, package manifest, `scripts/declaration-parity.json` or its checker;
- the Rust ledger core check, `node scripts/build-ledger-core.mjs --verify` (format, clippy, `cargo test` and a byte-for-byte rebuild of the tracked module), with the script tests that read the crate, when `packages/harness-runtime/native/ledger-core/`, `scripts/build-ledger-core.mjs` or the tracked `packages/harness-runtime/lib/native/ledger-core.*` change; only these changes need the pinned Rust toolchain, and without it the check fails with the command that installs it ([harness runtime](../packages/harness-runtime/DOCUMENTATION.md#rust-ledger-core)). A tracked module change also runs the harness suite;
- the native ledger check, `node scripts/build-ledger-native.mjs --verify` (format, clippy and `cargo test` of `packages/harness-runtime/native/ledger/`, the same lint for x86_64 Linux when that target is installed, then the JavaScript lock and atomic writes against the Rust ones), with the script tests that read the workspace, when one of its inputs changes: the files `scripts/ledger-native/inputs.mjs` lists (that workspace, the ledger core's crate, `packages/harness-runtime/lib/atomic-file.js` and every local module the verify loads); it needs the same pinned toolchain and the network for `cargo fetch` ([harness runtime](../packages/harness-runtime/DOCUMENTATION.md#native-ledger-io));
- the Cargo workspace check, `node scripts/check-native.mjs` (the licence check of `scripts/check-native-licenses.mjs` against the allow list in `deny.toml`, `cargo fmt --check`, clippy with warnings denied and `cargo test`, locked), with the script tests that read the workspace, when `packages/native/`, `scripts/check-native.mjs` or `scripts/check-native-licenses.mjs` change; without the pinned toolchain it fails with the command that installs it ([packages/native](../packages/native/DOCUMENTATION.md#gates)). Nothing in the workspace reads the server's sources, so a change under `packages/web/server` runs no native check. The `devryan-config-text` crate is held to tracked vectors that its generators write with the installed `jsonc-parser` and `yaml`; `scripts/check-native.test.mjs` regenerates them in memory without Rust, in its own process (about 1.7 s of CPU, measured at load average 37 on an 8-core Apple M-series machine) and fails with the command to rerun a generator, so a `bun.lock` change that alters either package's behaviour fails the scripts suite. Its differential probe and planted bugs are run by hand ([packages/native](../packages/native/DOCUMENTATION.md#devryan-config-text)). Recording and comparing traffic is not part of it: that will be a separate package, whose recordings stay in a run's scratch ([packages/native](../packages/native/DOCUMENTATION.md#devryan-front));
- `test:startup`, always: each startup group whose owner suite already runs in the same plan runs there instead of twice.

Fast mode narrows `test:scripts` to the script tests whose closure holds a changed file (`scripts/test-select.mjs`). The closure follows each test's imports, resolved as `scripts/check-import-boundaries.mjs` resolves them, and every file its scripts and tests name by path or file name (a spawned script, a `Bun.build` entry, a read fixture); shipped package code reaches files only through its imports and module URLs. Only a file that puts the scripts suite in the plan (under `scripts/`, `.github/`, `.opencode/agents|plugins` or the reviewed inputs) can widen the run: such a non-code file (workflow, fixture, JSON, shell) selects the tests naming it or its outermost directory (`.github` for workflows), and the whole suite when none does. Other changed files, such as package code, only add the script tests that reach them. A file under `packages/harness-runtime/native/ledger-core/` or `packages/harness-runtime/native/ledger/` also selects the script tests that read that whole tree (`TREE_READERS`: `scripts/build-ledger-core.test.mjs`, `scripts/build-ledger-native.test.mjs`), and a file under `packages/native/` selects `scripts/check-native.test.mjs`. Markdown and text files never enter the graph: any Markdown change other than `CHANGELOG.md`, alone or beside code, runs `scripts/release-docs.test.mjs`, which reads every tracked Markdown file for the published-release rule `docs:validate` does not check; Markdown under one of those trees also runs that tree's tests (the workspace's contract checks what its `DOCUMENTATION.md` says); and no script test reads tracked `.txt` files. Changes to the selector, its resolver, the suite runners (`validate.mjs`, `test-scripts.mjs`, `test-runner-utils.mjs`, `test-full.mjs`, `test-ci-lanes.mjs`, `test-pool.mjs`), the suite contract, reviewed inputs or the toolchain run the whole suite, and a changed test file also runs the inventory's tests. A change to a test file of any package, even one that does not put the scripts suite in the plan, also runs `scripts/test-suite-contract.test.mjs`, which inventories every test file. `scripts/test-select.test.mjs` checks on this checkout that every file in every script test's import and name closure selects that test. `validate` prints the selection and why the rest were skipped; a subset leaves the startup scripts group in `test:startup`. `validate:full` and CI always run every script test. A script test named `<name>.full.test.<ext>` (`FULL_SUITE_ONLY` in `scripts/test-select.mjs`) is a full-suite test: fast mode drops it from any selection, a whole-suite one included, and prints it as left to `validate:full` and CI.

A change confined to the `version` fields that `scripts/bump-version.mjs` writes (package manifests, workspace versions in `bun.lock`, the legacy Tauri `tauri.conf.json`, `Cargo.toml` and the `devryan-desktop` entry in `Cargo.lock`) runs `node scripts/release.mjs check-versions` (every version file and `bun.lock` workspace agrees) instead of every package's lint, type-check and tests. Any other change to those files keeps the full shared-configuration plan. CI still runs everything for the bump commit before release admission.

Independent static checks run concurrently and all report, and any failure stops before tests. In `validate:full` the build and bundle budgets then run in order beside the test pool, and `scripts/built-web-assets.test.mjs` (the only test that reads the build output) runs after the build; `validate` (fast) runs no build. Test commands run as one weighted pool of independent processes within a capacity of `DEVRYAN_TEST_CONCURRENCY` (default: half the cores, between 2 and 4). A unit reserves its `weight` (default 1): the Vitest `web` project and the harness suite start their own workers and weigh 2. Local runs split the serial `node --test` script batch into three timing-balanced shards and the web runtime-host project into two (`localTestUnits` in `scripts/test-ci-lanes.mjs`; CI lanes use their own inventory). While the host's 1-minute load average is above its core count, the pool starts no further unit (one always runs), so concurrent runs on one machine (other worktrees, a build) queue instead of driving timeouts; `DEVRYAN_TEST_LOAD_LIMIT` sets the ceiling as a multiple of the cores and `0` disables it. Every unit has a wall-clock budget (`DEVRYAN_TEST_UNIT_TIMEOUT_MS`, default 20 minutes) after which its process group is killed and it fails as timed out; script `node --test` files also get `--test-timeout=300000` and `--test-force-exit`. Each Bun package run gets the cores the pool leaves it (`--parallel=<cores / DEVRYAN_TEST_CONCURRENCY>`, at least two, scaled by a heavy unit's weight; `DEVRYAN_TEST_WORKERS` overrides), each unit's output printed whole when it ends, a heartbeat naming running units every minute, every unit run to completion and every failure listed. Native graph test files share one exclusive pool resource: they build and spawn the pinned runtime, and the shared fixture's browser OAuth callback binds localhost:1455. Independent units keep running alongside them. Interrupting stops every owned process group and removes the run's scratch. Both modes end with per-command and slowest-unit timings.

`scripts/check-import-boundaries.mjs` resolves static, re-export, `require` and literal dynamic imports between packages. Application packages (web, Electron, legacy desktop) expose only their `main`/`exports`; a package that declares `exports` exposes only those targets, by package name or relative path. Tests (`*.test.*`, `*.spec.*` and files under a `tests/` directory) may import another package's private files, since parity and integration tests exercise both sides; they are still refused a package-name import that the target's `exports` omit. Each temporary exception in `scripts/import-boundaries.json` (production code only; currently none) is one exact importer/target pair with the plan stage that removes it (`unscheduled` when none does yet); an exception that no longer matches fails, so the list only shrinks. No exception covers a package-name import of a subpath the target's `exports` omits, because Node refuses that import at runtime. `scripts/check-browser-graph.mjs` walks the web Vite entry points with the build's aliases and fails on Node builtins, `adm-zip`, or a web-server, Electron or Node-only shared-runtime file.

`scripts/check-unreached-files.mjs` walks the same graph, with the same resolver, from the web entry points and the service worker (`packages/web/src/sw.ts`), and again from every tracked test file (a server test contributes its own imports; the walk stops at privileged files as the browser graph does). Every code file under `packages/ui/src` and `packages/web/src` that neither walk reaches fails, unless `scripts/unreached-files.json` lists it with a kind (`awaiting-removal` for dead code a later phase deletes, `hand-run` for a tool run by hand and kept on purpose) and a reason; it also prints, as information, how many files only tests reach (`--verbose` names them). Two known limits: a file reached only through `import type` counts as reached, and helpers under a `test/` directory inside `src` count as tests, so they are not checked. The server packages are out of scope: their string-built dynamic imports make a file-level check noisy. `scripts/check-declarations.mjs` pairs every first-party hand-written declaration with its JavaScript twin (`x.d.ts` with `x.js`, `x.d.mts` with `x.mjs`, and the `types`/`default` pairs of package manifests) and fails when the declaration exports a value the implementation does not; type-only exports need no implementation, relative re-exports are followed on both sides, and exports the implementation has without a declaration are information (`--verbose` lists them). Vendored reviewed inputs and the frozen legacy desktop package are skipped. A pair it cannot compare (a CommonJS implementation, or one that re-exports a package) fails too. `scripts/declaration-parity.json` lists known mismatches and uncomparable pairs, each with its reason, and, separately, `transformExports`: permanent exemptions for names a native build transform adds to the bundled copy of an implementation only (the browser and document-reader plugins), each naming its transform; such an exemption fails when the transform's source stops exporting the name or the shipped implementation starts exporting it. The other lists only shrink: an unlisted finding fails, and an entry that no longer matches (the file is now reached or deleted, or the declaration was fixed) fails until it is removed. `--prune` on either checker removes stale entries and never adds one; fix the finding instead of listing it.

A docs-only change runs only `docs:validate`. Both validate modes fail if the run left anything new in the repository, files or folders (empty and dot-named ones included), outside the tracked paths, `.claude/`, editor droppings (whole file names), declared build outputs, kept caches and scratch-family folders listed in `GUARD_ALLOWANCES` (`scripts/cache-guard.mjs`); the guard removes nothing, names what a killed or interrupted test left with the command that removes it, and reports when it cannot judge (see [STORAGE_CLEANUP.md](STORAGE_CLEANUP.md#scratch-guard)).

## CI

`.github/workflows/ci.yml` runs on every main push and pull request. Every job starts at once; none waits for another and no artifacts move between them:

- `static` (Ubuntu): `node scripts/validate.mjs static` — lint, import boundaries, the browser graph, unreached browser files, declaration parity, type-check and `docs:validate`, run concurrently. Then, on every push and on a pull request that changes the ledger core's crate, build script, tracked module or `ci.yml`, it installs the pinned Rust and runs `node scripts/build-ledger-core.mjs --verify`, whose rebuild must match the module built on macOS byte for byte. A second step does the same for the native ledger (the inputs `scripts/ledger-native/inputs.mjs` prints, or `ci.yml`) and runs `node scripts/build-ledger-native.mjs --verify` on Linux; the system-call traces in it need macOS and report themselves skipped there. On every push, and on a pull request that changes `packages/native/`, `scripts/check-native.mjs`, `scripts/check-native-licenses.mjs` or `ci.yml`, it installs the pinned Rust and runs `node scripts/check-native.mjs`, licence check included, then the RustSec advisory check `node scripts/check-native.mjs --advisories` with cargo-deny 0.20.2 kept in GitHub's cache; a new advisory not ignored, with its reason, in `deny.toml` fails the job ([packages/native](../packages/native/DOCUMENTATION.md#gates)).
- `build` (Ubuntu): `node scripts/validate.mjs build` — the build, bundle budgets and the tests of the built assets (`BUILD_JOB_TESTS` in `scripts/test-ci-lanes.mjs`, such as `scripts/built-web-assets.test.mjs`).
- `tests` (two Ubuntu lanes): `node scripts/validate.mjs ci:<lane>` with the normal scratch guard.
- `native-tests` (three macOS lanes): build and verify the native v2 runtime in-lane (cheaper than shipping it between jobs), then run their lane. Lane `native-1` then runs the native ledger verify on macOS, filtered like the Ubuntu step, even when its suites failed: the macOS-only code, the sync chain and the system-call traces are tested there. GitHub Free runs five macOS jobs at a time and a release holds two while it waits for CI, so three is the most CI may use.

`scripts/test-ci-lanes.mjs` expands the full suite into files before assigning platforms; it keeps macOS sandbox, native binary, case-insensitive filesystem and platform-gated checks on macOS. Units are packed onto lanes longest first from the recorded durations in `scripts/test-unit-timings.json` (a unit without a recording costs the median); the web runtime-host Vitest project runs as two shards. Every lane uploads its unit timings as the `test-timings-<lane>` artifact; refresh the recordings with `bun run test:timings:update <files...>`. The native-stream file has two disjoint case shards (ordinary local runs register every case); `test-suite-contract.test.mjs` checks the complete inventory and shard union, and that a case-sharded file registers every test through its shard filter. CI runs Bun package suites in randomized order seeded with the workflow run number (`DEVRYAN_TEST_SEED`). Main-push concurrency is unique to the commit SHA and never cancels a different main commit; superseded PRs still cancel. Release preparation overlaps CI, but publication requires the exact main-push workflow to pass. `bun run validate:full` remains the equivalent complete local gate. `release-cache.yml` is manual-only; see [Release pipeline](RELEASE_PIPELINE.md).

Measured and deliberately not adopted (2026-10): caching `tsbuildinfo` or the Vitest module cache in CI (TypeScript 7 type-checks every package in about 26 s run one after another, measured 2026-11, and transforms are 1–2% of Vitest time), parallel `node --test` for the script suite (no speedup; deadline-sensitive tests fail under contention), and moving hazard-free web tests to `bun test` (they rely on Vitest APIs such as `vi.waitFor`, and parallel Vitest already runs them in under a minute).

## Startup contract

`scripts/test-startup-contract.mjs` runs the startup and user-data tests: runtime bundle startup, selection and upgrade, ledger and session integrity, Retry, cancellation, delayed bootstrap, event subscription, and Electron startup and ownership. It uses disposable fixtures only: no installed-app data, live accounts or OS service registration. `STARTUP_CONTRACT_GROUPS` names each group's owner suite (`electron`, `scripts`, `shared`, `harness`, `ui`, `web`); `--covered-by=<suite,...>` skips groups already covered elsewhere in the same run.

## Suites and runners

`test:full` runs every suite below, including the bundled Plan Mode contract in the frozen legacy Tauri package. Cargo tests are not run because they require native build assets. `FULL_TEST_SUITES` in `scripts/test-full.mjs` is the inventory. The pool splits three suites without changing what they run: one process per script Bun test file, the two Vitest projects of the web suite (`test:vitest --project=web|web-runtime-host`) beside its Bun native files (`test:native`), and the harness suite with Bun file workers (`bun test --parallel=4`). `scripts/test-suite-contract.test.mjs` checks every split runs each file exactly once.

Set `DEVRYAN_TEST_TIMINGS=<file.json>` to record each unit's duration and status. Set `DEVRYAN_TEST_SEED=<n>` to run Bun package suites in randomized order (`--randomize --seed=<n>`); a failure reproduces with the same seed. Tests must not depend on the order of other tests: reset shared stores, module-level mocks and globals in `beforeEach`, not only `afterEach`.

Expensive invariants are tested at the smallest size that crosses the boundary. Production limits that tests must exceed (ledger install batches, the change-store listing bound, the admission dedupe cache) are constructor options with unchanged defaults, so a test crosses them with a few hundred records instead of tens of thousands. Create test Git repositories with `initGitRepository()` from `scripts/test-git-template.mjs` (a copied template, about ten times faster than `git init`).

| Suite | Command | Runner |
| --- | --- | --- |
| Scripts, `.opencode/agents` and `.opencode/plugins` tests, reviewed runtime inputs | `bun run test:scripts` | `scripts/test-scripts.mjs`: files importing `bun:test` run one per `bun test` process (never sharing Bun's resolver), the rest in one `node --test` run, all through the bounded pool. `DEVRYAN_SCRIPT_TEST_CONCURRENCY` sets Node concurrency (default: one file at a time inside the outer pool). |
| Shared UI | `bun run --cwd packages/ui test` | `scripts/test-ui.mjs`: one `bun test --parallel` run in the isolation guard's environment; every file gets its own global and module registry, so `mock.module` and global replacements cannot leak |
| Web | `bun run --cwd packages/web test` | each step inside `scripts/test-isolation-guard.mjs`: `test:vitest` (`vitest.config.ts`: project `web` file-parallel with a 15 s test budget; project `web-runtime-host` with two workers for the native runtime-host suites; no app build plugins), then `test:native`: five native runtime-host files, the native integration directory and the native isolation canary under `bun test`. Native host scripts: `bun run --cwd packages/web test:native-host`. |
| Electron | `bun run --cwd packages/electron test` | `scripts/test-electron.mjs` routes by import, in the isolation guard's environment: `node:test` to Node (concurrent files, with the isolation `--import`), `bun:test` to one `bun test --parallel` run; any other framework is refused |
| Legacy Tauri JavaScript contract | `bun run --cwd packages/desktop test:managed-orchestration` | `bun test` (the frozen manifest is unchanged: run it through `test:full`, or wrap it in `node scripts/test-isolation-guard.mjs`) |
| `shared-runtime`, `harness-runtime`, `orchestration-runtime`, `cursor-sdk-runtime`, `agents-core` | `bun run --cwd packages/<name> test` | `bun test` inside `scripts/test-isolation-guard.mjs` |

Runner and discovery changes belong in `scripts/`. Feature tests live beside their source unless a contract spans packages.

## Test isolation

The `DEVRYAN_*` and `OPENCODE_*` variables production code reads are named in [environment variables](ENVIRONMENT.md), each described there or linked to the page that describes it; the guard below decides which of them a test may inherit.

No test process may read or write the real home folder, DevRyan, OpenCode or Git configuration. `scripts/test-isolation-guard.mjs` builds a private environment, and `scripts/test-isolation-check.mjs` checks it inside every test process.

The environment (`createTestIsolation`): one private root per run, `<os tmpdir>/devryan-test/run-*`, holds `HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME` and a private `GIT_CONFIG_GLOBAL` with a test identity (`GIT_CONFIG_NOSYSTEM=1`, `GIT_TERMINAL_PROMPT=0`). Every inherited variable that selects a location, endpoint or credential is removed, not re-pointed: `DEVRYAN_*`, `OPENCHAMBER_*` and `OPENCODE_*` names ending in a location, URL, host, port, binary, token, secret, password, key or identifier suffix (for example `DEVRYAN_DATA_DIR`, `DEVRYAN_RUNTIME_BUNDLE_ROOT`, `OPENCODE_CONFIG_DIR`, `OPENCODE_DB`, `OPENCODE_BINARY`, `DEVRYAN_SESSION_TMP`, `DEVRYAN_SERVER_URL`, `OPENCODE_PORT`, `OPENCODE_SERVER_PASSWORD`), plus `CLAUDE_CONFIG_DIR`, the Meridian, Cursor and `gh` locations, the `GIT_DIR`/`GIT_CONFIG_*` family and `SSH_AUTH_SOCK`. Each root then resolves to its default under the private `HOME`, exactly as in CI, which sets none of them. Product behaviour switches, limits and timeouts pass through (`PASSED_THROUGH` in the guard); `scripts/test-suite-contract.test.mjs` fails when product code reads a `DEVRYAN_*`, `OPENCHAMBER_*` or `OPENCODE_*` name that is in neither list. `TMPDIR` is left as the runner sets it. The root is removed when the run passes, fails or is interrupted (kept with `--keep-artifacts` or `DEVRYAN_KEEP_ARTIFACTS=1`), and a runner started inside an isolated environment reuses it. Bun's runtime transpiler cache (`BUN_RUNTIME_TRANSPILER_CACHE_PATH`) stays at its existing location: it holds only transpiled sources.

The check (`scripts/test-isolation-preload.mjs`) runs before any test: the Bun `preload` of the root `bunfig.toml` and of every package that runs `bun test` except the frozen `packages/desktop`, the `--import` of node:test runs, and the web Vitest global setup and setup file. It requires the home directory, the XDG folders, the Git configuration and every stripped variable that is still set to lie inside the private root named by `DEVRYAN_TEST_ISOLATION_ROOT`. What happens without that environment depends on the runtime:

- Node (`node --import=…preload --test`, Vitest): the process builds the environment itself, before any test or product module loads, because Node's `os.homedir()` follows `HOME` on every call; Vitest's workers inherit it. These direct runs are isolated.
- Bun: `bun test` reads `HOME` once at startup and its preload sees neither the command line nor the filters (`process.argv` holds only the test file; `ps` loses quoting, and with `--parallel` the preload runs in each worker), so it can neither move the process nor run it again. A bare `bun test` stops before any test with `DevRyan test isolation: refusing to run tests against the real home folder.`, the reason and the command that runs one file in that folder.
- A bare `node --test` without the `--import` loads nothing of the guard (Node reads no configuration file by default) and is not isolated.
- A `bun test` started inside a source subfolder (for example `packages/web/server` or `packages/ui/src`) reads no `bunfig.toml`, so the preload never runs. The shared test setups that such files import (`packages/ui/src/test/mountedDom.ts`, `packages/harness-runtime/test/session-mutations-fixture.js`, `packages/harness-runtime/test/session-change-fixture.js`) stop the file with the same explanation; other files run unguarded. Start `bun test` from the package folder.
- `packages/desktop` is frozen: its one contract file is isolated when a runner (`test:full`, `validate`, CI) starts it, not when it is run directly.

| `packages/web`, Vitest | `bunx vitest run <path>.test.js` |

| `packages/ui` | `bun run test src/<path>.test.ts` |

| `packages/electron`, `node:test` file | `node --import=../../scripts/test-isolation-preload.mjs --test <path>.test.mjs` |

`bun run --cwd packages/web test <file>` is not a single-file command (the file reaches only the last of its two steps), and the Electron runner ignores file arguments. `node scripts/test-isolation-guard.mjs <command> [args...]` wraps any command. Every repository runner builds the environment for its own processes: `bun run test:full`, `node scripts/test-scripts.mjs`, `bun run test:startup`, `bun run validate`, the CI lanes (through `prepareScriptTestEnvironment` in `scripts/test-scripts.mjs`), the built-asset tests (their `--import`), and the package `test` scripts (`node ../../scripts/test-isolation-guard.mjs bun test`, and the UI and Electron runners).

Each runner collects an isolation canary (`scripts/test-isolation-canary.test.mjs`, `scripts/test-isolation-canary-bun.test.mjs`, an `isolation-canary` test in every package, one in each web Vitest project) that takes the home folder, the DevRyan data root, the runtime-bundle root and the OpenCode config and data folders from the product modules that resolve them, derives the OpenCode state and cache folders and the DevRyan log folder from `XDG_*` and `HOME` as the bundled OpenCode host and Electron do (neither exposes an importable resolver), checks the Git identity, and requires each inside the private root. `scripts/test-isolation-guard.test.mjs` runs every canary and shows each Bun runner refusing and each Node runner isolating itself without the guard's environment; the suite contract fails when a runner, unit or package test script starts tests without the preload, the import or the environment.

## Policies enforced by lint

Module-graph rules that used to be source-text tests (a component must not import an eager dialog, a removed surface, or a heavy renderer; a file must not own timers) live in `.oxlintrc.json` `overrides` as path-scoped `no-restricted-imports` and `no-restricted-globals` rules, so `bun run lint` enforces them once instead of a test reading the source. Tests assert behaviour: rendered markup, calls and state, not the text of the implementation. Keep a source read only for a genuine text contract (CSS rules, generated assets, documentation).

## JavaScript lint

`bun run lint` runs each workspace's `lint` script (oxlint with `.oxlintrc.json` on `packages/ui/src` and `packages/web/src`, whose configuration ignores JavaScript), then `bun run lint:js`: `scripts/check-js-lint.mjs` lints every other first-party `.js`, `.mjs`, `.cjs` and `.jsx` file in the repository, tracked or new (the web backend, Electron's main process, the runtime packages, the scripts, the frozen desktop package and the root tests), with `.oxlintrc.javascript.json`. That configuration extends `.oxlintrc.json`, so both run one rule set, and states beside each JavaScript-only change its reason: `no-control-regex` and `require-yield` are off, `no-empty` allows an empty `catch`, `no-unused-expressions` allows ternary and short-circuit statements, `typescript/no-require-imports` is off for `.cjs`, `react/only-export-components` for `tests/`, and three vector rules for the conformance and fuzz vector generators. It never lints the vendored `packages/web/runtime/reviewed-inputs/` or the generated `routes.generated.js`. Packages have no JavaScript `lint` script of their own; the root check covers them and prints its counts per package. Fast `validate` runs it on the changed files; `validate:full` and CI's `static` job run it on all of them.

The findings that existed when JavaScript came under the linter are in `scripts/js-lint-baseline.json`, one `{ file, rule, count }` per line, sorted by file and rule in code-unit order, without line numbers so an unrelated edit does not churn it. The check fails on a finding the baseline does not cover (a new rule in a file, or more findings of a rule in a file than recorded; it prints each location), on an entry that no longer matches (fewer findings, none, or the file deleted or no longer linted), on a baseline not in that canonical form, and on any file oxlint cannot parse, which is never baselined because no rule ran on it. To shrink it, fix findings and run `node scripts/check-js-lint.mjs --prune`, which lowers or removes the stale entries and never adds one. A new finding is fixed; one that must stay (a deliberate idiom) is added or raised only by hand in the reviewed change, with the line the failure prints. `scripts/check-js-lint.test.mjs` plants a new finding, an increase, a stale entry and an unparsable file, and passes on the tree as it is.

## Test-suite contract

`scripts/test-suite-contract.test.mjs` fails when a test file is not discovered by its package runner, when a deterministic test uses `skip`, `todo` or `only` (`test.skip(`, `{ skip: … }`, `.todo(`, `.only(`), when a conditional skip is not inventoried, or when the feature matrix is stale. ## Ledger dual-run harness

`scripts/ledger-dual-run/` checks one implementation of the session mutation ledger against another before any of it is ported (plan row L0). It changes no product file. It records a scenario through the product host (`createSessionMutationHost`, worker thread and all) with a tap on the host's `Worker`, so every message that crosses `packages/harness-runtime/lib/session-mutation-host.js` is logged. A replay posts the recorded `call` messages to another implementation on a fresh twin of the fixture, behaves as the recording's host behaved (the recorded answers to input functions, observer callbacks answered as the host answers them, `abort` and `stream-return` where the host sent them, deadlines re-based on its own clock), and logs the same messages. Every judgement is made from outside the implementation: what it returns over the protocol, what it leaves on disk, what Git reads from its repository, and what the harness itself observes about its files, its clock and its ref moves.

| Command | Use |
| --- | --- |
| `node --import=./scripts/test-isolation-preload.mjs --test scripts/ledger-dual-run/dual-run.test.mjs` | Self-test (in the scripts suite): the identifier site table, the comparer's undefined/null, background-callback, stamp and time checks, and one small recording replayed against the product worker (no difference allowed) and against two planted differences (JSON key order; stamps cut to microseconds), each reported by its own check |
| `node scripts/ledger-dual-run/dual-run-harness.mjs` | Full run: every scenario against the worker-thread and the stdio-process implementation, cross-reading, the aged-profile corpus read and mutated, every planted difference seeded and unseeded, crash points with recovery, lock contention between implementations, and the coverage report. `--suite=`, `--scenario=`, `--implementation=worker,process,native:<path>,native-unseeded:<path>`, `--allow-inconclusive=<scenario>,…`, `--json=<file>`, `--keep-artifacts`. It isolates its own process from the owner's home and Git configuration first |

Every row ends **passed**, **failed**, **inconclusive** or **info** (a characterisation). Inconclusive is never a pass: the run exits 0 only when nothing failed and nothing was inconclusive, 1 when anything failed, and 2 when only inconclusive rows remain; `--allow-inconclusive` names scenarios whose inconclusive rows are counted and shown but not fatal. The last line prints the counts and the coverage summary. The full run also fails when a method of `SESSION_MUTATION_METHODS` or a seam message type is neither exercised by a scenario nor listed in `COVERAGE_WAIVERS` (`dual-run-suites.mjs`) with a reason, or when a method is only ever called or refused and never had a successful call whose result and effect on disk were compared (unless `COVERAGE_WAIVERS.refusedOnly` names it), and when a crash point expected to be reachable is not reached.

Every run uses `<os tmpdir>/devryan-ledger-dual-run/run-*` (removed on pass, failure and interruption unless artifacts are kept), runs at the same stage path one after another, and gives each arm and its ledger a private `HOME`, XDG folders, `TMPDIR` and Git configuration (no hooks, no templates) inside the stage. Fixtures and every Git command the harness runs itself read no system or global Git configuration.

What the comparer checks, and the independent observations it checks against:

| Check | How |
| --- | --- |
| Each call | result (`undefined` and `null` are different values; an absent member and a member set to `undefined` are different too, as structured clone keeps them), error fields, summary step names and counts, journal records, `progress` transitions, callbacks with arguments and answers, observer payloads, stream bytes in place |
| Background work | per process generation: the `ready` method list; observers and observer callbacks (`onChange`, `onMaterialize`) without a cause, as multisets |

| Cross-reading, aged corpus | each implementation reads a ledger the others wrote; the aged-profile corpus is read back, warmed, and mutated (leases cancelled and cleaned, reverts, a new edit, native holds, continuations and a removal) |

| Contention | two product hosts, then the product and each implementation, edit one project at once (both publish, both edits land, every state move under its mover's lock); a holder stopped inside `owner.lock` by the shim and then killed, in both directions: the survivor waits while the holder lives and then reclaims the dead owner's lock; the product's worker thread ended inside `owner.lock` while its host process lives (file 26 §8.1, preload `exit-thread`): the next call through the same host must succeed, leave no lock behind, and leave the ledger as a run on the same identifier seed where the holder's whole process was killed at that point and a new process made the next call (compared as a dual run: disk, Git objects and stamps; both runs' state moves under their mover's lock) |

| A call its host aborted | its result and callbacks compared; its reports, steps, progress and observers (how far it got before the abort landed) reported as notes |
| Order of `verified-objects.v1` lines | compared as a multiset of lines |
| Git index files | compared by entries through Git, not bytes |
| Receipt pages and receipt results, whose order follows `files/<sha256(id)>` key order | compared as written when both runs follow the identifier protocol, else as rows ordered by path |
| Unreachable objects, loose/packed split | compared with the identifier protocol outside concurrent scenarios, else reported; every reachable object and every historical state tree always |
| `drain`'s list of settled background work, `git/info/refs` ids, pack names | whether it settled; ref names only; not compared (pack bytes follow object content) |

### The native ledger interface

A native ledger is driven with `--implementation=native:<path>` (it follows the identifier protocol) or `native-unseeded:<path>` (it does not; list orders that follow random identifiers are then compared by path, and the planted-difference suite shows which checks still hold). It must:

1. Start as `<path>` with no arguments and the arm's environment (`HOME`, XDG folders, `TMPDIR` and Git configuration inside the stage; `PATH` starting with the git shim). Exit when stdin closes.
2. Read one JSON line per host-to-ledger message on stdin, the first `{"type":"init","workerData":{"directory":<storage>,"maintenance"?,"batching"?,"complexity"?,"stallClock"?,"observers":{"onChange":bool,"onMaterialize":bool,"onDiagnostic":bool,"onLockTiming":bool,"onWorkerStall":bool}}}` (a worker thread also gets `lockPort`, a channel beside the seam on which it names its owner-lock tokens so its host can remove a lock it leaves when the thread dies; a ledger process never gets it and is not recorded with it: its locks name its own pid, which the lock protocol recovers when the process dies), then `call {id, method, input, context}`, `abort {id, reason}`, `callback-result {id, failed, value|error}`, `pull {stream}`, `stream-return {stream}`.
3. Write one JSON line per ledger-to-host message on stdout and nothing else: `ready {methods}` first, then `result {id, failed, value|error, steps}`, `report {id, record}`, `progress {id, waiting}`, `observe {observer, payload, cause}`, `callback {id, target:{call, fn}|{observer, cause}, args}`, `chunk {stream, done, value|error}`. Field meanings as in `session-mutation-worker.js`; values as in `session-mutation-wire.js` (function, stream and error markers). `context.deadline` is an absolute wall-clock time in milliseconds.
4. Encode values as `dual-run-codec.mjs` does: `{"$dr":"bytes","base64"}`, `{"$dr":"undefined"}`, `{"$dr":"number","value":"NaN"|"Infinity"|"-Infinity"|"-0"}`, `bigint`, `date`, `map`, `set`, and `escape` for an object that has a `$dr` key. Key order of objects is significant.
5. Move ledger refs with the `git` on its `PATH`, spawned directly by the ledger's own process (not through `sh -c`, whose pid the shim would see instead) as `git --git-dir <root>/git update-ref <ref> <new> [<old>]` or `update-ref -d <ref> [<old>]` (`--git-dir=<root>/git` also works; `GIT_DIR`, `-C` and `update-ref --stdin` are not read), as today's ledger does: the lock oracle, the lock bytes, the ref history, the commit order and the outside crash points observe those moves. A ledger that moves refs without the Git executable shows as making no moves, a difference.
7. Write `owner.lock` exactly as the JavaScript does (file 26 §3b): the bytes above, written to a temporary and linked, removed only by its owner.
6. Persist, return and call back exactly what the JavaScript ledger does (file 26 §4b and §4c): the same records byte for byte, the same summary steps, journal records, observer payloads and callbacks in the same order per call.

#### Identifiers and time

Identifiers. With `LEDGER_DUAL_RUN_IDS=<seed>` in its environment, a ledger draws every random identifier from the protocol instead of its random source (`dual-run-ids.cjs`): the nth draw (from 1) at site *S* during seam call *C* is `sha256("<seed>:<C>:<S>:<n>")` in hex, laid out as `8-4-4-4-12` with the version nibble set to `4` and the variant nibble to `8`. *C* is the `id` of the `call` message whose work draws it (work a call started counts for that call even after its result was sent; anything else is `background`). The harness gives each process generation its own seed (`<seed>:<generation>`). The sites are names, not source positions:

| Site | Names |
| --- | --- |
| `lease` | a lease token (`views/<token>`, `refs/devryan/leases/<token>`, `leases/<sha256(token)>.json`) |
| `document` | a file document ID (`files/<sha256(id)>.json`) |
| `operation` | an operation ID: publications, reconciled outside changes, direct receipts |
| `materialization` | a materialization intent (`materializations/<id>/`) |
| `transaction` | a revert, redo or file-restore transaction ID |
| `hold` | a native admission hold ID |
| `removal` | a native removal intent ID |
| `standby` | a parked or discarded view folder (`view-standby/<id>`) |
| `temporary` | any temporary file name, never left at rest |
| `lock-owner` | the `ownerToken` of a cross-process lock file, never left at rest |

Order within a site. *n* counts the draws of one site in one call, so where a call draws more than once at a site the order is part of the protocol. Measured over every scenario (`LEDGER_DUAL_RUN_ID_CENSUS`):

| Site | Draws per call (max seen) | Reference order | Reaches disk? |
| --- | --- | --- | --- |
| `lease`, `transaction`, `hold`, `removal`, `standby`, `materialization` | 1 | one per call | the value does; no order within the site arises |
| `document` | up to 297 | the order in which the call records paths it has no document for: an observation or warm in the order of its path list, a publication in the order of the lease's changed paths (each loop is sequential in `session-mutations.js`) | **yes**: the ID decides `files/<sha256(id)>`, whose key order numbers reconciled operations (`published.sequence`) and orders lease base lists and receipt rows. Under the protocol a native must draw in this order to compare byte for byte; a correct ledger that draws in another order runs as `native-unseeded:`, where documents are paired by `published.path` and those orders are compared by path |
| `operation` | 2 | one per external change, in the same path order as `document` | **yes**, as for `document` |
| `temporary`, `lock-owner` | 1,776 and 4 | whatever the JavaScript does (eight installs run at once) | **no**: never at rest, each site counts separately, and the lock token is replaced before lock bytes are compared; a different order or number of these draws never fails a run |

The JavaScript ledger is mapped to these names by the source text around each draw (`ID_SITES`), so moving a line or adding a comment keeps the name; a draw no entry names is logged through `LEDGER_DUAL_RUN_ID_LOG`, a protocol difference, and the self-test fails when any `randomUUID(` in the ledger's files has no name.

Time. A ledger reads the system clock; nothing is injected. The harness makes the time comparable instead: it takes its own wall-clock window around every group of calls it issues (from before the first is posted to after the last returns) and lets the clock move on by at least one millisecond between windows, so every stored time falls in exactly one window or gap; a time is compared by that window. A deadline crosses the seam as an absolute time, so a replay posts it the same distance from its own posting time as in the recording.

Optional, JavaScript only: `LEDGER_DUAL_RUN_CRASH` and `LEDGER_DUAL_RUN_AUDIT` (`ledger-preload.cjs`) add crash points at the JavaScript ledger's own file operations and notes on them; a native ledger is crashed from outside by the git shim instead. A crash point either kills the process, ends only the ledger's worker thread (`exit-thread`), throws an uncaught error in it (`throw`), or blocks it (`hold`) for the caller to kill or terminate; `scripts/harness-session-mutation-host.test.mjs` uses it to end the product's worker at each stage of its owner lock.

### Native ledger module tests

Before a native ledger exists, its parts are compared with the JavaScript module by module through test-only probes. The first is the lock and the atomic writes (`scripts/ledger-native/`, run by `node scripts/build-ledger-native.mjs --verify`; [harness runtime](../packages/harness-runtime/DOCUMENTATION.md#native-ledger-io)). The shared specification runs each scenario on both sides through a recording file system and requires equal results, codes, call traces and trees. Processes of both languages contend on one counter and reclaim each other's killed holders. On macOS a test-only interposer (`trace-interpose.c`, built with `cc` into the run's scratch) compares the system calls of `writeFileAtomic`, lock publication, `copyfile` and the sync chain between Electron's Node and the Rust, and fails `fsync` to compare how both fail. Every JavaScript arm runs on the reference runtime, the Node inside Electron (`scripts/ledger-native/reference-runtime.mjs`), or on the Node running the tests where Electron's binary is absent; the run prints which. The lock bytes are held to the same `LOCK_FORMAT` as the harness's lock audit. `scripts/build-ledger-native.test.mjs` runs the specification against the JavaScript alone in the scripts suite.

The object database (`ledger-io::git::odb`) is compared with Git, the oracle, through the test-only `odb-probe` (`scripts/ledger-native/odb-differential.mjs`, in the same verify). Git runs with a private `HOME`, no system or global configuration and no inherited `GIT_*` variables, in the run's scratch. It covers:
- seeded sha1 and sha256 repositories in eight pack layouts (loose, `repack -d`, `repack -a -d`, two packs and loose objects, no `.rev`, a 120-deep delta chain, REF deltas, 64-bit offsets) and three ref styles, compared with `cat-file --batch-all-objects --batch` and `--batch-check`, `cat-file --batch` of every id and `<tree>:<path>` name, `ls-tree -r -l -z` whole and by prefix, and `for-each-ref`, byte for byte;
- every "ask Git" case in its own repository;
- writes: Rust-written objects pass `fsck --strict --full` and are read by Git, by the JavaScript store and by its direct listings, and JavaScript-written objects are read by the Rust; both writers' call sequences, retries and failures are equal;

- a crafted pack whose REF deltas have their base loose or in another pack, which Git reports missing and the Rust must ask Git about;
- corrupted packs, indexes and loose objects (seeded; half the rounds in the gate, all in the extended run; `LEDGER_NATIVE_ODB_FUZZ_SCALE` multiplies them), which must give the right object or "ask Git", never a panic, and stay within a memory bound.

**Codec** (`codec.mjs`). A JSON tree in which objects tagged `"$dr"` carry what JSON loses: `undefined` against `null`, `-0`, NaN and the infinities, bigint, Date, Map and Set in insertion order, sparse-array holes (walked by own keys, so a far index costs nothing), arrays and typed arrays with a subclass or extra members, objects without a prototype, with a constructor-less chain or with a `$dr` key of their own, symbols, own symbol keys, functions (with the port name when the recorder wrapped them), class instances by constructor name, boxed primitives, errors with name, message, cause and an AggregateError's errors (never the stack or JavaScriptCore's line, column and source URL), DOMException with its name, message and code (so `AbortError` and `TimeoutError` differ), AbortSignal with its reason, bytes, ArrayBuffer and DataView, RegExp, URL, URLSearchParams, Headers, and Response and Request by status, URL and headers (never their bodies). A Proxy the recorder did not make is written as opaque and makes the case unrecordable, since its traps would run. An own accessor is written as `{"$dr":"accessor"}` and never called, and it marks the case unrecordable. So does an iterator (anything that inherits `%IteratorPrototype%`: a Map's `values()`, a generator) the engine is handed or gives back unwrapped, flag `iterator`: its position and what it yields are internal, so it would be written as an empty object; one the recorder handed out as engine code is recorded by its own `next()` steps and is not flagged. Identity: a value is taken (`snapshot`) when it is seen and emitted later (`emitSlots`) together with the other slots of its scope, which is one case line; an object reached more than once anywhere in the scope gets `{"$dr":"id","n":k,"value":…}` at its first appearance in each slot (with its content when that slot was taken) and `{"$dr":"ref","n":k}` after that in the same slot, k numbered by first appearance in written order. So "returns its argument" and "returns a copy", and aliasing between arguments, results and states, record differently, and every slot still decodes alone. A recorder wrapper that is no port (an entry's wrapper, engine code handed out, a store's state view) is written as what it wraps and has its identity (package C0e): the test sees a Proxy, the engine its own object, and both are one object of the case. The scope is one family's line of one case: an object two families see in the same case is numbered separately in each family's container, and the two numbers say nothing about each other. Members keep the engine's own order (integer-like keys ascending first), strings are written as `JSON.stringify` writes them (lone surrogates as `\udXXX`), platform state is read through intrinsics captured when the codec loads, and the decoder refuses a tree that is not in canonical form. `decode(encode(v))` re-encodes to the same bytes.

**Naming rule for test code (a hard rule).** The recorder takes a family's entry call as a test's only when its caller is test code, and test code is decided by the file's repository-relative path alone (`port-map.mjs` `isTestPath`): a file named by Bun's test pattern (`name.test.ext`, `name_test.ext`, `name.spec.ext`, `name_spec.ext`), or any file under a `test`, `tests`, `__tests__` or `__mocks__` directory, outside `node_modules`. A test helper must be named so (under a `__tests__` or `test` directory, or `name_test.ext`): a helper named otherwise has its entry calls passed through, and the family command reports it as an unclassified caller, which makes the recording inconclusive until it is renamed.

**Container** (`container.mjs`). One NDJSON file per test file and family, named from the repository-relative test path (`/` as `~`, any other byte outside `[A-Za-z0-9._-]` as `%XX`, so two paths never share a name; a case-insensitive collision is an error, never an overwrite). Format 4 adds slices: a subtree or string of a value whose canonical text is 1,024 bytes or more (`SLICE_MIN`) is stored once as a table entry of its own and replaced by `{"$dr":"slice","hash":"<hash>"}` where it stood (never a whole slot, never the direct value of an `escape` node, whose members are the object's own data), so a large state handed to many calls of one case is stored once plus what changed: inside one case line an unchanged subtree has the same identity numbers, so the same text. The table order is first reference, each value followed by the slices it holds, depth first; the reader checks that, refuses a slice smaller than `SLICE_MIN`, and `resolve` hands out the whole tree, so no comparer or decoder ever sees a slice ("slice" is no codec tag). A header (format, codec version, `recording`: the recorder's semantics version, bumped by hand whenever what a recording says changes; the port-map digest; `modulesDigest`: a digest of the sources of the family's module and its port modules, so a recording of older product code is told apart; the test file and its digest; the family: no tool version, path or time), a value table keyed by the first 16 hex digits of each value's SHA-256, then one line per case in file order. Slots `"=<hash>"` sit only in a case's value parts (entry state, steps, end state, context). The reader is strict: every line must be canonical JSON, every value must match its hash, and the table must hold exactly the referenced values in order of first reference. A case has its id (`<file>:<line> <describe> > <name> #<occurrence>/<family>` from Bun's junit report; `<file> #hooks:<k>/<family>` for what ran after the k-th test and before the next, k = 0 being module load and the first `beforeAll`; `<file> #concurrent:<k>/<family>` for an overlapping test, which is never named by order), its kind, the test's status, the outcome (`recorded`; `unrecordable` with its flags and a reason; `inconclusive` for a failed test), the random seed, entry state and nominal time, the steps, end state and time (taken when the test ends), and the test-originated context. A step is one input (`call`, `new`, `get`, `timer`, `settle` of a port answer, `callback` into the engine, naming the function by identity in `target`) with its nominal `now`, `during: n` and `duringCall: k` when it arrived synchronously inside port call k of step n, `caller` when another family's engine called this entry as its port, and `late: true` when it arrived after the case's test ended; the effects in observed order (`port` with arguments and answer, `new`, `read` and `set` of a port object's data, `timer.set`, `timer.clear` (with the case's own `id`, or, for a timer that is no own timer of the clearing chain, `id: null` and the `handle` itself), `clock` and `draw` with their values, `notify` for a stateful family's store notification with the state and the previous state, `settled` for a promise the engine returned; an effect that arrived after the test ended in a step opened before is marked `late: true`); `returnedAt` (recording 7, package C0e: how many of the step's effects came before its synchronous part, a call, a timer callback or a callback, returned or threw; the rest followed in the jobs it started); for calls the return or thrown value, the arguments after the call and, for draft-mutating entries, the change set (every container path, Map keys included, whose object identity changed); `handedOut: n` when the step handed the test engine code that later steps name `<entry>#<n>`; and for a stateful family `state` (its state after the synchronous part) and `stateChanges` (that part's change set over the state, below its root). A port answer that the engine gets as a port object is recorded as that port (`{"$dr":"port","name":…}`), never walked as data. A stateful family's `entry.state` is taken before its first step in the case and its `end.state` when the test ends. Engine port calls and timers are numbered per family and case; the test's own are `t1`, `t2`, …

**Recorder** (`recorder.mjs`, a `bun test --preload`). Layers, all on by default (`DEVRYAN_CONFORMANCE_LAYERS`):
- *clock*: timers keep real scheduling; `Date.now()`, `new Date()`, `Date()` and `performance.now()` read a nominal time, and each case has a clock of its own (package C0c2), so what a case reads depends only on what the case did. A file's cases are numbered in order (k = 0 for module load, then each test and each hooks case between tests, so test n is case 2n − 1), and case k opens at 1,700,000,000,000 + k × 1,000 ms (`performance.now()` at 1,000 + k × 1,000; `CASE_SPAN_MS`), its own slot, so its start does not depend on how far the case before it got; it opens later only when the case before it closed later than that (time never runs backward within a file, as without the recorder), and while a test's `setSystemTime` stands it opens at the time that test set. Only a timer the case set (its test code, its engine chains or its port code) moves its clock: when it fires, to its nominal due time (its set time on that clock plus its delay), never backward; `performance.now()` moves only with the schedule. Who set a timer is followed through what it sets in motion: engine and port code run in their chain's store; test code runs in a test store of its case, since every test body and every hook the test file registers (through the `bun:test` the recorder re-exports: `test`, `it`, their `.each`, `.skip` and the like, and the four hooks; `describe` bodies run while the file loads) and every test timer's callback runs in one, and a promise job keeps the store it was made in. So a timer that test code sets after its test ended (a timer set from a test timer's callback, a timer set by a promise job the test started, after I/O for instance) is that case's, as is an entry that code calls (a late step of that case) and what it records (that case's context, marked `late`). A timer an earlier case left running, or set after its test ended, moves that case's clock only: an engine timer fires as a late input of its own case, a test timer's firing is context of its own case, marked `late`, and neither changes the time a later case sees, however real time interleaves them (`toy-stray.toy.mjs`, recorded with two waits by the self-test). Code with no store at all has no known case: a test API the recorder could not wrap (a test that does not import from `bun:test`), a job a module started while it loaded, a job of a passed-through call after the call returned. Its timer is taken for the current case, and if it moves that case's clock when it fires, the case is flagged `timer-owner-unknown` (unrecordable), never moved silently (`toy-unowned.toy.mjs`). Engine and port code read the clock of their chain's case, test code that of its test store's case (else the current case's). Before C0c2 the clock was per file, and a timer left by an earlier test shifted a later case's time by load (five cases of `session-actions.test.ts` were unstable in some product recordings, on a quiet machine too). What a test sees differently, stated: time moves forward by 2 × `CASE_SPAN_MS` = 2 s from one test to the next (each test and the hooks case after it have a slot each), where a plain run moves a few milliseconds; so a test that compares a time taken at module load or in a `beforeAll` with one taken in its body sees 1 s, 3 s, 5 s, … for tests 1, 2, 3 (plain: about 0), a time-to-live kept in module state from one test to the next expires sooner, and a test timer set in one test and awaited in the next measures 0 ms (it moved its own case's clock). No test of the product suite does this today (no `beforeAll` in `packages/ui/src`, the abort guard's module state is reset in `beforeEach`); such a test would pass plainly and fail recorded, which parity (`parity.mjs`) reports as a difference naming the test, and the product recording as `plain-differs`. What is still load-dependent, stated: a case's own timer that fires before or after its own test ends moves that case's own end time (and the next case's start only when that end passes the next slot, or while a `setSystemTime` stands); the order of a case's own late effects when its own I/O and its timers race (its context); and code with no known case, which is flagged as above when it moves a clock. Each is a race of the test itself, and a double recording reports it as unstable. A test that polls until its own timer fires (`abort-retry-guard.test.ts`) ends a millisecond earlier or later by load; before the slots, every later case inherited that. `setSystemTime`, `jest.setSystemTime` set the nominal time (and `setSystemTime()` returns to it); under fake timers the fake clock, started at the nominal time, is read, so `advanceTimersByTime` moves `Date.now()` and `performance.now()` as it does without the recorder. A clock stub the test installs (`Date.now = …`, `spyOn(Date, 'now')`, `spyOn(performance, 'now')`) answers, and its answers are recorded.
- *random*: `Math.random`, `crypto.getRandomValues` and `crypto.randomUUID` draw from a stream seeded by the test file and test ordinal (hooks cases by their position), the stream of the case whose code draws; every draw is recorded with its call site, a stub's answer included.
- *globals*: accessor properties on `globalThis` for `fetch`, the four timer functions, `WebSocket`, `EventSource`, `Date`, `performance`, `crypto`, `localStorage`, `sessionStorage`, `document`, `window` and `navigator` (and on `Math`, `crypto` and `performance` for the clock and random functions), so a stub a test assigns is wrapped as it is set. Bun's `spyOn` refuses accessors and installs nothing through a Proxy, so `bun:test` is re-exported (and `jest.spyOn`, `vi.spyOn` patched) with a `spyOn` that lowers the accessor to a data property around the call, spies on the object a recorder Proxy wraps, and re-arms the accessor right after. A test's own definition of one of these globals is never silent: a data property holding something the recorder did not wrap, or an accessor the test defined, hides what the engine does through it, so every case in which such a definition stands is flagged `global-defined:<name>` and is unrecordable. The globals are checked after every `Object.defineProperty`, `Object.defineProperties` and `Reflect.defineProperty` on their holder (observed through a Proxy of the native function) and at every test boundary, before the re-arming (the closing case) and after it (the opening case). A data property is re-armed at the next boundary; an accessor the test defined is never re-armed (its getter is the test's), so every later case is flagged until the test restores the recorder's own accessor. `packages/ui/src/sync/event-pipeline.test.ts` defines `navigator` that way, so its cases will be unrecordable once a family reads `navigator`.
- *mock-module*: `mock.module` is wrapped, so the exports of every module a test mocks are ports: a call that engine code makes inside a chain is a port effect with its arguments and answer, as for any port; last call wins and the factory runs when Bun runs it. A call with no engine chain (the test calling its own stub, or a component it renders calling a mocked store hook on every render) records nothing, neither a context entry nor a copy of its arguments or answer (package C0c2): no family's step holds it, and a replay is given steps only, so a port loses nothing; the outside-chain detector still runs on it, so family code found running there still flags its case. Before C0c2 every such call was copied into the case context: on mounted tests every render's props and store state, which failed 37 of 799 tests outside `sync/` by time-outs and ran one file for 33 minutes at 840 MB.
- *entries*: the families of the port map (`DEVRYAN_CONFORMANCE_PORT_MAP`, format in `port-map.mjs`; a family with `allExports` takes every function export of its module as an entry, found when the module loads, except those it lists under `inline`, each with a reason; ports and entries may carry a `reason`). An entry is a family's input only when the test calls it (the caller rule, an interim device until every engine module is mapped: recording every call engine code makes costs more than the tests can bear). The caller is the first stack frame outside the recorder, and it is test code by the naming rule below, or when it is the test file or a toy test (`*.toy.mjs`). A call from engine code no family maps yet (a product module such as `sync-context.tsx`, a library) is that module's behaviour, recorded with its own family once it is mapped (where the entry is then inlined), so it is passed through, never a step, and counted: per family and export (`unmapped` in the raw), per caller file (`callers`; a family's port such a caller uses, `portCallers`), and in totals (`passed`: calls, those made inside a pass-through call, those with no frame, port uses), which the family command prints, the totals on its last line. A passed-through call runs in a pass-through store, so what it does in turn (another family's entry, a debug flag read, a port it uses) is that module's too, never a flag; but the store holds only while the call runs synchronously: a timer, a promise job or a callback it schedules runs with no store, as test code would. And the caller frame decides on every entry call, inside a pass-through call too, so a test callback that a passed-through call runs, at once or later, is the test's. A proper tail call removes a frame, so a product function that tail-calls an entry for the test counts as the test's call, which is a genuine call either way; Bun's transpiler may turn `const x = f(); return x` into a tail call. A call with no frame with a file at all (an entry handed to `.then`, `queueMicrotask` or a timer, a bound entry a job runs, a test body that only returns the call) may be the test's: it flags its family's line in the case `no-frame` (unrecordable, so the run is inconclusive and the report names the test), unless the census lists that family and export under `noFrame` with a reason that names the engine site that calls it so (today only `sync-context.tsx`'s `.then(unwrapMessageRecordsResult)`); then it is passed through and counted. Residual, stated: for such a listed export, a test that hands the entry itself to `.then`, `queueMicrotask` or a timer is not told apart from the engine site. Engine code an entry handed the test (a closure, a thenable's `then`) is the test's when no frame shows a caller: the runtime runs it for the test (`await thenable`). Residual, stated (C0c review 2, N2): the test may hand such code on to engine code no family maps, and when that code runs it with no frame (`Promise.resolve().then(closure)`, `await thenable` inside it) the call is still recorded as the test's; called directly by that code (a frame) it is passed through. The steps are the family's real inputs in the order they happened; only who caused them is wrong. No cheap rule tells the two apart: both have no frame, and telling them apart would mean following every handed-out object into every unmapped call. A function the test hands an entry, as an argument or an own data member of one other than the draft (a store's state may carry its own actions), that no `injected` item declares a port (and that is no engine code handed back, nor a platform function) is opaque to a replayer: what it answers the engine, and any family call it makes inside the chain, would be lost. It flags the family's line `test-function` (unrecordable, listed by test) until the map declares it a port, whose calls are then effects with their answers. When a file ends the recorder also reports, for every mapped module it loaded, the exports its namespace shows with their kind (`function`, `class`, `data`) and the names its source declares (Bun's scan), so the census reads export lists from the modules themselves. The hook that writes a file's recording has a 10-minute timeout of its own (`WRITE_TIMEOUT_MS`), since writing can outlast a hook's default 5 s; that time is the recorder's, never a test's. A family's module loads through a facade (a Bun plugin) whose entry exports are wrapped and whose port modules' exports are recorded; nothing is imported earlier than the test imports it, so a test's own `mock.module` of a dependency still applies. An export may be one family's entry and other families' port: a call from those families is their port call and the entry family's input. A module port is a port only for the families that list it. Objects handed in (`injected`) and answers that have methods or iterate (an SDK, an async iterator, a Response) become port objects: method calls are effects and data reads are inputs. A port's promise answers are seen as they resolve only when the map says `wrapAnswers` (on `globals.fetch`, on a module port, or on an `injected` item): what they resolve to then becomes a port object too when it has behaviour or a member with behaviour (`{ items: <async iterator> }`), so each item of a stream is a `settle` input of its own; the engine gets a derived promise, one microtask later. Without it the answer's resolved value is recorded as data, and a stream it carries is not seen.

Attribution follows design §2.4: a step is one input with everything the module did because of it, and a continuation belongs to the input whose delivery made it runnable. An `AsyncLocalStorage` store names the chain that runs (family, case, step); an entry call, a port answer settling, an engine timer firing and a callback the engine handed out being invoked each open a step, and every effect goes to the step of the chain it runs in, not to whichever step opened last. An input delivered to an existing chain (the answer to its port call, the firing of its timer, a callback it handed out being invoked later) moves that chain to the new step. An `await` resumes in the store it was registered in, so a promise that another input resolves (a gate a later call opens, a timer one call set that releases another call's waiter) needs more: with a port map, `globalThis.Promise` is a Proxy whose `new Promise` and `Promise.withResolvers` hand out resolve and reject functions that run the real ones inside a release window. Marker jobs are queued just before and after the real resolve, so the jobs between them are exactly the reactions it made runnable; each generation re-queues its markers, so the window follows every job those reactions queue in turn, until 64 generations pass with no engine code (`SILENT_GENERATIONS`). Engine code inside a window belongs to the resolving step, and its chain moves there (only forward). A reaction registered on such a promise after it settled (`then`, which `catch`, `finally` and the adoption of a returned promise call) by a chain older than the release joins the release too. A continuation that test code released (a promise the test resolves and the engine awaits), that port code released (a stub's own timer resolving a promise it handed the engine inside an answer), or that another family's or case's input released, was caused by no input of its family: its case is flagged `released` and is unrecordable. A port answer is a step of its own (`settle`, opened by a reaction registered before the engine's), so a port whose promise the test or the port itself resolves is unaffected. A window ends after 64 silent generations, but it is remembered: a chain of its family and case (or any chain, for a test's or port's release) that then wakes still in a step older than the window's, idle since before the window opened, may be a continuation the window lost (a waiter that awaits 65 more times, or 33 awaited helpers, after its gate opened), so its case is flagged `release-expired` instead of being misplaced. That check is conservative: a chain woken by something no window follows (a native promise, such as a raw `Response` body) after such a window expired is flagged too.

Engine code the test runs is an input of its family. What an entry hands back to the test is wrapped when it holds engine code: a function (an unsubscribe closure) is the entry `<entry>#<n>`, an object with engine methods or getters, an iterator or async iterator (a generator's `next`, `return` and `throw` run its body) and a thenable are wrapped so that each method call (`<entry>#<n>.<member>`) and each read of an engine getter (input kind `get`) opens a step, and whatever those return, and members that hold engine code, are handed out the same way, so `un()`, `for await (const item of entry())` and `await thenable` are recorded as steps. One wrapper per object keeps `toBe` between two handings of the same object; platform methods an engine object inherits are called on the object itself, so brand checks hold; what the test passed in or a port answered is never handed back out as engine code. `returns: "entry-object"` also wraps a result that is plain data, and an async entry's resolved value (through a derived promise, one microtask later). What cannot be wrapped soundly is refused: reading engine code from a non-configurable, non-writable member (a frozen object) flags the case `unwrappable`. Engine code that still runs with no engine chain (a function deep inside returned data, one the engine passed to a test's callback, module load) is flagged, and a flag is never lost: a family the flag concerns gets a line in the case, with no step, if it has none, so the case is written, unrecordable, for that family. Two detectors. Any use of a family's port (a module port, or a member of a port object of particular families) with no chain running is decided by its caller: a frame of a family's own module is that family's engine code, whose line is flagged `outside-chain`; test code flags the port's families that have a line `outside-chain`, and gives each that has none a line flagged `port-no-line`, because JavaScriptCore's proper tail calls remove the frame of `() => port(…)`, so a closure of the family kept from an earlier test looks like the test's own call of the port (the abort guard's own tests, which call it directly, are waived by name in the product census); engine code no family maps (a product module that uses the port as its own dependency, such as session actions clearing the abort guard), or anything inside a pass-through call, is passed through and counted (`portCallers`). Any other effect with no chain running (a timer, a clock read, a draw, a global port) flags the case `outside-chain` when a frame of a family's own module is on the stack, and gives each such family a line; that one is best effort (a tail call or code in a module the family imports leaves no such frame). A case flagged so (`outside-chain`, `unwrappable`, `released`, `release-expired`, `no-frame`, `port-no-line`) that still carries no family's line is a problem of its own (`flagged-without-line`), never dropped. What an engine timer, port answer, callback or resolve does after its test ended is recorded in that test's case, marked `late`, because cases are written only when the file ends; anything that arrives after the file's recording was written is counted as `unplaced` and makes the recording inconclusive. A call with no engine store came from the test and is recorded as context, never compared, unless one of the detectors above finds engine code running (then the case is `outside-chain`); code running inside a port (a test's stub) records nothing of its own. Tests that overlap (`test.concurrent`) are detected when a test starts while another is open: every case current during the overlap, hooks included, is flagged `concurrent` and unrecordable. Output goes to `DEVRYAN_CONFORMANCE_OUT` (a raw file per test file, never overwritten; the record tool names the cases from junit and writes the containers), and recorded paths are relative to `DEVRYAN_CONFORMANCE_BASE` (default: the repository); without an output directory everything runs and nothing is written.

One attribution gap remains, and it is deterministic (it depends on the number of awaits, not on timing): an engine chain that, still in an old step, awaits (`await`, not `then`) a promise another input already resolved (`const g = gate.promise; await null; await g` with the gate opened synchronously in between) resumes in its own step, since a native `await` registers no observable reaction. The continuation more than 64 generations from its release is no longer a silent gap: it is flagged `release-expired`.

**What a replayer must do** (C0d and every later reader of these recordings). Deliver each step's input, then run the engine to quiescence (no runnable job and no due timer left of that step) before delivering the next, and compare each step's effects after its quiescence. Delivering the inputs in their recorded synchronous bursts would reproduce the gap above as a pass; delivered one at a time to quiescence, a module that misattributes it records differently and fails the closure check. Deliver `during` inputs synchronously inside the port call of the step they name, `late` inputs and effects in their own case after its test ended, and handed-out entries (`<entry>#<n>…`, `get` inputs) on the value the named earlier step returned. Treat every case that is not `recorded` as no reference.

What the recorder changes that a test could observe, none of which a sync test depends on (pass-set parity): wrappers are Proxies, so a wrapped function or object is not identical to what was assigned and its `toString` reads as native code, and a stub assigned to a clock or random function reads back as its wrapper, so `expect(Date.now).toHaveBeenCalled()` on the assigned mock would fail (a spy's own handle works); `Object.defineProperty`, `Object.defineProperties` and `Reflect.defineProperty` are Proxies of themselves; with a port map, `globalThis.Promise` is a Proxy (`p.constructor === Promise` is false for every promise, an async function's included; `instanceof` holds) and `Promise.prototype.then` is a Proxy of itself, and release windows queue no-op jobs between the program's own, never reordering them; an absent global such as `window` becomes an accessor that answers `undefined`, so `'window' in globalThis` is true; a promise the recorder observes (a port answer or an entry's result) gets a reaction, so a rejection the engine leaves unhandled no longer surfaces (the plain run of a product recording catches a test that depends on it); a port listed with `wrapAnswers`, and an async `entry-object` entry, answer through a derived promise, one microtask later; engine code handed to the test is a Proxy, so a test that compares it with a reference it got another way (not through an entry) sees a different object; with a port map, an effect of test code with no engine chain captures a stack, and every resolve by test or port code opens a window (at least 130 no-op jobs); busy work timed with `performance.now()` reads 0 ms; with the clock, time jumps 2 s between tests (see the clock layer); with the globals layer, a function a test file registers (a test body, a hook) is a wrapper of the same name and declared length that runs it in a test store, so its `toString` differs; a mocked module's stub that the test calls itself runs as test code, so a timer it sets is numbered among the test's own (`t1`, …), not left uncounted as port code; and a trap that answers the same number for two timers makes a later clear of that number ambiguous (recorded as such).

**Replayer** (package C0d: `replay.mjs`, `replay-compare.mjs`, `engine.mjs`, `engine-ts.mjs`, `manifest.mjs`, `children.mjs`, `replay-product.mjs`, `replay-mutants.mjs`, `toy/replay/`). It replays recorded cases against the TypeScript modules themselves and requires an exact reproduction, so that a difference can only be an input the recording does not hold (a recorder gap), a replayer bug or real non-determinism, never a difference of two engines. What it proves: for the families it replays, a recorded case holds every input its module needs (arguments, port answers, clock values and draws), so a case can be run without the test that made it; and the harness is honest, because planted differences in the modules, in the comparison and in the replayer are each caught where they must be. What it does not prove: anything beyond the recorded cases (a path no test reaches is not judged; the coverage gaps of the planted differences show some), that the TypeScript is right, or that the recording is of the sources replayed (it does not recompute the containers' `modulesDigest`; it refuses a container recorded with another port map, by its digest). A directory it replays must be what its recording's manifest lists (`manifest.mjs`, `recording-manifest.json`, written by the family command beside the containers): every family the recording was asked for, each container with its family, SHA-256 digest, size and cases by outcome; a container missing, one not listed, one whose bytes changed (a count changed, a case re-marked unrecordable, a line cut) or no manifest at all makes the run inconclusive. The manifest guards against loss and damage, not against someone who edits it too. Every case is replayed twice. *In file order*: the cases of one container, in order, on one fresh module instance, the way the tests ran them; a case that is not judged (unrecordable, say) is still delivered when all its steps are calls, so the module's history is the test file's. *Alone*: each judged case on a fresh module instance of its own. A unit (one fresh module instance) is a Bun Worker, so every module-level Map, counter or memo starts as the module's own load leaves it and dies with the unit; hidden module state that no export snapshots is reproduced in file order only, which the replayer's toy family has a fixture for (`REPLAYER_FIXTURES`: a counter, different alone, reproduced in file order). Within a case each step's input is delivered, the engine runs to quiescence (two rounds of the event loop with no engine activity, at most 10,000, beyond which the case halts and is inconclusive), and only then is the next delivered. What a case makes or throws while none of its steps is open is a difference of that case (`outside`): the engine keeps the case that scheduled each `setImmediate` and `queueMicrotask` job, so an error a later job throws, or a rejection left unhandled, is charged to it and the unit's worker lives on (the rest of its cases are still judged); `end` waits (bounded) for the case's own jobs; what the unit notes between two cases is charged to the case before. What a unit notes while its module loads is only reported (no case was open). The engine is a process behind a versioned protocol (`engine.mjs`, protocol 3: open a unit, open a case, seed a stateful family's state, deliver a step with its inputs (a call, `new` or `get`, a timer firing, a port's promise settling, a callback the test calls, and inputs nested in a port call), end the case and read back its steps and states; `replay.mjs --engine=<file>` runs another engine), so a Rust runner can take the TypeScript engine's place. The engine is told nothing that names or locates a case (no case id, test, container or path, no step number) and none of the recorded outputs; the replayer keeps the mapping to the recorded case. What that proves and does not: an engine that echoes what it is sent, that answers a step with another step's recording, or that looks a case up by anything the protocol carries fails the closure (the self-test runs three such engines, `toy/replay/fake-engine.mjs`, each exit 1); nothing is proved against an engine that reads the fixture files itself and matches a case by the content of its inputs, which only not handing it the files, or reading its source, stops. `engine.mjs` also lists what protocol 3 must add for the store, time-driven and transport families (entry state, timer firings and other input kinds, promises, async iterables and port objects as answers, `new`, `read`, `set` effects). `ENGINE_ACCIDENTS` there lists what in the recordings is an accident of JavaScript that a Rust engine should not have to imitate, with what its runner should do instead (clock reads as effects, draw sources as types, module port names as file paths, function names in values, identity numbers, the binding of engine-made objects, messages the JavaScript engine writes itself, lone surrogates in JSON text). The TypeScript engine (`engine-ts.mjs`) runs under the test isolation guard as `bun --preload` of the isolation preload, with the working directory where Bun resolves the modules' path aliases (`packages/ui` for the product). In each unit a Bun loader plugin replaces every port module of the family with one that re-exports the real module and answers the listed exports from the recording, and loads a planted copy's source in place of a module (the file is never written); the clock and the random sources answer from the step's recorded effects in order; the four timer functions record `timer.set` and `timer.clear` and never run a callback; `fetch`, `WebSocket` and `EventSource` have no recorded answer. A port call, clock read or draw is served the step's next recorded answer of its kind and name (a port the map waives as unordered by name, in any order); anything else halts the case, `effect-order` when what was asked is later in the step, `unanswered` when it is not there; a halt is never answered with a made-up value. Inputs are rebuilt with identity preserved: the recording's identity numbers are one scope per case, so an object the case already holds (one an earlier step was handed, or one the engine made and the recording names again, bound at the output slot where it first appears) is that very object, brought in place to the content the input gives it (what the test changed between two calls), and an object new to the case is made once and bound; a function at a position the map declares injected is that port, any other function the test handed in has no recorded answer. Comparison (`replay-compare.mjs`), with the rules of design §4.2 and no others: per step, the input as the engine saw it (a broken rebuild shows here), the effects as an ordered list (kinds and names first, then each one's members, arguments and answers), the return or thrown value, the arguments after the call and the change set (the recorder's own rule, recomputed), all as codec trees compared exactly (key order, `undefined` against `null`, `-0`, NaN, Set and Map order, holes); identity as structure: the recording's numbers and the engine's are paired position by position across the case, and an identity difference is reported where the pairing first breaks. The comparison itself is pinned by vectors: pairs of codec values that differ in one thing only (`-0`, NaN, the infinities, Map and Set order, a hole against `undefined`, identity across steps, a member's presence, an error's class, message, member or cause, a typed array's type, a lone surrogate), each reported by its own check and kind (design §4.5 item 18). **Exit codes**, for `record.mjs` and `parity.mjs` (design §4.8): 0 only for a complete run with nothing wrong or explicitly allowed; 1 when a test's outcome (or, for parity, its assertion count or a printed line) differs between the plain and the recorded run, named; 2 when the run is inconclusive: a named file that built no scheduler (`no-construction`), a run in which no case recorded one (`empty`), a case that is unrecordable or comes from a failing test, a case whose trace differs between two recordings (unstable, named, with the first differing field), a recorder error (a refused hidden read, a `Date.now()` spin), another number of tests than junit lists, a file without a recording, a recording that cannot be read or another raw version wrote (`unreadable-raw`), provenance that does not hold, an allowance that names no such case (`allowance-unused`); 64 for a usage error, and then nothing is written. **Allowances**: `--allow-inconclusive=<file>` names cases, each with its reason, in a JSON list of `{ "case": "<case id>", "reason": "<why>" }` (the case id as the run prints it; a reason is required); an unrecordable, failed or unstable case it names is printed `(allowed)` with the reason and does not count against the exit. It never covers a file-level problem or a recorder error. The last line counts the case outcomes (recorded, unrecordable, inconclusive, empty: a test that built no scheduler), the allowed cases, the cases with a note and every problem.

**Interception.** The recorder (`recorder.mjs`, a `bun test --preload`) registers a Bun plugin that serves `scheduler.js` as a facade: every export is re-exported from the real module (loaded under a query) unchanged, except the factory, which is wrapped. The relative `./scheduler.js` import of the scheduler tests, the `./index.js` re-export and the package-name import through a workspace link (Bun resolves it to the real path) all reach the facade; `ManagedOrchestrationError` keeps its identity. The target is a spec file, `scripts/scheduler-conformance/target.json` (`DEVRYAN_SCHEDULER_CONFORMANCE_TARGET` names another, as the self-test does for the toy's).

**What a construction records** (`trace.mjs` has the event table). Every construction has one trace, one total order (`seq`), and `at` orders the events of all constructions of one case. Inputs the scheduler arrives at: `call` (a public member, call 0 the construction: its arguments hold the options as they were then, its return the members, as a port), `control` (a method of the task control object the scheduler handed an executor call), `callback` (another function it handed a port, such as `onProgress`), `fire` (a timer it set), `abort` (an AbortSignal that reached it). Inputs it asked for: `answer` (a port call's return, throw or promise, then its resolve or reject), `read`, `clock`, `draw` and `env`. Only in the driver's recordings: `step` (an input group begins: its number, its virtual time, and its inputs as structured data in delivery order, each with its kind, label, construction and the recorder's own numbers: the call number of a call, control or fire, the port of an answer with its outcome and whether the driver or the scenario settled it, the timer, the signal; the events they cause need not follow in that order, so a replayer delivers from the marker). A driver's `timer.clear` of `null` is a `cancelTimeout` of a handle the scheduler never set, not an error. Outputs: `port` (a call to an option, a method of an object option, or a callback the caller passed a member, named like `submit#3.arg1.authorize`; the save port also carries the SHA-256 of the saved state as the package's ledger encoder writes it), `abort` (an AbortSignal the scheduler handed out aborted, with its reason), `timer.set` and `timer.clear` (timers numbered per construction; a clear through a primitive handle that several live timers share lists them as `ambiguous`), `return`, `throw` and `settle` (the settlement of a promise the scheduler returned, recorded by a reaction registered before the caller's). An input that arrives while a port call is still on the stack carries `during`, an event after its test ended `late`. Every input that arrived on its own carries `place`, where the recorder could show it arrived (below); an `answer` of `promise` carries `settled` when the promise was already settled when the port returned; a `timer.set` carries `handle`, `object` or `primitive`, what `scheduleTimeout` returned (a primitive handle is forgotten when its timer fires, so a later clear through it is `null`). AbortSignals in any value are numbered per construction, and the event that carried one names its number and its member path at any depth (`signals`). An abort is written before the signal dispatches when a controller aborts it (the recorder wraps `AbortController.prototype.abort` for the signals it watches, and passes the platform's own `AbortError` when no reason is given), so what any listener does, the scheduler's own on a signal it made included, follows the abort that caused it; a signal no controller aborts (`AbortSignal.timeout`, `AbortSignal.any`) is written when it dispatches. Only functions and objects holding functions are wrapped (platform objects never); data, tasks, signals and errors are handed on as they are, so a test that compares them by identity sees what it would without the recorder, and an object holding functions that crosses twice is one proxy both times. A promise a member returns is the exception, below. Values go through the client harness's codec, one identity scope per case.

**What the recorder changes that a test can observe** (pass-set parity on the 21 files and on the whole package shows no test outcome, assertion count or printed line changed). A promise a member (or a function the scheduler handed a port, or a timer callback) returns is not the scheduler's own: the caller gets a promise of the recorder's, one per promise of the scheduler's (two calls the scheduler answers with one promise, a memoised `shutdown()`, get one promise, so `s.shutdown() === s.shutdown()` holds as without the recorder), settled by the recorder's reaction to the scheduler's, so it settles one microtask later than the scheduler's own and behind every job already queued when the scheduler's settled (the rest rule, `settle`); a promise the test passed in and a member hands back is not the test's own object (`s.echo(p) !== p`). The globals `setTimeout`, `setInterval`, `setImmediate`, `Bun.sleep` and `MessagePort.prototype.postMessage` are wrappers that keep the original's own properties (`name`, `length`, and util.promisify's custom function, the same function, so `promisify(setTimeout)` works and is `timers/promises`' `setTimeout`), so `setTimeout === require('node:timers').setTimeout` is false; a timer callback the test passes is called through a wrapper (`this` and the arguments unchanged). bun:test's `jest.useFakeTimers`, `jest.useRealTimers`, `vi.useFakeTimers` and `vi.useRealTimers` are wrappers of the same name and length. An unhandled rejection's printed stack can differ by one frame text (`at <anonymous> (file)` plainly, `at file` recorded: seen by the third review, not in the third fix round's rerun of its probe); only a failing test prints it. `process.env` is a Proxy (Hidden inputs) and the nominal clock changes `Date` (Nominal clock).

**Where each input arrived (the rest rule).** A replay must deliver every input where it arrived relative to the scheduler's own queued work; the recorder writes what it can show about that, at the input, and a replay uses nothing else. Each arrived input (a call, control, callback, fire, abort, a step marker, a port answer's resolve or reject) gets the first `place` of these that holds. `during`: a port call of its construction was on the stack (the test's port code called it); a settlement written then is `busy` instead, since a reaction wrote it, so microtasks ran inside the port (Bun's `expect().rejects` does). `group`: the driver's latest step marker lists it. `return`: the settlement of a promise a port returned already settled (`settled`, read with `Bun.peek.status`, which runs no job): the recorder's reaction, registered first, was queued at the return. `with` and `after`: it arrived in the same synchronous run as that call's return or throw, nothing written between: the event before it is that return; the microtask the recorder queued at that return has not run; and the caller's async context holds the stamp (an `AsyncLocalStorage` store, a new object per call) the recorder entered right where it queued that microtask, which only the job that made the return can hold before that microtask runs (any other job carrying the stamp was queued after it). `settle` and `after`: it arrived in a reaction job that this call's settlement itself queued, with nothing written since that settlement. The caller never holds the scheduler's promise: the member wrapper hands it a promise of the recorder's own, settled only by the recorder's reaction to the scheduler's (registered first, at the return). That reaction writes the `settle` event, queues an opener microtask, settles the caller's promise (which queues exactly the reactions registered on it so far, and nothing else) and queues a closer microtask. The microtask queue runs in order, so the jobs between opener and closer are exactly those reactions: a job queued before the reaction ran (a chain of awaits beside the kept promise, however long) runs before the opener, a job queued later (an await after the continuation, the `.then` of a `.then`, the continuation of a function that awaited the call, the continuation after `Promise.all`) after the closer. The input is `settle` when that call's window is open, it is of the same case and no event was written since that `settle`; one microtask later it is not. The cost: a test's continuation after a member's settlement runs behind the jobs already queued then and the opener, one job later than without the recorder (parity on the 21 files holds). `rest`: the scheduler had come to rest. A rest point is a moment the microtask queue is empty: the recorder's own `setImmediate`, queued after any event (one at a time), and the entry of a timer callback, of a timer it set over the real `setTimeout` or of a real `setTimeout` or `setInterval` of the test's own (the recorder wraps the two globals; without that, whether its probe ran before a test's timer, or a real timer of the scheduler's fired just before it in the same timer phase, decided between `rest` and `busy`, so a mark depended on load) (Bun runs the microtask queue to the end between any two timer or immediate callbacks); at such a point every job the scheduler could run has run. Each is a rest point only when the event loop itself entered the callback, which the recorder checks at the entry: the callback's frame is the only one below the check (a fake clock's `advanceTimersByTime` or `runAllTimers` calls timer callbacks from the test's own code with microtasks still queued, and is a frame below it), and, for a timer, the test runner's fake timers are off (the recorder wraps bun:test's `useFakeTimers` and `useRealTimers` on `jest` and `vi` and also asks `jest.isFakeTimers()`; while they are installed no timer entry is a rest point, a real timer's included, and the case carries the note `fake-timers`). Under fake timers Bun fakes the native timers, the recorder's own among them (a scheduler timer the recorder set fires inside the fake clock's advance), and leaves `setImmediate` real, so the recorder's probe is still a rest point. `setSystemTime` alone installs no fake timers. Under the recorder a test cannot reach a timer's callback otherwise (Bun's `_onTimeout` holds an async-context frame then, not a function), so today the fake clock is the only caller the frame check meets; it is kept for any other. Both kinds of rest point rest on the scheduler queuing no macrotask of its own: the recorder watches `setTimeout`, `setInterval`, `setImmediate`, `Bun.sleep` and a `MessagePort`'s `postMessage`, and when a frame of the target's module closure calls one directly (the first frame below the recorder's own, or the recorder line that called product code in tail position; never through an option such as the `scheduleTimeout` the recorder always supplies), its case carries the note `own-macrotask` and gives no `rest` mark from then on (`queueMicrotask` and `process.nextTick` queue jobs Bun runs to the end before any timer or immediate callback, so they pass no rest point and are not watched). Today's scheduler calls none of them: its only reference is the `scheduleTimeout` fallback to `globalThis.setTimeout`, which the target spec lists as unreached, and no case of the corpus carries the note. The hidden-input scan also matches these names and imports of `node:timers` and `timers/promises`, which the run-time watch cannot see. The input is at rest when its case wrote no event since the latest rest point (step markers left out) and no promise its schedulers may await changed state silently since: every promise a port of the case returned pending whose settlement is not recorded yet, and every promise met in a value that went in, has the state it had then (the promise this input settles aside). The rule is per case because the schedulers of other cases share nothing with it (the scheduler's modules hold no mutable state; a test's own shared objects reach a scheduler only through recorded inputs and promises, which are watched). `busy`: none of these shown; the scheduler may have had work queued. Doubt is `busy`, never the reverse. What it costs: one `setImmediate` at a time, a promise and two microtasks per settlement, one microtask per member return, one `Bun.peek.status` per promise answer; parity on the 21 files shows no test outcome, assertion count or printed line changed. What it cannot show, so marks `busy`: an input after the caller awaited something other than the member's own promise (a helper `async` function that awaits `initialize()` and returns: its caller's next call), after `Promise.all` of members, a microtask or more after a settlement, after another settlement was written in between, or after a test's port promise settled in the same run. `return` is given only for a native promise (a subclass's `await` takes jobs of its own). What each placed mark rests on: `during`, the recorder's own stack of port calls (the input's wrapper runs while a port's test code is on it); `group`, the driver's step marker, which lists the group before delivering it in one macrotask; `return`, `Bun.peek.status` of the port's native promise at the return, so the recorder's reaction, registered first, is queued at the return; `with`, the event before the input is that call's return, the return's microtask has not run and the caller's store is the stamp entered at that return, which no job queued before it can carry; `settle`, the open window above; `rest`, a rest point (queue empty) after the case's last event, with every silently awaitable promise of the case unchanged since. `shapes.toy.mjs` and the toy case `a settlement's window holds only the reactions it queued` pin each awaiting shape's mark (the second review's sweep among them: a call made 1, 2, 3 or 19 microtasks after a kept promise is `busy`, only 0 is placed).

**The options object.** The scheduler gets a forwarding proxy over the test's own options object, so a member the test sets later is what the scheduler reads then (it reads several lazily: `onMutationTiming`, `expireUnacknowledged`, the hooks). Every member it reads is a `read` input, and so are `in`, listing the keys and an own-member check (`hasOwnProperty`, a descriptor, a spread), here and on every other object holding functions (`op: has`, `op: keys`, `op: own` with `found` and the data member's value); a getter runs once per read, as without the recorder.

**Options the test leaves out** (missing, or set to `null`: the scheduler falls back with `??`, which treats both alike). The recorder supplies `now` (the nominal clock), `scheduleTimeout` and `cancelTimeout` (over the real timers), the three identifier factories (the scheduler's own format, prefix and a dashless UUID, served), a recorded no-op `publishEvent`, a recorded `console` logger and the scheduler's own default persistence (`load` answers null, `save` does nothing, both async), as a port, so every save is in every trace: each behaves as the scheduler's default, a read of it is marked `supplied`, and the construction's `defaulted` list names them. The target spec anchors the scheduler's `createDefaultPersistence` source text (several lines, exactly once), so a change to that default fails the spec and the recorder loudly instead of drifting. A test that passes its own persistence records exactly what it did before (checked on the 21 files: every such case byte-equal).

**Hidden inputs** (design §3.1). `crypto.randomUUID`, `performance.now` and the target's environment variables are recorded only when the code that reads them is a product module of the scheduler (the target's static import closure) and a construction's chain is running; then the UUID is served (SHA-256 of the case, the construction, the site and the draw's number, laid out as a version 4 UUID, recomputable in any language), performance reads the nominal clock and the variable's real value is recorded. Each read is named by a site of the target spec, found by a one-line text anchor that must occur exactly once in its module, never by a source position: JavaScriptCore gives async arrow functions no name in a stack, so the spec's anchors map the reading line to the enclosing function (`persistLocked`, `cancelSingleTask`, `runExclusive.held`); a default parameter of a public member has no frame of its own and is named by the member (`recordOperatorStop`). These are recorder errors, and the value used is then the real one: a read in product code at a line no site names; a read whose product frame a proper tail call removed (the first frame below the recorder's own is the recorder delivering a scheduler input); a read by product code with no construction's chain running (an event listener runs without the chain's store), whichever case is running when it fires: a test, a test that built no scheduler, the hooks, or after the recording was written (such an error is kept in the `.unplaced.json` beside the recording). The one exemption is by function, not by case: the spec's `direct` list names product helpers that tests call themselves, each by an anchor that must occur exactly once (`createManagedRecoveryMessageId` in `transport-recovery.js`); a read on such a line is no scheduler input when the code that called the helper is no product module, and still an error when a product listener called it. What stays unseen: a product read in tail position inside a listener, which leaves no product frame (Bun's transpiler also folds `const id = read(); return id;` into such a tail call). The spec also lists, with a reason, each hidden-input line the recorder never reaches (the `Date.now` default of `now`, the fallback of a missing `randomUUID`) and each accepted one (the `localeCompare` sorts, at the C locale every run uses), and the self-test fails when a line of the closure that matches the hidden-input scan is in none of the lists. The scan is a text match (clocks, random sources, `process.env`, `Bun.env`, an `env` destructured from `process`, `globalThis[...]`, `Intl`, locale methods, imports of `crypto`, `os`, `process` and `perf_hooks`, and the macrotask names of the rest rule: `setTimeout`, `setInterval`, `setImmediate`, `MessageChannel`, `postMessage`, `Bun.sleep`, `node:timers`, `timers/promises`); it cannot see a name reached through a computed member or bound by an import it does not list. `process.env` is a Proxy while the recorder runs (Bun refuses an accessor on it), and `util.types.isProxy(process.env)` is then true.

**Nominal clock** (`DEVRYAN_SCHEDULER_CONFORMANCE_CLOCK=nominal`, the default; `real` turns it off). Each case starts at 1,700,000,000,000 ms. A scheduler built without `now` reads it, and so do `Date.now()`, `new Date()` and `Date()` anywhere in the test file (`Date` is then a Proxy over the real constructor whose instances are real Dates), so values a test computes from the clock agree with the scheduler's. Timers keep real scheduling; when a timer the recorder set over the real `setTimeout` fires, its case's time moves to that timer's virtual due time (never backward). A test that injects its own timers drives them, and moves no time. Limits: time never moves while a test only reads it, so a synchronous loop waiting on `Date.now()` for real time to pass fails: the same nominal time read 1,000,000 times in a row with nothing recorded between throws and is a recorder error (a rule that depends only on what the test did); a loop that awaits real sleeps between reads ends by the test's own timeout. Two recorder timers whose real firing order flips under load give the case other clock values, which stability reports (exit 2). `performance.now()` in test code stays real.

**Cases, late effects and unrecordable cases.** One test is one case, paired with Bun's junit report by order; what runs outside a test is a hooks case numbered by the tests before it, written only when it built a scheduler. A construction belongs to the case that was running when it was built, and everything it does or receives later stays there, marked `late`, never in the next test's case. Cases are written when the file ends (the recorder's `afterAll`, which runs after the file's own, with its own timeout since writing a large ledger's every save takes long); an event after that is counted in a `<stem>.unplaced.json` beside the recording and its case becomes unrecordable (`late-after-write`). Other flags that make a case unrecordable: a function the recorder did not wrap met in any recorded value (in a port's answer, nested in an argument, in a value read; `unwrapped-function`, or `handed-code` in what a public member returns: the test could run scheduler code with no input recorded), an object that crossed the boundary whose content differs when its case ends (`mutated-after-crossing`; the recorder cannot tell which side changed it) when the value went in to the scheduler, or went out and one of its objects crossed the boundary again in the case (the scheduler may still hold it), overlapping tests (`concurrent`), an accessor or foreign Proxy in a value (as in the codec). The event that held such a value lists the field under `unwrapped` or `mutated`. A value that went out and whose objects never crossed again, changed later, is what the scheduler handed over at that moment: the case keeps its outcome with the note `mutated-by-receiver` (the event lists the field under `mutatedByReceiver`, the case line under `notes`, and the run prints it as `info`). On the 21 scheduler files three cases carry that note, each changed by the test side: one sets a member of a snapshot the scheduler returned, and in two Bun's `toMatchObject` with `expect.stringContaining` writes the matcher into the received task.

**Containers.** One NDJSON file per test file, named from its repository-relative path as in the client harness: a header with the format, codec and recording versions and, for provenance, the recorder's digest (its own files and the shared codec and container modules), the SHA-256 of every product module of the target's import closure, the target, the clock mode and the Bun version; then the value table in order of first reference; then one line per case (its outcome, `flags` and `notes`, `events`, the recorder's own count of the events it wrote, and its constructions); then an end line with the number of case lines and of events. The reader is strict (canonical lines, the recording version it reads, hashes that match, exactly the referenced values, each case holding the events it counts, an end line whose counts hold): a lost case line, a case cut short and a cut file are refused, and the builder reports a raw case whose count is not what it holds (`event-count`). `checkProvenance` (in `trace.mjs`) recomputes the recorder and module digests from the files on disk and requires equality; every recording is checked when its containers are built. The raw reader refuses another raw version and names an unreadable file. Stability compares two recordings case line by case line, which, holding content hashes, is a byte comparison.

**Pass-set parity** uses the client harness's `judgeParity` and `outputLines`, and writes as `#` every run of hex digits holding a decimal digit when it learns what varies between the plain runs, because the scheduler prints random identifiers in its stall warnings. A line both plain runs print the same is never left out.

**Scripted driver and scenarios** (package O0b). `driver.mjs` builds a real scheduler (the factory is handed in) whose every port is the harness's and drives it under full virtual time. The clock is a number the driver moves; timers are the driver's and fire only when it advances past their due time (set time plus the delay as Node and Bun clamp it; a fractional delay is refused), earliest due first and then in set order, each fire its own step, and every timer due at one instant fires before any port is answered (one timers phase, only microtasks between its callbacks). Every asynchronous port call (executor, persistence, the hooks, a callback a scenario hands a member) returns a deferred settled by its policy: `hold` (the scenario settles it), `auto` (the driver answers it after quiescence and after the instant's timers, oldest call first, each answer its own step) or `never`; synchronous ports (`publishEvent`, `logger.warn`, the diagnostics hooks, `getLastRecoverableResult`, `resolveExecutionBackend`) answer at once. This models every port as answering in a later macrotask, one at a time: a hook that is effectively synchronous in production is a full step here, and no order with a port answering in the middle of a drain is produced. Identifiers come from the harness per named site, as the recorder serves them; under the recorder the hidden draws are the recorder's. Inputs are delivered in groups (member calls, control calls, port answers, a fire, an abort, all in one macrotask with no microtask between them: how simultaneous calls are modelled); each group drains to one `setImmediate` boundary, then two more boundaries must show no activity at any port, timer, clock, draw or member settlement, and nobody may have set a real timer, interval or immediate through the globals. What is guaranteed is narrower than "nothing else can run": every driver macrotask runs the microtasks it causes to the end itself (`drainMicrotasks` of `bun:jsc`, so the driver runs under Bun only) and is marked as the driver's while it does, so activity outside the driver's macrotasks or between two steps came from a macrotask the driver did not start (host I/O, a timer captured before the driver's guard was installed, a message) and is refused (`stray-activity`), whether it lands between steps, inside a later step's drain or after the scenario (an answer whose value is a promise must have settled by the end, and a final confirmation of sixteen boundaries and two real timer turns must show nothing). Not seen: a foreign macrotask that does nothing visible at those places, and one that fires after the final confirmation and settles nothing the driver answered (a recording marks what it does as late). When a check fails the driver stops with its name. Under the recorder every group begins with a `step` event. Named checks guard the driver itself: `settle-order`, `timer-time`, `input-before-drain`, `group-atomic`, `quiescence-confirmed`, `real-timer`, `stray-activity`, `unknown-port`, `dead-instance`, `crash-not-reached`; `driver-mutants.mjs` plants eight bugs in a copy of the driver (a deferred settled newest first, a timer fired late and one early, port answers between two timers of one instant, a step that does not wait for its drain, a group split by a boundary and one by a microtask, a drain that reports quiescence after one microtask), each reported by its own check, beside an unchanged copy that passes; the quiescence probe's negative controls pin `stray-activity`, `real-timer` and `quiescence-confirmed`, and it counts every drain's turns (one boundary; sixteen boundaries and two timer turns for the paranoid drain).

`scenarios.mjs` holds the scenarios, each with the purpose it states: the design's F1 to F11 (F1 at 1, 8 and 64 recorded, at 512 and 2,500 by the driver alone because a recording holds every saved state; the same prompt eight times with and without `allowDuplicate`; 64 roots; running tasks then more submits; failures and submits in one group; a held save; a failing admission save; restart with 10 active and 20 queued tasks; `withRuntimeRestart` on its success path and, as the design has it, with 5 deferred launches replayed in insertion order when the restart's reconcile is not terminal; prerequisites; auto-resume with a host that answers each attempt at once and one that answers late; handoff) and the ordinary lifecycle (submit to collect, a later duplicate, cancels with and without an abort answer, two cancels together, waits with a timeout and a signal, a retry acknowledgement, removal, run cleanup, native segments, an operator stop) and what the O0d review found no scenario reached (a restart with several active tasks of mixed reconcile answers and every crash point, `restart-mixed`; the second run-cleanup retry, `run-cleanup-backoff`; two queued tasks whose queue order only `createdAt` decides, `queue-order-ties`, loaded from a ledger; a shutdown with a task deadline and an admission retry armed, `shutdown-with-timers`). They record what the scheduler does today. Each states its facts, read from the scheduler (its comments name the lines) and checked exactly by `scenario-facts.mjs`: the steps and the virtual time of each, the inputs of every group in delivery order, the steps each port was called and answered in, the launches in order with the saves before each, every timer with its delay, set and fire time, how every member call ended, the final status of every task and, after a crash, which save the fresh instance loads. A scenario that states no facts fails, and a fact changes only by review. Crash points (design §4.5): a scenario that asks for them is also run stopped at each of its saves, `durable` (the write landed and the process died before the promise resolved: a fresh instance loads those bytes, encoded by the package's ledger encoder) and `torn` (the write never landed: it loads the save before, or nothing at the first save), and the fresh instance initializes and runs a minute of virtual time; each states which save it loads. `scenarios.corpus.mjs` is the corpus as a bun test file, one test per scenario and crash point, each failing when its facts differ from what it states (`DEVRYAN_SCHEDULER_SCENARIOS` keeps a comma list of test names, `DEVRYAN_SCHEDULER_DRIVER_DRAIN` picks the drain). `drive.mjs` exits 0 only when every case ran plainly and recorded, parity holds, every case is byte-equal across the recordings and between the one-boundary and the paranoid drain (a case that differs is printed with its first differing event), and every case's trace matches its stated facts with step markers that list exactly the inputs of their step; 1 when a scenario fails (a driver check or a stated fact), a trace's facts or markers differ, parity differs or a large run fails; 2 when a case is unrecordable, unstable or drain-dependent, or a large run is unstable; 64 for a usage error. It pins `DEVRYAN_ORCHESTRATION_UNACKNOWLEDGED_EXPIRY=1`, which the scheduler reads on every save. Every in-process run of the driver is a bun process: under heavy load Node's `setImmediate` turn takes about a millisecond, Bun's microseconds.

**Replayer and closure check** (package O0c). `replay.mjs` feeds a recorded case's inputs to a candidate and requires the candidate to produce the recorded trace exactly, in the recorded total order: every output (port calls with their arguments, timer sets and clears with their handle kind, returns, throws, settlements, the aborts it issues, saves with their ledger digests) and every input it asks for (option reads, clock values, identifiers and hidden draws by named site, environment reads, port answers), event for event and value for value. The candidate is a second copy of the scheduler package: `prepareCopy` copies the package's production modules and the rest of the scheduler's import closure into the run root at their repository-relative paths, and `loadCopy` imports it from there, a separate module graph whose closure must stay inside the copy and whose module digests must equal the recording's header (`copyProvenance`). The candidate sits behind a narrow interface (`candidate.mjs`, what a Rust core will later sit behind): inputs in (`deliver`: a construction, a member call, a control or callback call, a timer fire, a port answer's settlement, an abort; values live, decoded by the host), ordered effects out (`host.output`), and the inputs it asks for answered from the trace (`host.ask`, `host.portAnswer`, which also delivers the inputs the recording places inside a port call and says whether the promise is already settled, `host.timerHandle`). The JavaScript adapter mirrors the recorder's boundary code with the test's side replaced by the host. Values are decoded with the shared codec by a decoder that keeps identity across the case's events (an object the recording numbers is one live object), makes the stand-ins the trace names (a port, an option's clock, timers and identifier factories) by where they are, places the host's own signals where the recording lists them, and gives an error of a class the copy exports the copy's prototype. Every arrived input is delivered where its recorded `place` says, never by a search: `rest` when every event before it has been produced and the candidate is quiescent (a drain ends after two `setImmediate` boundaries in a row show no activity), `during` inside its port call, `group` with its step marker in one macrotask, `return` by settling the port's promise as the port returns, `with` right after that call's synchronous delivery returns (no microtask between), `settle` from a microtask queued by a reaction registered right after the candidate's own observer of that call's promise (so behind the same jobs the caller's reaction was behind in the recording). A case is compared strictly up to its first input whose place does not fix its position (`busy`, or a mark the recording does not back; `casePlacement` in `trace.mjs`, read from the recording alone before anything runs); an event the candidate produces at the position of an input not yet delivered is `order`, different. Each event is compared when it is produced; at the end of the case, or of its compared prefix, each save's state is digested again with the repository's ledger encoder, every object that crossed must still hold what it held then, and the values are compared in one identity scope (which objects are one object across events; an identity number that occurs once in what was compared is not sharing). `late`, `mutatedByReceiver`, `place` and `after` are left out of the comparison by name: they annotate the test's side and where an input arrived. Named checks: `order`, `value`, `missing`, `extra`, `input`, `draw`, `ledger`, `case-bytes`, `mutated`, `placement`, `quiescence`, `hidden-site`, `real-timer`. An unhandled rejection while a case runs is counted with its result and printed as `info` (a test's own handlers are not in a replay).

Outcomes per case: reproduced (every recorded event); partial (every event before its first busy input, with that prefix's length: compared, never counted as a reproduction of the case); crossed (its first input is busy: nothing compared); unrecordable (only a case the recording itself flags, with its flags as the reason; a replay that calls a recorded case unrecordable, for a value it cannot place or `microtasks-inside-port`, fails `unrecordable-mark`); empty; different, with its check and the first differing event. What a partial prefix says (for the comparer): the candidate produced every event before the first busy input as recorded, the outputs at the end of the prefix included; those last outputs are what the scheduler did on its own before an input whose position is unknown, so a partial agreement holds on the reading that the busy input arrived no earlier, relative to the scheduler's work, than the recorded events put it (O0c review 3, M1: against a scheduler planted to settle one to three microtasks later, a real run can put the busy input before the last outputs of the prefix while the replay reports `partial`). A comparer must not read a partial prefix as agreement on where that input lands. Partial and crossed are properties of the recording, never of what a candidate does: the closure judgement reads every container itself (`recordedMarks`) and fails a case whose outcome disagrees with its marks (`crossed-mark`; `unrecordable-mark` for a recorded case reported unrecordable), a reproduced or partial case that did not produce every event it should (`reproduced-complete`), a case the replay did not report (`case-missing`), a count that differs (`event-count`), and a container it cannot read or whose end line does not hold (`container-integrity`). That integrity is self-consistency: an accidental cut, a lost line, a missing end line or a changed event fails, while a file rewritten on purpose with every count made to match is out of scope. `closure.mjs` exits 0 only when every case is reproduced or classified (partial or crossed in a test recording, unrecordable where the recording says so, with its reason; empty) and nothing differs; 1 on any difference, a scenario that is not reproduced whole (a partial or crossed scenario is a failure of the driver), a replay process that failed, a container that cannot be read (a damaged or tampered file) and the judgement's own checks above; 2 when nothing was reproduced, a selected source has no case (`empty-source`), a recording is not complete or the copy is not the recorded code; 64 for a usage error. It prints, per test file, the cases by outcome, each partial case's compared prefix and how many recorded events were compared. `replay-mutants.mjs` plants differences in a copy of the scheduler, each reported `different` by its own check on its own source and judged exit 1 (the planted module's provenance aside): eight on the scenarios (a launch delayed by a microtask, a save dropped, two launches swapped, an abort race delay changed, an abort not issued, a return value changed, an extra port call, a settlement moved), one per final check, each seen by that check alone (a saved state changed after its save resolved: `ledger`; a returned task changed after its settlement: `mutated`; the executor given the admitted object itself: `case-bytes`), one whose only effect is a timer's delay (the starting lease one millisecond later: `value` at its `timer.set`), the review's escapes (an extra save and an extra publication six microtasks after submit returns and a deadline one millisecond early, each on the test recordings; recovery in parallel, on the scenarios), a flush that settles one, two or three microtasks later, each `order` on the `shapes.toy.mjs` case whose compared prefix holds an input placed `settle`, and three of the reviews' escapes that `shapes.toy.mjs` reaches and no scenario does (the refusal code of an initialize after shutdown: `value`; the warning a failed publication logs: `value`; the timing of a failed mutation not reported: `order`), and `getTask` of a missing task answering `undefined` (`value`, on a whole shape case; no compared prefix of the corpus reaches it any more); and bugs in a copy of the replayer (a `settle` input delivered one microtask early, one late or two late: `value` on the `shapes.toy.mjs` case `awaited, then a call the settlement's own continuation makes`, replayed against the delivery copy (`DELIVERY_COPY`: its flush changes what `getTask` answers for that probe in the job before the continuation, the job of the continuation and the two after it, silently, and answers as the unchanged scheduler in the job of the continuation, so the unchanged replayer reproduces every case against it); the same plants against the unchanged copy on the real recordings are reported with their counts: no real recording has a job between a settlement and its continuation that changes state silently, so none tells an early delivery apart (0 of 306 cases), while a late one is `order` where the scheduler's own next job writes an event the input came before (one and two late: 3 of 306 each, which the full test requires); an input delivered early: `placement`; a port's already-settled promise settled at quiescence instead of at its return: `order`, on two schedulers initializing at once; a value difference reported unrecordable, against the deadline copy: `unrecordable-mark`; a partial case reported whole and busy marks ignored: `crossed-mark`; a case cut short before its last call: `event-count`; a draw from the wrong site: `draw`; and, each reported because a copy plant it breaks is no longer caught: output values not compared online, a value difference reported crossed, the ledger, `mutated` and identity checks skipped, `timer.set` compared nowhere).

**Comparer** (package O0d). `compare.mjs` compares one replayed case: the recording's events against the events the candidate produced, cut where the replay stopped. Exact equality with the recording stays the base rule and the replayer still decides `different`; the comparer names what differs, adds what equality cannot see, and can only turn a reproduced or partial case `different` (`check: compare`, with its `rule`) or `inconclusive`, never the other way. `replayCase` runs it on every compared case (`mode.compare`, on by default), and `closure.mjs` fails a reproduced or partial case without its verdict of pass (`compare-missing`); a different case keeps its check and gets the comparer's rule (`order/launch_delayed`). Rules, each reported by its name when it fails, the first difference by the most specific: `event-sequence` (exact total order of `in` and `out` events: kind, construction, member, port name, call, timer and port numbers); `port-arguments` (codec-equal, `executor.start`'s task in full); `saved-state` (every `persistence.save` where the recording has one, its state codec-equal and its bytes by the reference `encodeLedgerSnapshot` equal to the recorded digest; the save count is exact because the sequence rule matches every event); `shard-writes` (each proof shard write and removal, its text byte-equal); `times`; `identifiers`; `errors` (class tag, name, code, message); `mutation-timing` (count, `failed`, durations under the nominal `performance.now`); `logs` (message and fields); `returned-values`; `inputs` (what the candidate is given or asks for). Two rules also hold on every output of the candidate, equal to the recording or not: `times`, every time value (a key ending in `At`, `at`, `since`, a deadline, and every `timer.set` delay) is a `now` handed out at or before it, or a time an input carried, plus one named constant of `DELAYS` (the delay table of design §2.1, or a numeric option ending in `Ms`); a delay is such a constant or a due time less the now it is armed at; no window, no rank; the first difference says which now and constant each side matched; `identifiers`, every identifier (`taskId`, `leaseToken`, `dispatchWaveId`, `ownerID`, `requestId` and the task references) is a draw of its own site (`ID_SITES`; a hidden draw with its prefix) or one an input carried (each site's draw order is the sequence rule's: every draw is an event compared with its value). Over the corpus every time value and identifier of every reference derives this way (0 findings). Where the replay stopped inside a port call (the call compared, its answer never asked for), what the candidate produced of that call is compared, so a wrong argument is named by its value rule (`port-arguments`, `times`, `identifiers`, `saved-state` for a save's other fields), not as an order difference.

The independent oracles, computed from what crossed the ports, never from anything the candidate reports about itself: `codec-round-trip` (every saved state encodes with the reference codec, decodes and re-encodes to the same bytes; every shard text likewise); `transitions` (for every task, each proposed record against the record of the latest resolved save, the loaded one first when it is a save of the same trace, by the reference `assertManagedTaskTransition`; a member equal by value is given the previous record's object, as the scheduler's spread does, and a native job tombstone is compaction's, not a transition); `timer-census` (every timer fired, cleared or reported pending at the end; a settled `shutdown` leaves none live; at the first difference no timer the recording clears there is left live); the launch-latency oracle; `durability` (no launch before a resolved save, or the loaded state, holds that task active with that lease token: `starting`, or `running` for recovery's relaunch of a task the crashed instance had accepted, which `recoverTask`'s `relaunch` branch launches without a new save, as `restart-mixed` at save 9 shows; no waiter resolves with a task state before a resolved save holds it). The global assertions of design §5: `waiting-capacity` (no saved `waitingReason` of kind `capacity` or `system_pressure` unless the construction was given `admitLaunch` or a loaded state carried it, reported as information then: `scheduler.removal.test.js` passes the hook), `waiting-prerequisites` (only where the reference's save of the same number has it for that task), `admit-launch` (no call unless the hook was given), `active-count` (tasks starting or running in the latest saves at the end of each step equal the reference's).

**The launch-latency oracle** (design §5) holds a port to today's launch timing, which is the contract as recorded (for example 1 + 2N saves before the first of N simultaneous launches): the owner's rule is that sub-agent launches are never capped, queued, throttled or delayed. It judges every launch of the compared part independently of where the first event difference is. Per task, port and launch number it takes, in the reference and in the candidate, the step (the driver's step marker, or each arrived input in a test recording), the virtual time (the last now handed out), the event distance from the input that made it launchable (the last arrived input before it) and the timers set in between. The candidate's launch is read from its compared events when it is there, else from its run past the first difference: when a replay is `different` and the compared part launches at or after the difference, `replayCase` runs a fresh candidate again (`ObserveHost` in `replay.mjs`, observe-only: nothing is compared and the case stays different, OD1) on the recording's arrived inputs in recorded order, at quiescence or at their place where the candidate reaches it, with what it asks for answered by identity instead of position (a port call is the recording's call of that construction, port name and task in call order, and gets that call's answers and control calls; a timer is the recording's timer of that delay in set order; a read, clock or environment value is the recording's value of that key in the current step; identifiers come from their site's queue); what it cannot answer stops that run, and the launches it did not reach are listed as information (`launch-unjudged`), never passed. Step first, then time, then distance: a later one, more timers set between the input and the launch than the reference set, or a launch missing where the candidate's compared events or its run past the difference reached it is `launch_delayed`, in addition to whatever else is reported. An earlier one, or a launch the reference makes only past the compared part, only after a restart, or never because its instance stopped at a crash point first, is `launch_advanced`: a difference, reported as a change of dispatch timing that would need the owner's yes, not as a defect (it fails the case all the same). A launch the reference does not make is a defect: `launch_duplicated` when the reference launches that task through that port fewer times (design §2.2 place 17), else `launch_extra`. The design's cap at admission (M7), its capacity hold (M8) and a recovery that never pumps each diverge before any launch (an admission save, a hold, a recovery) and fail first as `event-sequence`, and each is also `launch_delayed` by name from the run past the difference; M8 is `waiting-capacity` there too (the capacity and admitLaunch assertions are also read from that run). A cap, a queue, a timer before a launch and a launch one tick late fail as `launch_delayed` as well (below).

**The two relaxations.** Nothing else makes a comparison more lenient than the replayer. The independence table (`mode.independence`; pairs of lanes whose relative order the code does not fix; a port call with its synchronous answer, or a timer set, is a unit; a unit may pass recorded units of a lane independent of its own and nothing else, never an input; order within a lane stays exact; port numbers follow the candidate's order of calls) is applied online by the replayer (`relax`: the recording's unit moves, positions and port numbers renumbered) and again, independently, by the comparer from the recorded order: each use is `info` with its citation, and the two must agree. It ships empty (`INDEPENDENCE`): the brief ships the design's two entries (`DESIGN_INDEPENDENCE`: publications against executor calls, publications against timer sets, each citing the scheduler lines) only if running code confirms them, and it does not: no recording varies the relative order of these lanes (they are byte-stable), a publication is never next to a launch in the corpus (next to a timer set 11 times), and a copy whose publication lane runs one or two microtasks later moves its publications past the mutation lane's own clock and option reads, which no entry covers (69 and 70 of 76 scenarios different with the entries and without them alike, the entries used 0 times). Widening the table is a timing decision for the owner. OD2's read mode (`mode.reads: 'free'`, off for the JavaScript closure, which compares reads exactly): for a candidate that is not the JavaScript scheduler, the recorded option reads leave the order and the candidate's reads are answered by key (object, operation, key) from the recorded value; a case whose compared prefix reads one key with two values is `inconclusive` (`option-varies`), a key the recording never read is `inconclusive` (`option-unread`), and every case reports its recorded and served reads. Over the corpus no case was `option-varies` (0 of 381 compared cases, 27,699 reads, the O0d build's `sweep.mjs --option-varies` run; the four scenarios fix round 1 added read the same keys once-valued as the scenarios before them). Production builds the scheduler in `packages/web/server/lib/orchestration/runtime.js` and, for recovery after a stop, `packages/web/server/lib/opencode/runtime-host/native-bundle-task-recovery.js`; neither passes option data that changes after construction (no getter, no object mutated later; the members read later are functions), the one value read again per save being the environment fallback of `expireUnacknowledged` (`DEVRYAN_ORCHESTRATION_UNACKNOWLEDGED_EXPIRY`), which the recorder records as an `env` input, not a read.

**Restart at every save point** (design §4.5). A crash point stops the scenario's instance at its k-th save (`durable`: the write landed and the process died before the promise settled, the fresh instance loads save k; `torn`: the write never landed, it loads save k - 1) and a fresh instance runs `initialize`'s recovery on it; replayed, a fresh reference and a fresh candidate load the same state and are compared through that recovery. `submit-complete`, `native-proof-shard` and `restart-mixed` have every crash point in the corpus (and in `candidates.test.mjs`); `CRASH_SWEEP_ENV` (`DEVRYAN_SCHEDULER_CRASH_SWEEP=1`) gives every other scenario its crash points too (from its stated save count; F7, which states its own crash, aside): 1,848 cases, whose stated facts all hold. Recording and replaying all of them costs CPU-hours (F1 at 64 and F2 alone are 258 crash points of 64 tasks each), so it is `sweep.mjs`, a manual run, and per push only the three scenarios above are swept. `restart-mixed` (3 submits in one group, the first accepted; its reconciles answered transient, live, terminal and relaunch in turn) restarts with two, three or no active tasks, some starting and some queued, so a recovery that runs in reverse order, reconciles in parallel, leaves a still-starting task without its re-armed lease or never pumps the queued ones differs at its crash point at save 6 (asserted per push). `native-proof-shard` (maxTerminalRecords 0, the driver's shard store outliving a crash as a file would) writes the completed native task's proof to its shard before the main commit that drops it, so its torn crash at save 9 is the crash between a shard write and the main commit; the self-test reads that from the recording (the shard answered before save 9, which never settles; the fresh instance loads save 8 and one shard). `wait-then-shutdown` has a waiter released after its terminal save and a shutdown with a starting lease armed.

**Bounded children.** Every child process the comparer's tools and tests start has an overall deadline that fails naming what was running (`bounded.mjs`: `runBounded`, `bunJson`, `replayBounded`). A child's deadline stops that child's tree only (`stopTree`: the processes below it listed first, while they are still its own; SIGTERM to the child, which, if it is a tool child, stops what it started through its own handler; then SIGKILL to the child if it still runs and to every listed process still there with the same command line), never a sibling's, and the result says it was a deadline. `withDeadline` bounds in-process work and stops every descendant on its deadline, so it is used only where that work runs alone (a recording in a test's `before`, a sweep scenario's own child). A tool interrupted by SIGINT or SIGTERM stops its descendants through its run root and starts no new child. Nothing relies on the shared runner's exit hook. CPU per test file (user plus sys, children included): numbers in the O0d report; each is under a minute.

**Planted candidates** (`compare-mutants.mjs`), each a copy of the scheduler package with one change, replayed against the reference recording of its scenarios with the comparer on, each `different` with its own rule among the comparer's failures and judged exit 1, against an unchanged control that reproduces every case: a launch one tick late (`launch_delayed`, on F1 at 8: with one task nothing comes between); a cap of four concurrent launches, a queue that launches one at a time and an extra timer set before a launch (`launch_delayed`); a launch right after its own starting save, before the admissions behind it (`launch_advanced`); an extra save and a skipped save (`saved-state`); a waiter resolved before its save and a launch before its starting save (`durability`); `startedAt` now plus 7 (`times`); a lease token made from the task ID while the draw still happens (`identifiers`); a label changed on acceptance with the scheduler's own guard taken out (`transitions`); shutdown no longer clearing starting leases (`timer-census`); a prerequisites hold written as capacity (`waiting-capacity`); fix round 1's: the design's cap at admission and its capacity hold, and a recovery that never pumps (`launch_delayed`, the hold also `waiting-capacity`); a recovery in reverse order (`port-arguments`), in parallel and without its starting leases (`event-sequence`), each on `restart-mixed` at save 6; a task launched twice (`launch_duplicated`); the second run-cleanup retry at 31,000 ms (`times`, on `run-cleanup-backoff`); queue order without its `createdAt` tiebreak (`saved-state` and `launch_delayed`, on `queue-order-ties`); shutdown no longer clearing task deadlines or the admission retry (`timer-census`, on `shutdown-with-timers`).

## Backend route-group conformance harness

`scripts/backend-conformance/` will show that a port of one route group of the web server behaves like today's JavaScript, judged at the group's own boundary (where the edge hands a request to the group's handlers). Five packages exist: the run skeleton (BH0), the group host with its tap (BH1), the scenario format and driver (BH2), the comparer (BH3) and the closure check (BH4). The census (BH5) and the planted-difference suite with its CI wiring (BH6) do not exist yet. A run records every scenario of the group on the reference, on a second reference and on the JavaScript candidate adapter, compares them, and judges each row; no candidate other than that adapter can be named on the command line yet.

**When the server's composition is checked.** The group host re-states how `application.js` composes the edge (`edge.mjs`). Whether it still does so is checked every time the harness runs (a run first runs the composition check, below) and by the explicit command `composition-drift.mjs`, which exits 0 when the composition matches, 2 on drift and 64 when refused. A run on a drifted composition judges nothing: its verdict is `COMPOSITION DRIFT`, it exits 2 (inconclusive) and it names every statement. Until a ported route group depends on this harness, the real file is not checked on every push: an edit to `application.js` does not fail a push gate because of the harness. The self-test proves the detectors on synthetic compositions and never reads or names the server's composition file; `composition.full.test.mjs` reads the real files but only asserts relatively (each planted change must add a problem that names it, whatever the baseline reports), so it cannot fail on an edit either. When the first port lands, its group's composition check joins the gates of that port: drift then fails the port's lane until the table is reviewed, and the edit that drifts must update the table in the same change.

**The composition check** (`composition.mjs`, `composition-drift.mjs`, `reach.mjs`, `edge-probes.mjs`, `census.mjs`).
- Text: the block of `application.js` from `const app = express();` through the feature-routes call to the end of the block, and the body of `registerRoutes` in `lib/opencode/feature-routes-runtime.js` from its start through the group's own call to its end, are parsed with the repository's TypeScript. Statements are compared as printed without comments, with strings in single quotes and without parentheses around a bare name or literal. A statement is relevant when it mentions the app, the HTTP server or the edge's state objects, or a name a relevant statement before it assigned (an alias); reads one of those as a property (`openCodeLifecycleState.expressApp.use(…)`); mutates an object the composition uses (a property of a name any entry or definition reads, of an import or of a span parameter: `express.response.json = …`, `compression.filter = …`, `routeDependencies.fsPromises = …`, `Object.assign(…)`); or calls a function of the same file whose body reaches one of those, directly or through another such function. The statements after the group's call count too: Express reads settings per request (`app.set('json spaces', 2)` after the call changes the group's answers), and layers registered there run when the group passes a request on. Every relevant statement, and every binding a classified statement reads, must be an entry of the table: composed (an `EDGE_STEPS` step of `edge.mjs`, in the same order), not applicable (its layers run for none of the group's requests, proven by the reach check; or, after the group's call, only for requests the group passes on, which the tail stand-in answers) or touching no request. A not-applicable entry must read the registrar it hands the app to, and the names a classified statement reads from outside the span are pinned as definitions (so moving a registrar's import to another module is drift: the reach check reads the census, which imports its own copy). An unclassified statement, a changed text or a changed order is drift. `--draft` prints the statements and digests as they are now, for re-reviewing the table.
- What reading the text cannot see, by construction: a patch or a setting made in another module (a module that patches `express.response` when imported, a registrar that calls `app.set`; today `lib/opencode/proxy.js` sets `opencodeProxyConfigured`, which Express does not read), a function defined in another module that reaches the app, and what the caller does with the app and server the host construction returns. The group host covers the first for every module it loads: it snapshots the framework's shared objects (express and its application, request and response prototypes, compression, the `http` server, response, outgoing and incoming prototypes, `fs.promises`) before composing and refuses to serve when composing the edge and the group changed any of them. A module only the server loads is seen by neither check.
- Reach: the product route census (`enumerateServerRoutes`, in a child process) must record no layer before the group's first route that runs for a group request, except from a composed step or a listed omission (the Electron runtime service's session layer). Whether a layer runs is decided by the server's own express router, case-insensitively as the app is configured, for every group route and method (HEAD for GET) with its parameters filled in, and for the layer's own literal path when a group route matches it.
- Layer stack: the layers of the composed steps that run for the group's requests, as the tap recorded them in the group host, must be the census's, in the same order.
- Probes (14): one per composed layer whose effect a client can see, against a host serving the toy group behind the same edge: no-store (`Cache-Control` with `no-store`, `Pragma: no-cache`) and indexing headers, compression just below, at and above its threshold, the server's compression skip policy (a request accepting `text/event-stream` is not compressed), the legacy path alias, the admission gate (one more `finish` listener on a write), the shared body parser's limit, execution readiness, the absence of a UI password (`/auth/session` says auth is disabled and a plain loopback `/api` request reaches the group), the local administrator as the principal, the local-owner enrollment page, the tunnel boundary (a request naming another host or forwarded from a tunnel is locked; its content-free liveness answer and its refusal of local-only paths), and the tail stand-in. Trust proxy is not visible to a client through this edge (any forwarded request from loopback is refused before the group), so its probe reads the composed app's settings. The thresholds the probes expect are checked against the server's own statements, and the self-test runs each probe on synthetic answers that lack its layer (a threshold one byte off either way, an event stream compressed, no `no-store`, no `X-Robots-Tag`).

**Runs and outcomes** (`run-scratch.mjs`, `outcomes.mjs`, `conformance-run.mjs`, `conformance.mjs`). Every tool refuses with exit 64 outside the test isolation guard and writes nothing then. A run's files live in `<os tmpdir>/devryan-backend-conformance/run-*`: the parent must be a private canonical directory of this user, the run directory is opened, held and checked before anything is written, and every write checks again that the path still names the held directory, refuses symbolic links and creates files exclusively (on Linux through the held descriptor; elsewhere a same-user swap between the check and the creation is detected right after it and refused). The directory is removed on pass, failure, SIGINT, SIGTERM and SIGHUP, never through a swapped path, and kept only with `--keep-artifacts` or `DEVRYAN_KEEP_ARTIFACTS=1`. A run killed by SIGKILL leaves its directory, marked with its pid; the next run removes every such directory whose process is gone, after it has continued and killed every process group the killed run recorded there (`process-groups/`, `arm-groups.mjs`: each record names the group's leader by pid, start time and a marker of its command line, and a pid that now names another process is never signalled; a group that survives the sweep's wait, 10 s per group, keeps the directory for the next sweep; runs a self-test nested in a killed run, in a private parent of its own, are swept with it). A row ends passed, failed, inconclusive, unstable or unrecordable; a passed row carries no differences. A row about the whole recording (`whole`: `<scenario>/recording`, `<scenario>/start`) never counts as the passed row exit 0 needs. A row carries `judged`, the differences and faults of the judged arm (the candidate, or J without one); a waiver never covers a row whose `judged` is not empty. A waiver names the row, the one outcome it covers and why, and may name the checks it covers (`checks`): then a row with any other check, or none, is not waived, and the waiver is a problem; a failure is never waivable, `--allow-inconclusive` waives inconclusive rows only, and a waiver that waives nothing (no such row, a passed row, another outcome) is a problem. Exit 0 needs every row passed or waived and at least one row that judged an exchange passed; 1 is any failed row; 2 is anything else not waived, composition drift, a census gap, or no rows; 64 is refused. Before the last line the report prints each named limit of the run with the number of things it applies to (`LIMIT candidate-effects-unseen (<n> candidate exchanges): …`, below), and the last line prints every count. After SIGINT, SIGTERM or SIGHUP the run prints one line saying it was interrupted and nothing more: no row and no summary made from the teardown's half-finished recordings.

**Group host** (`group-host.mjs`, `groups.mjs`, `edge.mjs`, `host-launch.mjs`). One process that serves one route group as the real server does: the group's real registrar behind the re-stated web edge, on loopback, on a data root the harness gives it, with the tap preloaded. `groups.mjs` is the table (registrar, the files that count as the group's, the dependencies the server hands the registrar, parameter values for the reach check's probes, handler factories whose functions count as the group's wherever they are registered, declared background work). The declared differences from the server: no OpenCode (the tunnel boundary's readiness answers ready), no UI password, the execution readiness of a verified bundle, the harness data root, and dependencies the edge takes but the group's paths never use, which throw once the host is serving (and are counted in `/status`). A host whose composition changed the framework's shared objects refuses to start (above). What the server composes after the group (preview, terminal, the OpenCode proxy, static files) is not composed: a stand-in answers 599 and marks the exchange `tail`, which is never compared and never counts as covered. `--home=<dir>` gives the host the HOME (and the XDG folders under it) that the scenario driver gives both arms: the host checks the isolation guard with the guard's own HOME first, then takes this one before it imports the group. The host stops on SIGTERM, SIGINT, SIGHUP, `POST /stop`, the end of its stdin (a pipe from its launcher, so it never outlives a launcher killed by any signal) and a change of its parent process. Product code logs to stdout: the launcher takes only a line starting `{"ready":` for the ready record and keeps the rest as the host's output; a host that is not ready in time, or exits first, is killed. Its control port answers `/quiescent?seq=n&timeoutMs=t` (bounded; `quiescent:false` with the pending sites when the time passes, after writing the exchange's changed effects), `/pending?seq=n`, `/status`, `/registrations` and `POST /stop`; every control call of `host-launch.mjs` has a timeout, and so has every test.

**Tap** (`tap.mjs`, a `node --import` preload, inert unless `DEVRYAN_BACKEND_TAP` names its setup file). It writes one NDJSON record file per process. Every patched method keeps its name and arity, and an error thrown through one has the tap's frame removed and the stack depth the untapped call would have had; group handlers are Proxies that add no frame, and the router's read of a handler's arity right before it calls it marks the entry. What it cannot see is printed in its first record and marked on the exchange where it can be detected (below).

**Record format, for the scenario driver and the comparer.** Records: `tap` (format 2), `host` (group, edge steps, source digests: the composition's identity), `registration` (kind, method, path, group, claimed, file, line, inWindow, router, top), `problem`, `exchange-start` (seq, peer, method, url), `exchange`, `blind`, `quiescent` (with its blind and crossed marks), `late` and `unattributed` (each with an `id`), `effect-update`. An `exchange` has `kind` (`group` when a group handler was entered, `tail`, or `edge`), `entered`, `tail` and `answeredBy` (who wrote the status line: `group`, `tail`, or the edge module); `peer` (the driver's correlation key: its local port and the request index on the connection); `request` (method, start URL, raw headers, the raw body bytes, `bodyComplete`); `entry` (what the first group handler received: URL after the rewrite, original URL, headers, `bodyParsedByEdge`, `bodyConsumedBeforeEntry`, the principal, `ip`, `ips`, socket addresses, the edge's headers at entry); `response` (status, the exact head, `headers`, `ops`, `body`, `afterEnd`, `wire`, `bodyHasStack`); `effects` (hub publications; `fetch` and `http-request` with headers, body chunks, `bodyEnded`, the answer's status and headers, and `error`; `child` with argv, cwd, `env` as changes against the host's environment with values as digests, `stdin` bytes and `exit`; each of these with `finished`); `blind` and `crossed` marks; `pendingAtEnd`. An effect is written as it stands when its exchange record (or its `late` or `unattributed` record) is written; whatever changes afterwards (a child's exit, an outbound answer or failure, body or stdin bytes sent later) is written as an `effect-update` record naming where it was written (`seq` and `list` `effects` or `edgeEffects` with `index`, or `list` `late` or `unattributed` with `id`) and carrying the effect's whole new state: the reader replaces the effect with the last update. An unfinished `fetch`, `http-request` or `child` is pending work of its exchange (type `EFFECT`, its site naming it), so an exchange is quiescent only once its effects finished, and every update is written before its `quiescent` record; an `http.request` never answered keeps it pending. An effect whose end the tap cannot see (a child spawned without an exit hook on its handle) is marked `unfinished-effect` when the exchange goes quiescent, and its record keeps `finished: false`. Each `response.headers` entry is one header name: `value` (final, or null when absent at the end), `owner` (its last writer), `group` (the value as of the group's last write, null when the group never wrote it) and, for `Vary`, `Cache-Control` and `Set-Cookie`, `elements` with each element's owner. The comparer compares `response.body` (the group's writes up to its first `end`; `afterEnd` and `wire` are never body) and, per header, `group.value`, or the group-owned elements of a list-valued header; never `owner` alone (the edge amends headers after the group) and never `ops[op=status]` alone. An exchange whose `answeredBy` is `tail`, or that has a blind or crossed mark, is inconclusive; one with `bodyHasStack` is unrecordable (a printed stack depends on how the process composed its layers; recognised as raw text, in finalhandler's HTML error page, the server's own error format, and escaped in JSON); `bodyComplete: false` or `aborted: true` is inconclusive; a `late`, `unattributed` or `problem` record must never pass silently. The blind marks: `response-callback` (timers, immediates or promises that product or group code starts from a response callback such as `finish`: not waited for), `foreign-listener` (a listener the group adds to an emitter created outside the exchange: when it fires under another exchange, that one gets a `crossed` mark), `async-resource` (an `AsyncResource` product or group code created: work it carries to a queue is not seen), `unfinished-effect` (above). A timer that product or group code started under one exchange and that fires after a later exchange entered the group marks the later one `crossed` (`event: 'timer'`, with the timer's site): a debounce or coalescing queue that the later exchange only pushes onto runs its work on the earlier exchange's timer, so the later one is quiescent before that work ran. A promise that never settles (a fetch body never read, a race against a cleared timer) keeps the exchange pending while something references it (once garbage collection takes it, its destroy settles it, so an unreferenced one may turn quiescent later: either answer is the collector's, which is why such an exchange must not pass on quiescence alone), and `/quiescent` says `quiescent:false` with the sites (the first frame outside Node, or the first Node frame past the async-hooks machinery, such as the unread stream). A compression handle (`zlib.gzip` and its kin) ends its work when it is closed, not when garbage collection destroys it; Node's `queueMicrotask` resource is ordinary work. An `http-request` effect's `port` is the one its Host header names. Not seen at all: work handed to a long-lived queue through a plain closure that no timer of an exchange runs, native threads without an async resource, worker threads, a child process's own descendants; pooled outbound connections (undici's, or a keep-alive `http.Agent`'s) are not waited for, the request is. An `AbortSignal.timeout(n)` given to an outbound call is a timer of the exchange: it keeps the exchange pending for n ms after the work is done.

**Scenarios** (`scenario.mjs`, `scenarios/<group>.mjs`, listed per group in `scenario-rows.mjs`). A scenario is code, made by `defineScenario`: an `id` that starts with its group's name, the `group`, the `principals` it uses (entries of `PRINCIPALS`), `fixture(root, values)`, which builds the starting data root (no fixture files in git), `steps(values)`, which returns the ordered steps, and `waivers` keyed by step id, each naming the outcome, the reason and the `checks` it covers (a row with any other problem is not waived). Every value the harness supplies and an arm may echo or store (ids, texts, times, tokens) is registered in the supplied-value registry passed as `values`, under a name: a name given twice must name the same value, and two names with the same value of a kind are refused, because a comparer could not tell which one an arm echoed. The fixture is given the registry too (what it writes, an arm may echo), and the driver registers each principal's own request headers (the forwarded address) and the arm's own values (the data root and home, with their canonical and URL-encoded spellings, and each process's listen port as `listen.<n>`). The step kinds: `exchange` (method, target, headers as ordered pairs, a body made by `jsonBody` or `rawBody`, the principal, and `edge: true` when the edge answers it: recorded on the reference, never sent to a candidate), `concurrent` (2 or 3 members sent at once), `external` (the harness writes, deletes, renames, makes a directory or link, or changes a mode in the data root), `restart`, `kill-after` (one exchange, then SIGKILL after `request-sent`, `response-head` or `response-end`, then a start on the same tree), `stream-open`, `stream-barrier <n items>` and `stream-close` (by the client after a barrier, or by waiting for the server's end), `quiesce` and `snapshot`. The format refuses, naming each problem: a step id given twice, a request header with a line break or one of the harness's own headers, a principal the scenario does not list, a principal the edge always answers in a step not marked edge, a concurrent step with fewer than 2 or more than 3 members, an unknown kill point, an external path that leaves the root, a barrier or close of a stream that is not open, a restart or kill while a stream is open, a stream never closed, a waiver that names no step, and a waiver that names no checks. The principals (design §6): the local administrator and an unauthenticated request forwarded from outside loopback, which the reference produces (the tunnel boundary refuses the second, so its steps are edge steps), and a managed administrator and a managed developer, which it cannot (they need the Supabase-backed runtime); a step whose principal an arm cannot be given is not sent, and its row is inconclusive (`principal-unavailable`), waived by the scenario's table for that check only. A candidate is given the principal as an envelope (version 1: principal, assignment, peer, `authorizationActive`, the original URL and the sequence number) in `X-DevRyan-Harness-Envelope`, base64 JSON, with `X-DevRyan-Harness-Seq`. On the reference every field of the envelope of a class it produces is checked against what its group saw at entry (`envelope`): the principal from the tap's entry, and the request-context store's assignment, the peer (a direct local request; a tunnel owner's) and whether the principal's authorisation is live, read at entry with the product's own functions by the group host (`tap.observeEntry`); a field the record does not carry is a problem too. The managed envelopes are harness input that no arm has confirmed (`confirmedBy: null` in `PRINCIPALS`); they are confirmed only once an arm can produce those principals (edge auth, inventory B12). The pilot's four scenarios are `magic-prompts.reads-and-writes` (every route for each principal class; the id, text and body matrices of the design; validation failures; a `null` body and malformed JSON, both answered by the shared parser; remote requests refused by the tunnel boundary), `magic-prompts.write-lock` (concurrent PUTs, and a PUT with a DELETE of the same id) `magic-prompts.restarts` (a restart between a write and a read, external edits including a malformed file, a kill after a write's response and a kill as soon as a write's request is sent) and `magic-prompts.request-forms` (what Express and the shared body parser give the JavaScript group and a port must give itself: a conditional GET sending the ETag back (304), a trailing slash, the path in another letter case, HEAD, a query string, `charset=latin1` (the edge answers 415) beside an explicit `charset=utf-8`, a gzip body (inflated by the parser), a body one byte over the path's 50 MB (the edge answers 413 after reading it all), a byte-order mark, an empty JSON body and an `application/*+json` type (the group answers both); each step states who answers it, which the reference's tap confirms).

**The driver** (`driver.mjs`, `arms.mjs`, `tree.mjs`, `http-exchange.mjs`). It runs one scenario against one arm and records each step; it judges nothing. An arm is a process that leads its own process group: the reference is the group host (`referenceArm`), a candidate any executable that speaks the candidate protocol of the design (`candidateArm`: `--listen`, `--control`, `--data-root`, `--home`, `--stub name=URL`, a ready line, `GET /quiescent?seq=n`, `POST /stop`; each control call on a connection of its own, so an idle keep-alive connection the candidate closed cannot fail a call); the self-test's fake candidate is `toy/fake-candidate.mjs`. Requests are written as raw bytes on a connection of their own (the client adds `Host`, `Connection: close` and `Content-Length` only when the scenario did not), and the response is read to its end (Content-Length, chunked or the connection's end; the body is not decoded). Both arms get the guard's environment plus `TZ=UTC`, `LANG` and `LC_ALL` `en_US.UTF-8`, umask 022, and a HOME of the run (with the XDG folders under it; the group host takes it with `--home`, after its isolation check). The tracked roots are the data root and that HOME: both are held, frozen, walked and compared (a HOME path is written `home:<path>`). Every arm process group is recorded in the run (`process-groups/`) and handed to the keeper (`keeper.mjs`, one per harness process, in a session of its own, holding a pipe from the harness) before the arm can be frozen: when the pipe ends, the harness is gone (by any signal, SIGKILL included), and the keeper continues and kills exactly the groups it still holds, each checked to be the recorded process, then exits; the next run's sweep does the same from the records, so an arm frozen when the harness was killed never stays stopped. One exchange: a descriptor is held on every regular file of the tracked roots; the request is sent and the response read (t0, t1); the arm's group is frozen with SIGSTOP and S1 taken (two walks of the tree that must agree: names, types, permission bits, sizes, content digests, link targets and each directory's listing order, with inodes and mtimes recorded; plus the files the arm holds open); the group is continued with SIGCONT on every path, failure included; the arm's quiescence claim is asked (for the reference, the exchange is found by its connection's local port in the tap's records); the claim must name the exchange and say quiescent; the group is frozen again for S2, where any file the arm still holds open is a false claim; the descriptors are released, which says which files were replaced (a new inode at the path) or removed. The claim is never taken on trust: before the next step the driver opens an idle connection to the arm's listen port (work deferred to the next connection runs now), asks the claim again and takes a snapshot that must equal S2 (a change, or a withdrawn claim, is a late effect of that exchange), and after the last step it stops the arm and compares the tree left once the process group is gone. At every frozen snapshot and before every stop the driver walks the process tree from the arm's group by parent pid: a descendant outside the group (`group-escaped`, naming its pid and command) is recorded and handed to the keeper like a group, and killed when the arm stops. The members of a concurrent step must overlap on the wire: every request handed to its socket before any answer began (`concurrency`, by the order of wire events, no clock). A kill-after step records the arm's exit, which must be by SIGKILL (`step-error` otherwise), and whether the kill landed before the response. A stream the arm ends before a barrier is reached, or before the client closes it, is `stream-truncated`. A step the harness cannot perform (an external change the tree no longer allows, a walk that fails) is `step-error` for that step, and the run goes on; every step of the scenario gets a record and a row, also when the arm never started (`arm-start`) or died before it (`arm-died`, said once per step; the tree the dead arm left is the step's `afterDeath`). A concurrent step on the reference is also run once per order of its members, each from a copy of the tree before the step on a restarted host; the concurrent result must be one of those serialisations (`not-linearisable` makes the row unrecordable), and the tree is restored to the concurrent result afterwards. Once an arm that was asked to stop has exited, its process group must hold no live process (`group-survived`); an arm that does not stop when asked is signalled (`stop-escalated`). The reference's edge rewrites the multi-user vault (`multi-user-vault.json`, new ciphertext) in the data root at every start: snapshots mark that entry `edge: true`, and the driver's own tree comparisons (admissible serialisations, the restore check) leave it out. Its `multi-user-vault.key` is written once, at the first start, and never changes, so the driver compares it like any file; the comparer leaves it out of reference-to-candidate and reference-to-reference comparisons after checking that no snapshot after the first start changed it (`REFERENCE_EDGE_STARTUP_FILES` in `arms.mjs`). Every snapshot also keeps, once per content digest, the bytes of each file of 1 MiB or less (`recording.blobs`, for the comparer's substitutions) and the window of its own walk (`takenAt`); a concurrent step keeps the tree restored after its serialisations (`restored`). Each problem names its check (`CHECKS` in `driver.mjs`); every wait has a deadline (60 s or more by default) that names what did not answer. The driver's teardown (every group it started continued and killed, every connection closed, every held descriptor released) runs at process exit and from `interruptTeardown`, which the command passes to the run root so that it runs on SIGINT, SIGTERM and SIGHUP before the scratch is removed. What it cannot see: a write that lands before SIGSTOP takes effect is in S1; work an arm defers until it receives the next *request*, or runs on a timer that fires after the next-step snapshot, lands inside the next step together with that step's own effects, and the driver cannot tell the two apart, so each step's record names the step that would absorb it (`lateUntil`) and only the comparer (this step's S2 against the reference's) can find it; a descendant that leaves the group is found by its parent pid, so one whose parent has already exited (a daemon's double fork) is not linked to the arm any more; the walk itself has no deadline. **Effects seen from outside** (`observe.mjs`). The reference's effects are the tap's. A candidate runs under an observation from outside, and its exchange records carry `effects` (`seenBy`, `outbound`, `children`; `events` null): every arm gets one loopback stub per stub name (`outbound`, then the group's own; each a supplied port `stub.<name>`), handed to the group host with `--stubs` and to a candidate with `--stub name=URL` and as `DEVRYAN_HARNESS_STUB_<NAME>` in its environment, recording every request (method, path, headers, body bytes) and answering 204; a candidate's `PATH` starts with a folder of the run holding a link to one shell script for every program name on its `PATH`, which records the name, the working directory and the arguments, puts the original `PATH` back (so the program's own children are not recorded, as the tap records only the group's) and runs the real program; and at every frozen snapshot the driver lists the members of the candidate's process group other than the candidate itself (the process-group look; a child the shim already recorded is the same pid and is not repeated). What is observed is attributed to the exchange whose S1 and S2 it falls in (a concurrent step's to its first member: from outside the members cannot be told apart); what arrives after the claim is `late-effect`. Not seen, and said in every run's summary as the limit `candidate-effects-unseen` with the number of candidate exchanges it applies to: a child started by absolute path that exits between two looks, a connection to an address the harness did not hand out, and hub events (a candidate publishes them only through the protocol's `/events`, which is not read). The time windows (t0, t1) are checked by the comparer; the file system's mtime lag behind the clock is measured once per run (files written and stated against `Date.now()`, `recording.mtimeGranularityMs`) for the comparer's mtime window. Snapshots record each tracked root's own permission bits (`rootMode`); a file written and removed between two snapshots leaves no trace in either and is not seen.

**The comparer** (`compare.mjs`, `compareRecordings`). It compares two recordings of one scenario and names every difference (scenario, step, component, location, rule, the reference's value and the other's), and every part it cannot compare in full (inconclusive, never passed); it imports only Node built-ins. Two modes: `stability` (a reference against a second reference: the client's view and the tap's, every header with its owner and each list element's owner, the group's entry, request bytes and effects) and `candidate` (the reference's tap against a candidate seen from outside). In `candidate` mode the reference's group exchange is the tap's: its status, the headers the group itself wrote (for `Vary`, `Cache-Control` and `Set-Cookie` only the elements the group owns; a header the edge later changed or removed is expected as the group wrote it), and the body before compression. The rules (`RULES`), each with its self-test: **S** supplied values (the data root and HOME of each arm by name, each spelling: as given, canonical, the firmlink alias `/var` for `/private/var`, URL-encoded; listen ports per exchange, from its `Host`) are written in the other arm's spelling, only where the value stands as a whole path (not followed or preceded by a name character or a slash, `file://` allowed) or a whole port after a colon; a value that merely contains a root, or a path outside every root, is compared as it is; arms that share a root are inconclusive. **P** identifiers at JSON keys the group declares (`DECLARATIONS` in `closure.mjs`; none for `magic-prompts`) are paired by position, one to one: a value only one side has is never paired, a conflict is a difference, a pair used once is reported. **W** times at declared keys are replaced in both arms by their exchange window and their rank in the record (equal times share a rank), a time outside every window stays as it is; the `Date` header must fall between its exchange's t0 and t1; a changed file's mtime must fall between the two snapshots it changed between (the lower bound widened by the file system's lag the driver measured). `ETag` is exact (over a body holding a supplied value it is inconclusive). Files: each tracked root's own mode; type, mode, bytes (after S, P and W), link target, extra and missing paths, replaced or removed (the driver's held descriptors), the step that last changed each path (any fact, inode and mtime included), each directory's listing order; inode and time values never; bytes the snapshot did not keep are inconclusive. Bodies are compared as bytes (the first differing offset, and the JSON path when both parse); in structured values (effects, the tap's entry) null, undefined and an absent key differ, and so do 3 and "3", 0 and -0, and the same keys in another order. Headers are matched by name case-insensitively, every line exactly and in order within a name; `Content-Length` must be on both sides and equal its own body's length (a HEAD answer has no body: its value is compared with the reference's); `Date`, `Connection`, `Keep-Alive` and `Transfer-Encoding` are the transport's, but the presence of `Date` is a rule (the candidate sends one exactly when the reference's wire has one); anything else a candidate sends that the group did not set (an edge header such as `Content-Encoding`, the envelope echoed) is a difference. Not compared, by design, because no client of this server reads them and an HTTP library other than Node's would differ in each without a difference in meaning: the case of header names, the order of headers of different names, the reason phrase and `Connection`. The request a candidate was given must be the one the group received (method, URL, headers without the harness's two, body bytes). When the group answered before its body ended and nothing read the body (no edge parser, nothing consumed before entry), how many bytes the tap saw is timing and is never compared: the tap's bytes must be a prefix of the bytes the driver sent the reference (otherwise inconclusive), and the candidate must be given exactly the sent bytes; in stability mode each tap's bytes must be a prefix of what its arm was sent, and the bytes sent are compared. A body that something may have read and the tap saw incomplete is inconclusive. Effects (hub events, outbound calls, children) are compared in order and by count; a candidate side that was not observed at all (`effects` null) is inconclusive with the check `candidate-effects-unobserved`, never taken as no effects; a kind the other arm does not report is inconclusive when the reference made one, and a difference when the group is declared unable to cause it. An effect seen from outside is compared on what the outside sees: a child's program name and arguments, an outbound call's method, host, port and path, and body bytes (the reference's headers, working directory, environment and stdin, when it has them, are said not compared). Streams: items one by one, their count, how they ended. A concurrent step is compared with each of the reference's serialisations (every member's exchange and the final tree, by all the rules above); it is admissible only if it equals one, otherwise `concurrency(not admissible)`. The reference's edge files (`multi-user-vault.json`, marked `edge`; `multi-user-vault.key`, written at the first start) are left out of tree comparisons; a candidate that has one fails. Server log lines are not compared.

**The closure check** (`closure.mjs`, `js-candidate.mjs`). Every scenario runs on the reference (R), on a second reference on a fresh data root (R') and on the JavaScript candidate adapter (J), at the same time, each with its own data root and HOME; with a candidate command (`runClosure({ candidateCommand })`, not on the command line yet) also on that candidate (C). J is the group's own registrar in a process of its own behind the candidate protocol: Express as the server resolves it with `x-powered-by` off, the product's request decoding (`registerCommonRequestMiddleware`: a candidate is given the raw body), and the envelope's `principal` and `assignment` set with the product's `runWithRequestPrincipal`; it ignores the envelope's `peer`, `authorizationActive` and `originalUrl`, and refuses an envelope that is not version 1 or names another exchange. Its quiescence claim counts the runtime's own kinds of work (file system requests, timers, sockets, writes) started under each request (not a compression handle, which only garbage collection destroys: a body it inflates has ended before the response). The stubs it is given (`--stub`) go to the group's dependencies; `--compose <file>` replaces its own layers with the file's `compose` (the planted differences in J's layers use it). J and a candidate are given only the principals the reference can produce (`local-admin`). A row's outcome, in this order: a driver problem on R or R' makes it inconclusive (unrecordable for `body-has-stack` and `not-linearisable`); R against R' differing makes it unstable; a stable edge exchange is inconclusive with the check `edge-exchange` (nothing of the group's is judged on it); a problem of J, or R against J differing, makes it unrecordable; a part of either comparison that could not be made makes it inconclusive; with a candidate, a candidate fault or a difference fails it; otherwise it passed. What the judged arm did is never hidden by an earlier class: a candidate fault or a difference of the candidate fails the row whatever came before (the earlier class stays in the reason), and on a row an earlier class left inconclusive a fault of J, or R against J differing, makes it unrecordable. Each scenario also has the row `<scenario>/recording` for what belongs to the whole recording (the supplied values, the start and exit trees, the edge files, the last-writer and mtime rules at the start and exit). A row of a kill at `request-sent` or `response-head` still says it is nondeterministic; it is stable when R and R' agree in this run.

**A run.** `conformance.mjs --group=<name>` runs the composition check, then the closure check on every scenario of the group (or those named by `--scenario`), writes each arm's recording to `recordings/<scenario>/<arm>.json` in the run's scratch (removed with it unless the run is kept), and judges the rows. A row awaiting comparison (`awaiting`, only the driver's own rows have it) can never be waived: `--allow-inconclusive` naming one is refused (64), and a table waiver of one is dropped and counted as a census gap. Census gaps returned by the rows' producer reach the verdict. For `magic-prompts` today: 74 rows (70 steps of four scenarios and 4 recording rows), 63 passed, 11 inconclusive and every one waived by the scenarios' tables: the five managed-principal rows (for `principal-unavailable` only: the reference cannot produce a managed principal) and six edge exchanges (for `edge-exchange` only: null and malformed JSON bodies, the two remote requests, `charset=latin1` and the body over the limit), so the command exits 0; the summary's limit line says the 57 exchanges J was sent were observed from outside under the named limit. `put-text-plain` (the group answers a `text/plain` PUT before reading its body) is judged by the unread-body rule and passes.

**Harmlessness** (`harmlessness.mjs`, judged by `harmlessness-judge.mjs`). Each test set runs under Vitest twice plainly and once with the tap in every process (`NODE_OPTIONS`); outcomes and printed lines (stdout and each test's junit output) must be equal, judged by `judgeParity` and `outputLines` from the client harness. Lines the two plain runs already disagree on are learned (digit shapes there, and here also one differing word between a common prefix and suffix, such as a temporary directory name) and counted. A difference exits 1 even when something else is inconclusive; a tapped run in which the tap wrote nothing, or a set that should drive group handlers but did not, is inconclusive (2).
