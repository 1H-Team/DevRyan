# DevRyan Testing

## Commands

| Command | Use |
| --- | --- |
| `bun run validate` | The local gate before every push and release tag. Diffs against the upstream branch (override with `VALIDATE_BASE`) and runs only what the change touches. |
| `bun run validate:full` | Lint, import boundaries, the browser graph, unreached browser files, declaration parity, type-check, `docs:validate`, build (once), `bundle:check` and `test:full`. CI runs these same checks across its build and test lanes. |
| `bun run test:startup` | Curated startup and user-data contract. |
| `bun run test:full` | Scripts and every package suite, as one bounded concurrent pool (`node scripts/test-full.mjs [--suite=web,ui]`). |
| `bun run docs:validate` | Markdown links and inline-code paths, and drift against package manifests, source exports and environment-variable names. |

`bun run validate` runs:

- oxlint on changed `.ts`/`.tsx` files inside the directories `bun run lint` covers (the targets of each workspace's oxlint `lint` script, today `packages/ui/src` and `packages/web/src`), so fast and full lint check the same files (everything when shared configuration changes);
- type-check of changed packages and their dependents (everything when root `package.json`, `bun.lock`, `patches/`, `.oxlintrc.json`, `tsconfig.json`, `vite-theme-plugin.ts` or `.opencode/opencode.json` change). Any `packages/ui/src` change also type-checks web, whose tsconfig includes the UI source, and a `scripts/opencode-v2-native/*.ts` change type-checks web, whose runtime-host tsconfig includes those files;
- tests of changed packages and their dependents: any file under `packages/ui/src` runs the UI suite, any `packages/web` file (server, bin, src, the Vite and Vitest configuration, test setup) the web suite, any `packages/agents-core` file the agents-core suite and its web dependent;
- every suite in `FULL_TEST_SUITES` when root `package.json`, `bun.lock`, `patches/`, `.nvmrc` or `bunfig.toml` change (so a patch edit runs `scripts/opencode-v2-native/mcp-client-patch.test.mjs`);
- `test:scripts` when `scripts/`, `.github/`, `.opencode/agents|plugins` or `packages/web/runtime/reviewed-inputs` change (their Markdown and text included, since the reviewed-inputs manifest hashes every file), and `bun run catalog:check` (which fetches the live catalog) when the reviewed model catalog changes;
- `docs:validate` for every change: besides Markdown it reads package manifests, source exports and environment-variable names, so a code-only change can make docs stale;
- import boundaries and the browser graph when package code changes (every importer when a package manifest, `scripts/import-boundaries.json` or a checker changes); unreached browser files for the same changes, any test file, `scripts/unreached-files.json` or its checker; declaration parity for any JavaScript or declaration file, package manifest, `scripts/declaration-parity.json` or its checker;
- the Rust ledger core check, `node scripts/build-ledger-core.mjs --verify` (format, clippy, `cargo test` and a byte-for-byte rebuild of the tracked module), with the script tests that read the crate, when `packages/harness-runtime/native/ledger-core/`, `scripts/build-ledger-core.mjs` or the tracked `packages/harness-runtime/lib/native/ledger-core.*` change; only these changes need the pinned Rust toolchain, and without it the check fails with the command that installs it ([harness runtime](../packages/harness-runtime/DOCUMENTATION.md#rust-ledger-core)). A tracked module change also runs the harness suite;
- `test:startup`, always: each startup group whose owner suite already runs in the same plan runs there instead of twice.

Fast mode narrows `test:scripts` to the script tests whose closure holds a changed file (`scripts/test-select.mjs`). The closure follows each test's imports, resolved as `scripts/check-import-boundaries.mjs` resolves them, and every file its scripts and tests name by path or file name (a spawned script, a `Bun.build` entry, a read fixture); shipped package code reaches files only through its imports and module URLs. Only a file that puts the scripts suite in the plan (under `scripts/`, `.github/`, `.opencode/agents|plugins` or the reviewed inputs) can widen the run: such a non-code file (workflow, fixture, JSON, shell) selects the tests naming it or its outermost directory (`.github` for workflows), and the whole suite when none does. Other changed files, such as package code, only add the script tests that reach them. A file under `packages/harness-runtime/native/ledger-core/` also selects the script tests that read that whole tree (`TREE_READERS`: `scripts/build-ledger-core.test.mjs`). Markdown and text files never enter the graph: any Markdown change other than `CHANGELOG.md`, alone or beside code, runs `scripts/release-docs.test.mjs`, which reads every tracked Markdown file for the published-release rule `docs:validate` does not check, and no script test reads tracked `.txt` files. Changes to the selector, its resolver, the suite runners (`validate.mjs`, `test-scripts.mjs`, `test-runner-utils.mjs`, `test-full.mjs`, `test-ci-lanes.mjs`, `test-pool.mjs`), the suite contract, reviewed inputs or the toolchain run the whole suite, and a changed test file also runs the inventory's tests. A change to a test file of any package, even one that does not put the scripts suite in the plan, also runs `scripts/test-suite-contract.test.mjs`, which inventories every test file. `scripts/test-select.test.mjs` checks on this checkout that every file in every script test's import and name closure selects that test. `validate` prints the selection and why the rest were skipped; a subset leaves the startup scripts group in `test:startup`. `validate:full` and CI always run every script test.

A change confined to the `version` fields that `scripts/bump-version.mjs` writes (package manifests, workspace versions in `bun.lock`, the legacy Tauri `tauri.conf.json`, `Cargo.toml` and the `devryan-desktop` entry in `Cargo.lock`) runs `node scripts/release.mjs check-versions` (every version file and `bun.lock` workspace agrees) instead of every package's lint, type-check and tests. Any other change to those files keeps the full shared-configuration plan. CI still runs everything for the bump commit before release admission.

Independent static checks run concurrently and all report, and any failure stops before tests. In `validate:full` the build and bundle budgets then run in order beside the test pool, and `scripts/built-web-assets.test.mjs` (the only test that reads the build output) runs after the build; `validate` (fast) runs no build. Test commands run as one weighted pool of independent processes within a capacity of `DEVRYAN_TEST_CONCURRENCY` (default: half the cores, between 2 and 4). A unit reserves its `weight` (default 1): the Vitest `web` project and the harness suite start their own workers and weigh 2. Local runs split the serial `node --test` script batch into three timing-balanced shards and the web runtime-host project into two (`localTestUnits` in `scripts/test-ci-lanes.mjs`; CI lanes use their own inventory). While the host's 1-minute load average is above its core count, the pool starts no further unit (one always runs), so concurrent runs on one machine (other worktrees, a build) queue instead of driving timeouts; `DEVRYAN_TEST_LOAD_LIMIT` sets the ceiling as a multiple of the cores and `0` disables it. Every unit has a wall-clock budget (`DEVRYAN_TEST_UNIT_TIMEOUT_MS`, default 20 minutes) after which its process group is killed and it fails as timed out; script `node --test` files also get `--test-timeout=300000` and `--test-force-exit`. Each Bun package run gets the cores the pool leaves it (`--parallel=<cores / DEVRYAN_TEST_CONCURRENCY>`, at least two, scaled by a heavy unit's weight; `DEVRYAN_TEST_WORKERS` overrides), each unit's output printed whole when it ends, a heartbeat naming running units every minute, every unit run to completion and every failure listed. Native graph test files share one exclusive pool resource: they build and spawn the pinned runtime, and the shared fixture's browser OAuth callback binds localhost:1455. Independent units keep running alongside them. Interrupting stops every owned process group and removes the run's scratch. Both modes end with per-command and slowest-unit timings.

`scripts/check-import-boundaries.mjs` resolves static, re-export, `require` and literal dynamic imports between packages. Application packages (web, Electron, legacy desktop) expose only their `main`/`exports`; a package that declares `exports` exposes only those targets, by package name or relative path. Tests (`*.test.*`, `*.spec.*` and files under a `tests/` directory) may import another package's private files, since parity and integration tests exercise both sides; they are still refused a package-name import that the target's `exports` omit. Each temporary exception in `scripts/import-boundaries.json` (production code only; currently none) is one exact importer/target pair with the plan stage that removes it (`unscheduled` when none does yet); an exception that no longer matches fails, so the list only shrinks. No exception covers a package-name import of a subpath the target's `exports` omits, because Node refuses that import at runtime. `scripts/check-browser-graph.mjs` walks the web Vite entry points with the build's aliases and fails on Node builtins, `adm-zip`, or a web-server, Electron or Node-only shared-runtime file.

`scripts/check-unreached-files.mjs` walks the same graph, with the same resolver, from the web entry points and the service worker (`packages/web/src/sw.ts`), and again from every tracked test file (a server test contributes its own imports; the walk stops at privileged files as the browser graph does). Every code file under `packages/ui/src` and `packages/web/src` that neither walk reaches fails, unless `scripts/unreached-files.json` lists it with a kind (`awaiting-removal` for dead code a later phase deletes, `hand-run` for a tool run by hand and kept on purpose) and a reason; it also prints, as information, how many files only tests reach (`--verbose` names them). Two known limits: a file reached only through `import type` counts as reached, and helpers under a `test/` directory inside `src` count as tests, so they are not checked. The server packages are out of scope: their string-built dynamic imports make a file-level check noisy. `scripts/check-declarations.mjs` pairs every first-party hand-written declaration with its JavaScript twin (`x.d.ts` with `x.js`, `x.d.mts` with `x.mjs`, and the `types`/`default` pairs of package manifests) and fails when the declaration exports a value the implementation does not; type-only exports need no implementation, relative re-exports are followed on both sides, and exports the implementation has without a declaration are information (`--verbose` lists them). Vendored reviewed inputs and the frozen legacy desktop package are skipped. A pair it cannot compare (a CommonJS implementation, or one that re-exports a package) fails too. `scripts/declaration-parity.json` lists known mismatches and uncomparable pairs, each with its reason, and, separately, `transformExports`: permanent exemptions for names a native build transform adds to the bundled copy of an implementation only (the browser and document-reader plugins), each naming its transform; such an exemption fails when the transform's source stops exporting the name or the shipped implementation starts exporting it. The other lists only shrink: an unlisted finding fails, and an entry that no longer matches (the file is now reached or deleted, or the declaration was fixed) fails until it is removed. `--prune` on either checker removes stale entries and never adds one; fix the finding instead of listing it.

A docs-only change runs only `docs:validate`. Both validate modes fail if the run left new entries in `.cache/` (see [STORAGE_CLEANUP.md](STORAGE_CLEANUP.md)).

## CI

`.github/workflows/ci.yml` runs on every main push and pull request. Every job starts at once; none waits for another and no artifacts move between them:

- `static` (Ubuntu): `node scripts/validate.mjs static` — lint, import boundaries, the browser graph, unreached browser files, declaration parity, type-check and `docs:validate`, run concurrently. Then, on every push and on a pull request that changes the ledger core's crate, build script, tracked module or `ci.yml`, it installs the pinned Rust and runs `node scripts/build-ledger-core.mjs --verify`, whose rebuild must match the module built on macOS byte for byte.
- `build` (Ubuntu): `node scripts/validate.mjs build` — the build, bundle budgets and the tests of the built assets (`BUILD_JOB_TESTS` in `scripts/test-ci-lanes.mjs`, such as `scripts/built-web-assets.test.mjs`).
- `tests` (two Ubuntu lanes): `node scripts/validate.mjs ci:<lane>` with the normal scratch guard.
- `native-tests` (three macOS lanes): build and verify the native v2 runtime in-lane (cheaper than shipping it between jobs), then run their lane. GitHub Free runs five macOS jobs at a time and a release holds two while it waits for CI, so three is the most CI may use.

`scripts/test-ci-lanes.mjs` expands the full suite into files before assigning platforms; it keeps macOS sandbox, native binary, case-insensitive filesystem and platform-gated checks on macOS. Units are packed onto lanes longest first from the recorded durations in `scripts/test-unit-timings.json` (a unit without a recording costs the median); the web runtime-host Vitest project runs as two shards. Every lane uploads its unit timings as the `test-timings-<lane>` artifact; refresh the recordings with `bun run test:timings:update <files...>`. The native-stream file has two disjoint case shards (ordinary local runs register every case); `test-suite-contract.test.mjs` checks the complete inventory and shard union, and that a case-sharded file registers every test through its shard filter. CI runs Bun package suites in randomized order seeded with the workflow run number (`DEVRYAN_TEST_SEED`). Main-push concurrency is unique to the commit SHA and never cancels a different main commit; superseded PRs still cancel. Release preparation overlaps CI, but publication requires the exact main-push workflow to pass. `bun run validate:full` remains the equivalent complete local gate. `release-cache.yml` is manual-only; see [Release pipeline](RELEASE_PIPELINE.md).

Measured and deliberately not adopted (2026-10): caching `tsbuildinfo` or the Vitest module cache in CI (TypeScript 7 type-checks every package in about 26 s run one after another, measured 2026-11, and transforms are 1–2% of Vitest time), parallel `node --test` for the script suite (no speedup; deadline-sensitive tests fail under contention), and moving hazard-free web tests to `bun test` (they rely on Vitest APIs such as `vi.waitFor`, and parallel Vitest already runs them in under a minute).

## Startup contract

`scripts/test-startup-contract.mjs` runs the startup and user-data tests: runtime bundle startup, selection and upgrade, ledger and session integrity, Retry, cancellation, delayed bootstrap, event subscription, and Electron startup and ownership. It uses disposable fixtures only: no installed-app data, live accounts or OS service registration. `STARTUP_CONTRACT_GROUPS` names each group's owner suite (`electron`, `scripts`, `shared`, `harness`, `ui`, `web`); `--covered-by=<suite,...>` skips groups already covered elsewhere in the same run.

## Suites and runners

`test:full` runs every suite below, including the bundled Plan Mode contract in the frozen legacy Tauri package. Cargo tests are not run because they require native build assets. `FULL_TEST_SUITES` in `scripts/test-full.mjs` is the inventory. The pool splits three suites without changing what they run: one process per script Bun test file, the two Vitest projects of the web suite (`test:vitest --project=web|web-runtime-host`) beside its Bun native files (`test:native`), and the harness suite with Bun file workers (`bun test --parallel=4`). `scripts/test-suite-contract.test.mjs` checks every split runs each file exactly once.

Set `DEVRYAN_TEST_TIMINGS=<file.json>` to record each unit's duration and status. Set `DEVRYAN_TEST_SEED=<n>` to run Bun package suites in randomized order (`--randomize --seed=<n>`); a failure reproduces with the same seed. Tests must not depend on the order of other tests: reset shared stores, module-level mocks and globals in `beforeEach`, not only `afterEach`.

Expensive invariants are tested at the smallest size that crosses the boundary. Production limits that tests must exceed (ledger install batches, the change-store listing bound, the admission dedupe cache) are constructor options with unchanged defaults, so a test crosses them with a few hundred records instead of tens of thousands. Create test Git repositories with `initGitRepository()` from `scripts/test-git-template.mjs` (a copied template, about ten times faster than `git init`).

| Suite | Command | Runner |
| --- | --- | --- |
| Scripts, `.opencode/agents` and `.opencode/plugins` tests, reviewed runtime inputs | `bun run test:scripts` | `scripts/test-scripts.mjs`: files importing `bun:test` run one per `bun test` process (never sharing Bun's resolver), the rest in one `node --test` run, all through the bounded pool. `DEVRYAN_SCRIPT_TEST_CONCURRENCY` sets Node concurrency (default: one file at a time inside the outer pool). |
| Shared UI | `bun run --cwd packages/ui test` | `scripts/test-ui.mjs`: one `bun test --parallel` run in the isolation guard's environment; every file gets its own global and module registry, so `mock.module` and global replacements cannot leak |
| Web | `bun run --cwd packages/web test` | each step inside `scripts/test-isolation-guard.mjs`: `test:vitest` (`vitest.config.ts`: project `web` file-parallel with a 15 s test budget; project `web-runtime-host` with two workers for the native runtime-host suites; no app build plugins), then `test:native`: five native runtime-host files, the native integration directory and the native isolation canary under `bun test`. Native host scripts: `bun run --cwd packages/web test:native-host`. |
| Electron | `bun run --cwd packages/electron test` | `scripts/test-electron.mjs` routes by import, in the isolation guard's environment: `node:test` to Node (concurrent files, with the isolation `--import`), `bun:test` to one `bun test --parallel` run; any other framework is refused |
| Legacy Tauri JavaScript contract | `bun run --cwd packages/desktop test:managed-orchestration` | `bun test` (the frozen manifest is unchanged: run it through `test:full`, or wrap it in `node scripts/test-isolation-guard.mjs`) |
| `shared-runtime`, `harness-runtime`, `orchestration-runtime`, `cursor-sdk-runtime`, `agents-core` | `bun run --cwd packages/<name> test` | `bun test` inside `scripts/test-isolation-guard.mjs` |

Runner and discovery changes belong in `scripts/`. Feature tests live beside their source unless a contract spans packages.

## Test isolation

No test process may read or write the real home folder, DevRyan, OpenCode or Git configuration. `scripts/test-isolation-guard.mjs` builds a private environment, and `scripts/test-isolation-check.mjs` checks it inside every test process.

The environment (`createTestIsolation`): one private root per run, `<os tmpdir>/devryan-test/run-*`, holds `HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME` and a private `GIT_CONFIG_GLOBAL` with a test identity (`GIT_CONFIG_NOSYSTEM=1`, `GIT_TERMINAL_PROMPT=0`). Every inherited variable that selects a location, endpoint or credential is removed, not re-pointed: `DEVRYAN_*`, `OPENCHAMBER_*` and `OPENCODE_*` names ending in a location, URL, host, port, binary, token, secret, password, key or identifier suffix (for example `DEVRYAN_DATA_DIR`, `DEVRYAN_RUNTIME_BUNDLE_ROOT`, `OPENCODE_CONFIG_DIR`, `OPENCODE_DB`, `OPENCODE_BINARY`, `DEVRYAN_SESSION_TMP`, `DEVRYAN_SERVER_URL`, `OPENCODE_PORT`, `OPENCODE_SERVER_PASSWORD`), plus `CLAUDE_CONFIG_DIR`, the Meridian, Cursor and `gh` locations, the `GIT_DIR`/`GIT_CONFIG_*` family and `SSH_AUTH_SOCK`. Each root then resolves to its default under the private `HOME`, exactly as in CI, which sets none of them. Product behaviour switches, limits and timeouts pass through (`PASSED_THROUGH` in the guard); `scripts/test-suite-contract.test.mjs` fails when product code reads a `DEVRYAN_*`, `OPENCHAMBER_*` or `OPENCODE_*` name that is in neither list. `TMPDIR` is left as the runner sets it. The root is removed when the run passes, fails or is interrupted (kept with `--keep-artifacts` or `DEVRYAN_KEEP_ARTIFACTS=1`), and a runner started inside an isolated environment reuses it. Bun's runtime transpiler cache (`BUN_RUNTIME_TRANSPILER_CACHE_PATH`) stays at its existing location: it holds only transpiled sources.

The check (`scripts/test-isolation-preload.mjs`) runs before any test: the Bun `preload` of the root `bunfig.toml` and of every package that runs `bun test` except the frozen `packages/desktop`, the `--import` of node:test runs, and the web Vitest global setup and setup file. It requires the home directory, the XDG folders, the Git configuration and every stripped variable that is still set to lie inside the private root named by `DEVRYAN_TEST_ISOLATION_ROOT`. What happens without that environment depends on the runtime:

- Node (`node --import=…preload --test`, Vitest): the process builds the environment itself, before any test or product module loads, because Node's `os.homedir()` follows `HOME` on every call; Vitest's workers inherit it. These direct runs are isolated.
- Bun: `bun test` reads `HOME` once at startup and its preload sees neither the command line nor the filters (`process.argv` holds only the test file; `ps` loses quoting, and with `--parallel` the preload runs in each worker), so it can neither move the process nor run it again. A bare `bun test` stops before any test with `DevRyan test isolation: refusing to run tests against the real home folder.`, the reason and the command that runs one file in that folder.
- A bare `node --test` without the `--import` loads nothing of the guard (Node reads no configuration file by default) and is not isolated.
- A `bun test` started inside a source subfolder (for example `packages/web/server` or `packages/ui/src`) reads no `bunfig.toml`, so the preload never runs. The shared test setups that such files import (`packages/ui/src/test/mountedDom.ts`, `packages/harness-runtime/test/session-mutations-fixture.js`, `packages/harness-runtime/test/session-change-fixture.js`) stop the file with the same explanation; other files run unguarded. Start `bun test` from the package folder.
- `packages/desktop` is frozen: its one contract file is isolated when a runner (`test:full`, `validate`, CI) starts it, not when it is run directly.

| `packages/web`, Vitest | `bunx vitest run <path>.test.js` |

`bun run --cwd packages/web test <file>` is not a single-file command (the file reaches only the last of its two steps), and the Electron runner ignores file arguments. `node scripts/test-isolation-guard.mjs <command> [args...]` wraps any command. Every repository runner builds the environment for its own processes: `bun run test:full`, `node scripts/test-scripts.mjs`, `bun run test:startup`, `bun run validate`, the CI lanes (through `prepareScriptTestEnvironment` in `scripts/test-scripts.mjs`), the built-asset tests (their `--import`), and the package `test` scripts (`node ../../scripts/test-isolation-guard.mjs bun test`, and the UI and Electron runners).

Each runner collects an isolation canary (`scripts/test-isolation-canary.test.mjs`, `scripts/test-isolation-canary-bun.test.mjs`, an `isolation-canary` test in every package, one in each web Vitest project) that takes the home folder, the DevRyan data root, the runtime-bundle root and the OpenCode config and data folders from the product modules that resolve them, derives the OpenCode state and cache folders and the DevRyan log folder from `XDG_*` and `HOME` as the bundled OpenCode host and Electron do (neither exposes an importable resolver), checks the Git identity, and requires each inside the private root. `scripts/test-isolation-guard.test.mjs` runs every canary and shows each Bun runner refusing and each Node runner isolating itself without the guard's environment; the suite contract fails when a runner, unit or package test script starts tests without the preload, the import or the environment.

What stays real, on purpose: `PATH` and the tools on it (Git, Xcode command-line tools, `codesign`, `sandbox-exec`, `openssl`), `USER`, `TMPDIR`, loopback ports, `BUN_INSTALL` and the Bun transpiler cache. The private home also gets a copy of the ripgrep binary the installed Cursor SDK ships at `.cache/opencode/bin/rg`, where OpenCode's ripgrep lookup lands when `rg` is not on `PATH`; without it, tests that build that layer would download ripgrep from GitHub. Vitest stores its own startup token under the home folder before any setup runs, so a direct Vitest run still writes `Library/Application Support/vitest` in the real home.

## Policies enforced by lint

Module-graph rules that used to be source-text tests (a component must not import an eager dialog, a removed surface, or a heavy renderer; a file must not own timers) live in `.oxlintrc.json` `overrides` as path-scoped `no-restricted-imports` and `no-restricted-globals` rules, so `bun run lint` enforces them once instead of a test reading the source. Tests assert behaviour: rendered markup, calls and state, not the text of the implementation. Keep a source read only for a genuine text contract (CSS rules, generated assets, documentation).

## Test-suite contract

`scripts/test-suite-contract.test.mjs` fails when a test file is not discovered by its package runner, when a deterministic test uses `skip`, `todo` or `only` (`test.skip(`, `{ skip: … }`, `.todo(`, `.only(`), when a conditional skip is not inventoried, or when the feature matrix is stale. Do not silence a scenario: delete tests for removed behavior or rewrite them for the current contract. Opt-in gates below are reported as not run, never skipped.

For the web package it lists what Vitest collects (`vitest list --filesOnly`, nothing runs) and checks that `notVitest` in `packages/web/vitest.config.ts`, apart from the reviewed inputs, names exactly the `test:native` targets of `packages/web/package.json`, that every entry exists, and that every web test file runs under exactly one of a Vitest project and `test:native`. Each web startup-contract file must be collected by a web Vitest project and be in no `notVitest` entry. That proves only that the configuration collects it; whether the CI lanes' `DEVRYAN_VITEST_EXCLUDE` moves it to another unit is covered by the full-inventory lane test, not by this check.

`scripts/test-conditional-skips.json` inventories every test file that can skip a test or return early from one on a condition (platform, a built launcher, a full Xcode, System Integrity Protection, a captured install, the Node version, an opt-in variable). Each entry names the CI job that runs the file (`tests`, `native-tests` or `build`, checked against the lane inventory) and each guard its mechanism, its exact source text, the condition in words and whether CI satisfies it (`ci`: `yes` or `no`). The contract fails when a `skipIf(…)`, `runIf(…)` or `t.skip(…)` call, or any reference to `test|it|describe.skip|todo|skipIf|runIf` without a call (an alias such as `process.platform === 'darwin' ? test : test.skip`), is not covered by one of its file's guards, or when a guard's text, its condition's `definition` or the file is gone. Guard texts are compared with whitespace ignored, so reformatting keeps them pinned. Early-return and `if`-wrapped guards cannot be found mechanically, so add them by hand. It prints every guard CI never satisfies: those tests never run in CI. The pool summary still counts a unit whose tests all skipped as passed, because it keeps no unit output.

`scripts/feature-test-matrix.mjs` maps feature families to source and test anchors; the contract test checks that every anchor exists. Add a row when you add a feature family. Tool tests describe stable policy and presentation families, not every plugin tool; a new tool must stay visible through the generic fallback.

## Fixture rules

- Use temporary directories in the OS temp dir, injected dependencies or loopback-only fakes. Never require credentials, live providers, external network, the user's configuration or installed-app state.
- Every runner starts its test processes inside the private environment described in [Test isolation](#test-isolation).
- `packages/web` Vitest also gives every test file its own empty `DEVRYAN_DATA_DIR` under `<private root>/web-test/run-*` (`test/isolated-data.global.mjs`, `test/isolated-data.setup.mjs`), removed when the run ends. A write guard fails any test file whose process creates, writes, moves or removes a path inside the real home's DevRyan, OpenChamber or OpenCode folders (code that reads the account home rather than `HOME` could still reach them), even when the code swallows the refusal. Child processes and the Bun `test:native` suites are not intercepted by that write guard; the environment isolates them.

## Ledger dual-run harness

`scripts/ledger-dual-run/` checks one implementation of the session mutation ledger against another before any of it is ported (plan row L0). It changes no product file. It records a scenario through the product host (`createSessionMutationHost`, worker thread and all) with a tap on the host's `Worker`, so every message that crosses `packages/harness-runtime/lib/session-mutation-host.js` is logged. A replay posts the recorded `call` messages to another implementation on a fresh twin of the fixture, behaves as the recording's host behaved (the recorded answers to input functions, observer callbacks answered as the host answers them, `abort` and `stream-return` where the host sent them, deadlines re-based on its own clock), and logs the same messages. Every judgement is made from outside the implementation: what it returns over the protocol, what it leaves on disk, what Git reads from its repository, and what the harness itself observes about its files, its clock and its ref moves.

| Command | Use |
| --- | --- |
| `node --import=./scripts/test-isolation-preload.mjs --test scripts/ledger-dual-run/dual-run.test.mjs` | Self-test (in the scripts suite): the identifier site table, the comparer's undefined/null, background-callback, stamp and time checks, and one small recording replayed against the product worker (no difference allowed) and against two planted differences (JSON key order; stamps cut to microseconds), each reported by its own check |
| `node scripts/ledger-dual-run/dual-run-harness.mjs` | Full run: every scenario against the worker-thread and the stdio-process implementation, cross-reading, the aged-profile corpus read and mutated, every planted difference seeded and unseeded, crash points with recovery, lock contention between implementations, and the coverage report. `--suite=`, `--scenario=`, `--implementation=worker,process,native:<path>,native-unseeded:<path>`, `--allow-inconclusive=<scenario>,…`, `--json=<file>`, `--keep-artifacts`. It isolates its own process from the owner's home and Git configuration first |

Every row ends **passed**, **failed**, **inconclusive** or **info** (a characterisation). Inconclusive is never a pass: the run exits 0 only when nothing failed and nothing was inconclusive, 1 when anything failed, and 2 when only inconclusive rows remain; `--allow-inconclusive` names scenarios whose inconclusive rows are counted and shown but not fatal. The last line prints the counts and the coverage summary. The full run also fails when a method of `SESSION_MUTATION_METHODS` or a seam message type is neither exercised by a scenario nor listed in `COVERAGE_WAIVERS` (`dual-run-suites.mjs`) with a reason, and when a crash point expected to be reachable is not reached.

Every run uses `<os tmpdir>/devryan-ledger-dual-run/run-*` (removed on pass, failure and interruption unless artifacts are kept), runs at the same stage path one after another, and gives each arm and its ledger a private `HOME`, XDG folders, `TMPDIR` and Git configuration (no hooks, no templates) inside the stage. Fixtures and every Git command the harness runs itself read no system or global Git configuration.

What the comparer checks, and the independent observations it checks against:

| Check | How |
| --- | --- |
| Each call | result (`undefined` and `null` are different values; an absent member and a member set to `undefined` are different too, as structured clone keeps them), error fields, summary step names and counts, journal records, `progress` transitions, callbacks with arguments and answers, observer payloads, stream bytes in place |
| Background work | per process generation: the `ready` method list; observers and observer callbacks (`onChange`, `onMaterialize`) without a cause, as multisets |
| Disk | every entry under the stage by type, mode, link target and bytes, JSON text byte for byte after the rules below; a ledger's own Git files are read through Git only at `<storage>/<root>/git/` (refs, packed refs, loose objects, packs, `objects/info/packs`, reflogs, `info/refs`); any `*.lock` in a ledger's Git repository is an oracle finding; anything else there (`objects/info/alternates`, a leftover `tmp_obj_*`) is compared as a file |
| Git | object format, `HEAD`, refs, every reachable object by type and content paired through the trees that name them; `git fsck --strict`; Git's canonical tree order; index files by entries |
| Ref moves (git shim) | every arm's `PATH` starts with a shell `git` (`dual-run-git-shim.mjs`) that execs Git unchanged except for `update-ref`, where it records the calling process, the bytes of `owner.lock` before and after the real update, and the exit code. Oracle: every move of `refs/devryan/state` happens while `owner.lock` exists and names the moving process, before and after. Compared: the number of state moves; every tree the state ref ever pointed to, in order, object by object (a wrong step a later commit repairs still shows); lease refs created and deleted, by lock state; lease-ref advances outside concurrent scenarios |
| Commit order of concurrent calls | read from each run's own Git history: which session, call, prompt and lease records each state move changed. A replay is compared when its order equals the recording's; a reordering of the same commits is replayed up to twenty times and is inconclusive if it never matches; anything else is compared and fails |
| Cross-reading, aged corpus | each implementation reads a ledger the others wrote; the aged-profile corpus is read back, warmed, and mutated (leases cancelled and cleaned, reverts, a new edit, native holds, continuations and a removal) |
| Crash points | made from outside by the git shim at `update-ref` (before the first and second commit of a publication, after the intent commit, inside a first build) for every implementation, and at the JavaScript ledger's own file operations (`ledger-preload.cjs`) for the JavaScript process; each crashed ledger is recovered by the product and by every implementation, and each recovering run's own stage is checked for atomicity of the project file and `git fsck` |
| Contention | two product hosts, then the product and each implementation, edit one project at once (both publish, both edits land, every state move under its mover's lock); a holder stopped inside `owner.lock` by the shim and then killed, in both directions: the survivor waits while the holder lives and then reclaims the dead owner's lock |
| JavaScript-only | the preload's counts of the JavaScript ledger's own file operations are reported as notes, never compared |

What legitimately differs between two runs, and how it is judged:

| Source | Treatment |
| --- | --- |
| `randomUUID` (tokens, record, operation, transaction, hold, removal IDs, folders, temporaries) | the identifier protocol below when both runs follow it; always paired one to one by position (results, aligned records, tree entries), with derived forms (no dashes, SHA-256 key names); a value that would pair twice is a difference |
| Proof digests (`digest` in restore proofs) | computed over tree IDs of records that hold file stamps, so different in every run: paired one to one like identifiers |
| Wall-clock times (`reservedAt`, `createdAt`, `updatedAt` and the other keys in `VOLATILE.timeKeys`) | replaced by the harness's own call window they fall in (`<time in window N>`, `<time after window N>`); outside the run, compared as numbers |
| File stamps `dev:ino[:size:mtimeNs:ctimeNs[:mode]]` (`identity`, `observation`, `stamp`, `before`, `after`, `verified-objects.v1`) | replaced by the path and moment of the harness's own bigint `lstat` observation they equal exactly (`<stamp project/a.js@3>`); a stamp that equals none names the inode's path and the fields that differ, so a truncated time or another file's inode is a difference |
| Durations (`elapsedMs`, `queueMs`, `waitMs`, `holdMs`, `lockWaitMs`, `ms`, summary `steps` times) | masked as numbers at those keys |
| Journal records emitted only past a duration threshold (`slow: true`), worker stall observations, `progress` timing | counted or not compared; `progress` compared as its sequence of states |
| A call its host aborted | its result and callbacks compared; its reports, steps, progress and observers (how far it got before the abort landed) reported as notes |
| Order of `verified-objects.v1` lines | compared as a multiset of lines |
| Git index files | compared by entries through Git, not bytes |
| Receipt pages and receipt results, whose order follows `files/<sha256(id)>` key order | compared as written when both runs follow the identifier protocol, else as rows ordered by path |
| Unreachable objects, loose/packed split | compared with the identifier protocol outside concurrent scenarios, else reported; every reachable object and every historical state tree always |
| `drain`'s list of settled background work, `git/info/refs` ids, pack names | whether it settled; ref names only; not compared (pack bytes follow object content) |

### The native ledger interface

A native ledger is driven with `--implementation=native:<path>` (it follows the identifier protocol) or `native-unseeded:<path>` (it does not; list orders that follow random identifiers are then compared by path, and the planted-difference suite shows which checks still hold). It must:

1. Start as `<path>` with no arguments and the arm's environment (`HOME`, XDG folders, `TMPDIR` and Git configuration inside the stage; `PATH` starting with the git shim). Exit when stdin closes.
2. Read one JSON line per host-to-ledger message on stdin, the first `{"type":"init","workerData":{"directory":<storage>,"maintenance"?,"batching"?,"complexity"?,"stallClock"?,"observers":{"onChange":bool,"onMaterialize":bool,"onDiagnostic":bool,"onLockTiming":bool,"onWorkerStall":bool}}}`, then `call {id, method, input, context}`, `abort {id, reason}`, `callback-result {id, failed, value|error}`, `pull {stream}`, `stream-return {stream}`.
3. Write one JSON line per ledger-to-host message on stdout and nothing else: `ready {methods}` first, then `result {id, failed, value|error, steps}`, `report {id, record}`, `progress {id, waiting}`, `observe {observer, payload, cause}`, `callback {id, target:{call, fn}|{observer, cause}, args}`, `chunk {stream, done, value|error}`. Field meanings as in `session-mutation-worker.js`; values as in `session-mutation-wire.js` (function, stream and error markers). `context.deadline` is an absolute wall-clock time in milliseconds.
4. Encode values as `dual-run-codec.mjs` does: `{"$dr":"bytes","base64"}`, `{"$dr":"undefined"}`, `{"$dr":"number","value":"NaN"|"Infinity"|"-Infinity"|"-0"}`, `bigint`, `date`, `map`, `set`, and `escape` for an object that has a `$dr` key. Key order of objects is significant.
5. Move ledger refs with the `git` on its `PATH` (`git --git-dir <root>/git update-ref …`), as today's ledger does: the lock oracle, the ref history, the commit order and the outside crash points observe those moves. A ledger that moves refs without the Git executable shows as making no moves, a difference.
6. Persist, return and call back exactly what the JavaScript ledger does (file 26 §4b and §4c): the same records byte for byte, the same summary steps, journal records, observer payloads and callbacks in the same order per call.

#### Identifiers and time

Identifiers. With `LEDGER_DUAL_RUN_IDS=<seed>` in its environment, a ledger draws every random identifier from the protocol instead of its random source (`dual-run-ids.cjs`): the nth draw (from 1) at site *S* during seam call *C* is `sha256("<seed>:<C>:<S>:<n>")` in hex, laid out as `8-4-4-4-12` with the version nibble set to `4` and the variant nibble to `8`. *C* is the `id` of the `call` message whose work draws it (work a call started counts for that call even after its result was sent; anything else is `background`). The harness gives each process generation its own seed (`<seed>:<generation>`). The sites are names, not source positions:

| Site | Names |
| --- | --- |
| `lease` | a lease token (`views/<token>`, `refs/devryan/leases/<token>`, `leases/<sha256(token)>.json`) |
| `document` | a file document ID (`files/<sha256(id)>.json`) |
| `operation` | an operation ID: publications, reconciled outside changes, direct receipts |
| `materialization` | a materialization intent (`materializations/<id>/`) |
| `transaction` | a revert, redo or file-restore transaction ID |
| `hold` | a native admission hold ID |
| `removal` | a native removal intent ID |
| `standby` | a parked or discarded view folder (`view-standby/<id>`) |
| `temporary` | any temporary file name, never left at rest |
| `lock-owner` | the `ownerToken` of a cross-process lock file, never left at rest |

The JavaScript ledger is mapped to these names by the source text around each draw (`ID_SITES`), so moving a line or adding a comment keeps the name; a draw no entry names is logged through `LEDGER_DUAL_RUN_ID_LOG`, a protocol difference, and the self-test fails when any `randomUUID(` in the ledger's files has no name.

Time. A ledger reads the system clock; nothing is injected. The harness makes the time comparable instead: it takes its own wall-clock window around every group of calls it issues (from before the first is posted to after the last returns) and lets the clock move on by at least one millisecond between windows, so every stored time falls in exactly one window or gap; a time is compared by that window. A deadline crosses the seam as an absolute time, so a replay posts it the same distance from its own posting time as in the recording.

Optional, JavaScript only: `LEDGER_DUAL_RUN_CRASH` and `LEDGER_DUAL_RUN_AUDIT` (`ledger-preload.cjs`) add crash points at the JavaScript ledger's own file operations and notes on them; a native ledger is crashed from outside by the git shim instead.
