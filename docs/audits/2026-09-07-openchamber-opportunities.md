# OpenChamber opportunities for DevRyan — 7 September 2026

The best first investment is a focused chat/performance pass: narrow the composer's prompt-history subscription, bound tool diff rendering, keep question context visible, preserve copied Markdown, and bound shell discovery. These are identifiable gaps in the inspected DevRyan source. Larger OpenChamber rewrites should be treated as design references and evaluated independently against DevRyan's contracts.

## Scope and evidence

- User-authorized comparison with `openchamber/openchamber`; no access to the separate OpenCode repository.
- Window: 24 August 2026 00:00 UTC through the inspected 7 September default-branch head, `cab07805456c97be462ce2289c2ba3a1c56d3eca`.
- Inventoried 573 reachable commits returned by GitHub for the date window. This includes merges and intermediate/follow-up commits; it is **not 573 distinct features**. Read 44 selected commit-detail responses and inspected relevant pinned upstream source against local source. This is not a line-by-line audit of every commit.
- DevRyan comparison: working tree at HEAD `76c7cbfb3721610e5760a98e6795724f3334c6c4`, including the pre-existing uncommitted work. No application implementation was changed during this review.
- Latest published upstream release at review time: [v1.22.2, 5 September](https://github.com/openchamber/openchamber/releases/tag/v1.22.2). The inspected head includes later work; notably the new terminal adapter is newer than that release.
- Rankings are engineering judgments about expected benefit **in DevRyan**, frequency of use, scope, and integration risk. They are not measured speedups. Static code establishes the cited gaps; live reproduction and performance benchmarking were not performed.

The numbered order favors useful, contained changes before larger changes with broader failure modes. “High, conditional” means severe when triggered but not an everyday benefit for every user. Low risk still requires normal verification.

## Findings beyond commit titles

### The composer still follows assistant output through prompt history

In [ChatInput.tsx](../../packages/ui/src/components/chat/ChatInput.tsx), around line 1086, `useUserMessageHistory` is used to populate recall. Its nearby comment describes a narrow hook, but the current implementation in [sync-context.tsx](../../packages/ui/src/sync/sync-context.tsx), around line 4557, calls `useSessionMessageRecords`. That record snapshot changes when an assistant's parts change, and the history builder creates a fresh history result.

The proposed correction is a selector whose output changes only when visible user prompts or their revert boundary change. It must handle delayed user-part arrival, session changes, deletion and rollback. A useful acceptance test checks reference identity across assistant-only updates and observes composer render counts during synthetic streaming. This is more focused than replacing global session stores.

### Stable React keys currently preserve one large Markdown subtree

[markdownStreamingBlocks.ts](../../packages/ui/src/components/chat/markdownStreamingBlocks.ts) returns one object containing the full response. [MarkdownRendererImpl.tsx](../../packages/ui/src/components/chat/MarkdownRendererImpl.tsx), around lines 522 and 877, preserves unchanged block identities, but that one block changes whenever text grows. Its memoized React Markdown child therefore receives the full updated text.

Stable keys already solve a real completion-remount problem; retain that behavior. Introduce an incremental parsing strategy only with checks for open fences, list continuation, tables, reference links, math, HTML comments, file references and finalization. A naive split on blank lines would break Markdown. Profile long single answers separately from long histories: history virtualization does not make the currently streaming message cheaper to parse.

DevRyan also defers Prism highlighting while a code block changes, then highlights after a settling delay. A bounded tail-highlighting strategy could improve appearance during streaming. It should not re-highlight an entire growing code fence for every token or add animation that repeatedly changes row height.

### Output budgets should cover more than diffs

The rich preview and raw fallback in [ToolPart.tsx](../../packages/ui/src/components/chat/message/parts/ToolPart.tsx), around lines 788 and 907, accept the whole patch. [toolPartDiffEntries.ts](../../packages/ui/src/components/chat/message/parts/toolPartDiffEntries.ts) also splits complete patch strings. Put the budget before that work; truncating only the final `<pre>` is insufficient.

Similarly, [toolRenderers.tsx](../../packages/ui/src/components/chat/message/toolRenderers.tsx), around line 80, calls `JSON.parse` without an explicit output-size ceiling. A small collapsed tree can still require parsing a huge input. Apply budgets to parsing, highlighting and rendered nodes, while keeping the full source available through an explicit user action. Label previews as partial rather than silently treating a truncated output as complete.

### Queue fidelity and queue ownership are separate projects

[messageQueueStore.ts](../../packages/ui/src/stores/messageQueueStore.ts) already captures attached files and provider/model/agent/variant/Plan settings. It should not be replaced with an older or simpler upstream send-config shape.

The remaining concern is context fidelity: [ChatInput.tsx](../../packages/ui/src/components/chat/ChatInput.tsx), around lines 1519 and 1568, retains `confirmedMentionsRef` for later file-mention extraction. The background [useQueuedMessageAutoSend.ts](../../packages/ui/src/hooks/useQueuedMessageAutoSend.ts), around lines 80–101, uses stored attachments and agent-mention parsing. That code shape motivates a focused parity test across manual send, auto-send, edit and remount. It does not prove that every queued attachment is lost.

Capture the complete resolved input once, then make every delivery path consume it. Only afterward evaluate moving dispatch into the host. Preserve DevRyan's dispatch-time message IDs, Builder admission, Plan choice, recovery intent and authorization checks.

### Idle work and cache ownership still deserve measurement

DevRyan already returns early when no project actions are running in [ProjectActionsButton.tsx](../../packages/ui/src/components/layout/ProjectActionsButton.tsx), around line 466. The upstream idle-polling fix is therefore not a new gain in that path.

A more relevant profiling candidate is the app-level queue hook's all-session status subscription even when its queue is empty. First measure its notification frequency and cost; if material, disable status subscription for an empty queue or restrict it to queued sessions. Preserve cross-directory blocking-request checks.

For session switching, retain [session-message-loader.ts](../../packages/ui/src/sync/session-message-loader.ts), its prefetch bounds and lifecycle fencing. Compare parse cost, visible-paint delay, component commits and retained heap. Do not enlarge caches merely because upstream did; scope entries to the runtime/account/session and invalidate on deletion or revocation.

## Already present, inapplicable, or not justified as a direct port

- **Completed reasoning without simulated streaming:** DevRyan's [ReasoningPart.tsx](../../packages/ui/src/components/chat/message/parts/ReasoningPart.tsx) selects terminal mode when complete, and [useStreamingTextThrottle.ts](../../packages/ui/src/components/chat/hooks/useStreamingTextThrottle.ts) returns the full terminal text. Upstream [e24caa918f](https://github.com/openchamber/openchamber/commit/e24caa918f) is largely redundant here.
- **Restore prompt on failed send:** DevRyan already has target-aware draft/attachment restoration and ambiguous-network handling in `ChatInput`. Do not overwrite this with the simpler upstream [ae491bf5b5](https://github.com/openchamber/openchamber/commit/ae491bf5b5) catch path.
- **History virtualization, prefetch and narrow sync state:** already substantial in DevRyan. Its [MessageList.tsx](../../packages/ui/src/components/chat/MessageList.tsx) virtualizes history above an 80-entry threshold and keeps the streaming tail separate. Upstream's move to LegendList is not a prerequisite for improving DevRyan.
- **Child discovery above 200 sessions:** upstream [741b7c5588](https://github.com/openchamber/openchamber/commit/741b7c5588) fixes a broad directory-list discovery path, with an overlap follow-up [52f5f52a5d](https://github.com/openchamber/openchamber/commit/52f5f52a5d). DevRyan's inspected `useEnsureSessionChildren` instead calls the parent-specific children endpoint and fences request ownership. Do not label DevRyan as having that exact truncation bug without a matching reproduction.
- **Shiki template-call OOM fix:** [e2c25aa019](https://github.com/openchamber/openchamber/commit/e2c25aa019) addresses upstream's Markdown Shiki worker. DevRyan's Markdown renderer uses Prism; its Pierre diff worker does use Shiki. Evaluate diff-worker resilience independently, but do not copy a patch for a Markdown worker DevRyan does not have.
- **Optional UI extras:** batch project add, context-tab close menus, tool-header quick-open, session tabs and additional shortcuts are worthwhile small product choices. They rank below the first-pass chat/performance fixes; preserve existing DevRyan navigation and editable-field shortcut exclusions.
- **Provider-specific integrations:** Hyper/exe.dev quota support and Linear integration depend on actual use. They are not universal performance improvements. Likewise, upstream custom-provider metadata preservation deserves a targeted round-trip test if that editor is adopted, rather than transplanting upstream provider configuration code over DevRyan's provider adapters.
- **Upstream-only product direction:** extension work and new legacy-Tauri features are outside DevRyan's supported scope. Blanket SDK/dependency upgrades, removal of plugin integrations, private-relay changes and automatic worktree moves should not accompany this adoption pass.

## Suggested implementation sequence and acceptance

1. **First pass: ranks 1–6.** Small, evidence-backed corrections. Measure composer commits under streaming; exercise oversized LF/CRLF/emoji diffs; preserve Markdown copy whitespace; keep question context visible in sorted mode; bound disposable shell probes; preserve dirty files and stale-read fencing.
2. **Output and input polish: ranks 7–13.** Verify settings races, wide/narrow tables, huge JSON, keyboard/mobile behavior, bundle boundaries, large-paste restoration and unknown telemetry. Prefer independently reviewable changes.
3. **Reliability and rendering experiments: ranks 14–20.** Queue context round trips before server dispatch; synthetic renderer crashes in an isolated Electron fixture; compare long-answer parsing and session-switch costs before/after. Keep rollback paths for rendering/scroll changes.
4. **Separate designs: ranks 21–25.** Specify ownership, recovery and cross-host contracts before implementation. Do not combine repository/worktree mutations, queue ownership and renderer replacements in one change.

Use [performance guidance](../AGENT_PERFORMANCE.md) and the repository's [testing policy](../TESTING.md). Package behavior changes need affected validation; sync/server/shared-contract changes need full validation. Bundling changes additionally need build and bundle checks. Scroll, clipboard and renderer recovery require isolated runtime/visual checks. Use representative small and large sessions, active tool output, background sessions, narrow widths and user scroll release. Report measured p50/p95, long tasks, commits and retained heap only after actually collecting them.

This review changes documentation only. No application test run, live session inspection, renderer crash test or performance benchmark is implied by these recommendations.
