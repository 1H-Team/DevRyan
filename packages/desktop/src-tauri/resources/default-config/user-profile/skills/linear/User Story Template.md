\f0\fs24 \cf0 # User Story Template and Examples\
\
User stories are often expressed in a simple sentence, structured as follows:\
\
> \'93As a [persona], I [want to], [so that].\'94\
\
## Breaking This Down\
\
### "As a [persona]"\
Who are we building this for?\
\
We\'92re not just after a job title \'97 we\'92re after the persona of the person. Max. Our team should have a shared understanding of who Max is. We\'92ve hopefully interviewed plenty of Max\'92s. We understand how that person works, how they think, and what they feel. We have empathy for Max.\
\
### "Wants to"\
Here we\'92re describing their intent \'97 not the features they use.\
\
What is it they\'92re actually trying to achieve? This statement should be implementation-free. If you\'92re describing any part of the UI and not what the user goal is, you're missing the point.\
\
### "So that"\
How does their immediate desire to do something fit into their bigger picture?\
\
What\'92s the overall benefit they\'92re trying to achieve? What is the big problem that needs solving?\
\

\
# User Story Examples\
\
- As Max, I want to invite my friends, so we can enjoy this service together.\
\
- As Sascha, I want to organize my work, so I can feel more in control.\
\
- As a manager, I want to be able to understand my colleagues' progress, so I can better report our success and failures.\
\
---\
\
This structure is not required, but it is helpful for defining done. When that persona can capture their desired value, then the story is complete.\
\
We encourage teams to define their own structure, and then to stick to it.\
\
---\
\
# Considerations When Writing User Stories\
\
## Definition of Done\
The story is generally \'93done\'94 when the user can complete the outlined task, but make sure to define what that is.\
\
## Outline Subtasks or Tasks\
Decide which specific steps need to be completed and who is responsible for each of them.\
\
## User Personas\
For whom?\
\
If there are multiple end users, consider making multiple stories.\
\
## Ordered Steps\
Write a story for each step in a larger process.\
\
## Listen to Feedback\
Talk to your users and capture the problem or need in their words. No need to guess at stories when you can source them from your customers.\
\
## Time\
Time is a touchy subject. Many development teams avoid discussions of time altogether, relying instead on their estimation frameworks.\
\
Since stories should be completable in one sprint, stories that might take weeks or months to complete should be broken up into smaller stories or should be considered their own epic.\
\
---\
\
Once the user stories are clearly defined, make sure they are visible for the entire team.}
