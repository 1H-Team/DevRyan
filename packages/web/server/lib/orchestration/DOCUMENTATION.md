# Web Managed Orchestration

## Purpose

This module owns the single DevRyan-managed scheduler for the web server process. Electron inherits the same owner because it starts this web server in-process. Provider-native task events do not enter this module and are never counted or cancelled here.

## Ownership and startup

`runtime.js` composes the shared `@openchamber/orchestration-runtime` scheduler with the web OpenCode transport, atomic ledger, synthetic-event publisher, and private tool host. `lifecycle.js` asks the runtime for bridge environment immediately before spawning managed OpenCode. Only `DEVRYAN_ORCHESTRATION_URL` and `DEVRYAN_ORCHESTRATION_TOKEN` are injected; configured external OpenCode runtimes keep managed orchestration unavailable.

The private host binds `127.0.0.1:0`, requires a random bearer token, caps JSON input, exposes only `/rpc`, and is stopped before provider runtimes during graceful shutdown. URL/token values are never returned by diagnostics, UI routes, events, or routine logs.

## Persistence and recovery

`atomic-ledger.js` writes `OPENCHAMBER_DATA_DIR/orchestration/ledger.json` through a private mode-0600 temp file, file sync, atomic rename, and best-effort directory sync. Saves are serialized. Pre-barrier tasks missing `dispatchGroupId` hydrate to `null`; invalid JSON, oversized input, duplicate identity, and task/result contradictions are moved to a timestamped `.corrupt-*` file before the scheduler starts from an explicit empty state. Only the recovery warning, never ledger content or quarantine path, reaches the UI snapshot.

The shared executor records a child session before sending one queue-time provider/model/agent/variant snapshot. Web transport routes normal providers to managed OpenCode and Cursor to the existing Cursor SDK owner. Scheduler checkpoints confirm that the launch still owns its durable lease before prompting and after provider acceptance; a stale fresh child is aborted and deleted through OpenCode, with Cursor state cleaned through its SDK owner as well. Provider `busy` and transient `retry` status remains live, while definite usage/quota exhaustion, including an exhausted provider session allowance, settles as an immediately user-recoverable failure and starts bounded retry-loop cleanup. Transient status/message polling failures retry against the same child while retaining the last successful preview and references. Non-retryable observation failures become resumable interruptions instead of provider failures. The same shared prompt-tool policy used by the UI is applied to managed children, including both OpenCode names for Copilot's optional Resend MCP namespace. Restart reconciliation observes existing children and never blindly replays prompts.

## Contracts

- Private tool RPC methods: `submit`, `status`, `wait`, `barrier`, `barrier_status`, `handoff`, `cancel`, `snapshot`, and `acknowledge`. `wait` accepts an optional positive-safe-integer `waitTimeoutMs`, clamps it to 25 seconds, and forwards that polling slice without changing the task's execution deadline; omission preserves the legacy unbounded terminal wait. `barrier` is root-scoped, abortable, and remains unbounded while it waits for grouped children to become terminal before reporting result IDs that still need disposition. `barrier_status` is the non-blocking plugin gate, while `handoff` inspects or confirms the Orchestrator-to-Builder cleanup under a temporary root lock.
- Authenticated UI routes: `GET /api/orchestration/snapshot`, `GET /api/orchestration/task/:taskId`, `POST /api/orchestration/task/:taskId/cancel`, `POST /api/orchestration/task/:taskId/acknowledge`, and `POST /api/orchestration/handoff`. The handoff route is inspection-first, requires an idempotency key for confirmed cleanup, returns valid operation states with HTTP 200, and exposes only safe task projections and generic per-task cleanup failures. Confirmed cleanup never abandons active work unless provider abort is authoritatively confirmed; rejection, timeout, and an explicitly declined abort remain blocked and retryable. Grouped Orchestrator tasks allow one agent `retry`, `resume`, or `recover_in_place`; a later agent recovery returns `managed_retry_limit_reached` with HTTP 409 without acknowledging the failed envelope. Automatic `recover_in_place` requires a provider usage-limit result and reuses its canonical child with an authoritative replacement model. A user `retry_in_place` acknowledgement remains exempt. VS Code applies the same conflict mapping.
- Events: safe `openchamber:managed-task` projections omit prompt, idempotency key, private dispatch group, and lease token while exposing `agentRetryAvailable` for the one remaining grouped agent recovery and derived `failureKind` for provider-limit UI. Definite usage/quota exhaustion, including an exhausted provider session allowance, keeps that flag available on the initial attempt so the Orchestrator can automatically recover the same child; manual recovery appears only if that managed recovery also fails. Identity-only `openchamber:managed-task-removed` events mirror durable compaction so connected UIs release history immediately.
- Packaged OpenCode surface: one `devryan_task` tool multiplexes start/status/wait/cancel/continue/retry/resume/recover-in-place/abandon to minimize provider tool-count pressure. Every tool-driven wait requests a 25-second polling slice; live `queued`, `starting`, or `running` snapshots are not collected results and must be waited again immediately, without being narrated as a timeout or failure. Start timeouts are constrained to 1,800–86,400 seconds and web/Electron clamps every ordinary model-directed attempt to at least 30 minutes; packaged guidance uses at least 60 minutes for multi-file implementation plus tests and two hours when builds or browser verification belong to the same child. Recovery-in-place ignores model-supplied overrides, resolves the invoking Orchestrator message's authoritative provider/model/variant, and never overwrites it with the specialist's configured model. For preserved older Orchestrator prompts, a collected provider-limit `resume` is translated to this recovery action; ordinary timeout/interruption resume behavior is unchanged. Retry, resume, and in-place follow-ups receive a fresh 30-minute deadline when omitted by the caller. A hard timeout preserves its deadline cause, bounds and cancels the provider abort request, logs cleanup failure separately, and leaves an existing canonical child resumable when immediate recovery cannot read it. Council submits carry a private deadline class that keeps the separate three-minute councillor limit. When the runtime agent catalog is available, its configured provider/model/variant is authoritative for starts and agent-targeted retries; model-supplied IDs cannot bypass Settings. Explicit provider/model input remains only as a compatibility fallback when no catalog is available.
- Parent-model tool serialization keeps terminal task identity and lifecycle metadata but removes `recoverablePreview`, `failureReason`, and `canonicalRefs` from the task copy when they exactly match the result envelope. The complete envelope remains authoritative for acknowledgement and recovery. Divergent fields are retained fail-safely, and scheduler, ledger, private RPC, UI event, and snapshot shapes are unchanged. Because the bundled plugin is provisioned into managed web/Electron and VS Code runtimes, this context reduction is shared across providers and shells.

The packaged orchestrator alone receives `devryan_task`. Builder, Council, Plan, and specialists explicitly deny it. Orchestrator starts carry the parent assistant message as a private dispatch group. The plugin's `tool.execute.before` gate permits `skill` alongside `devryan_task`, `todowrite`, and `todoread` until the scheduler barrier clears; synchronous pending-start registration prevents a start and work tool emitted in one assistant response from racing. A registration normally settles in the start tool's `finally`; if a later OpenCode pre-execution hook aborts the call before DevRyan's tool runs, the plugin settles the orphan only when OpenCode emits the authoritative `session.idle` lifecycle event. The invoking assistant's agent is resolved from the authoritative message/tool-call record through a bounded cache. Known Orchestrator ownership remains gated, Builder direct tools bypass stale Orchestrator barriers without receiving graph mutation access, and unknown ownership under a locked barrier fails closed. Every result must be collected through `wait` before disposition, and successful results require `continue`. A known local or recovered barrier fails closed if its private bridge cannot be verified, while direct work remains available when no managed dispatch has ever been found. The orchestrator may consume partial managed output and perform at most one managed recovery when resumable; a provider-limit recovery continues the same canonical child with the Orchestrator model, while retry is reserved for an intentional new child and resume only observes. After that it continues directly within scope or reports a genuine blocker. Provider-native `task` is never an automatic managed-failure fallback and remains available only for an explicit current-user request. Council's locally owned fanout stays ungrouped while using the private RPC when present, so all of its parallel children receive the same durable lifecycle and immediate admission without entering the primary-agent barrier. Without bridge environment, Council retains its existing direct behavior for external compatibility, and its separate three-minute councillor timeout is unchanged.

Managed OpenCode launches intentionally omit `--pure` and do not set `OPENCODE_DISABLE_DEFAULT_PLUGINS`: either switch suppresses the bundled managed tool itself. The generated runtime overlay remains the plugin allowlist owner, while prompt-scoped provider rules bound only the reproduced provider-specific tool surface.

## Testing

Run the module files under `packages/web/server/lib/orchestration/*.test.js`, the packaged managed-tool and Council plugin tests, the OpenCode lifecycle/shutdown tests, and `bun test packages/orchestration-runtime`. Runtime tests cover immediate one/three/five admission without a concurrency cap, root/barrier scope, inspection and confirmed handoff cleanup, idempotent retries, grouped retry-limit conflicts, manual retry-in-place exemption, partial failure, 30-minute start/follow-up deadlines, safe projection, legacy hydration, corrupt-ledger quarantine, atomic overlapping saves, bearer/body rejection, normal/Cursor transports, same-turn plugin races, idle recovery for starts abandoned between pre-hook and execution, authoritative agent gating, fail-closed unknown ownership, external-runtime unavailability, and deterministic cleanup.
