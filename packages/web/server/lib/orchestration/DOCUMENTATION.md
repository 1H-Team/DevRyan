# Web Managed Orchestration

## Purpose

This module owns the single DevRyan-managed scheduler for the web server process. Electron inherits the same owner because it starts this web server in-process. Provider-native task events do not enter this module and are never counted or cancelled here.

## Ownership and startup

`runtime.js` composes the shared `@openchamber/orchestration-runtime` scheduler with the web OpenCode transport, atomic ledger, synthetic-event publisher, and private tool host. `lifecycle.js` asks the runtime for bridge environment immediately before spawning managed OpenCode. The runtime must acquire the ledger's cross-process owner lease before it starts the private bridge or initializes recovery, so two web/Electron processes cannot manage the same data directory. A competing live owner fails closed with `managed_orchestration_owner_conflict`; snapshots remain empty and surface a sanitized warning without running scheduler recovery. OpenCode spawn continues without injecting the private bridge, so a leftover or competing owner cannot brick the rest of the app. Only `DEVRYAN_ORCHESTRATION_URL`, `DEVRYAN_ORCHESTRATION_TOKEN`, and the fixed capability marker `DEVRYAN_ORCHESTRATION_ACCOUNT_DEFAULTS=1` are injected; configured external OpenCode runtimes keep managed orchestration unavailable.

The private host binds `127.0.0.1:0`, requires a random bearer token, caps JSON input, exposes only `/rpc`, and is stopped before provider runtimes during graceful shutdown. URL/token values are never returned by diagnostics, UI routes, events, or routine logs.

Private task-result RPCs accept `resultMode: "eager" | "reference"`; omission is eager for UI routes, Council, older plugins, and compatibility callers. Reference mode lazifies only a matching retained preview above 8,192 UTF-8 bytes and exposes the first page beside the existing wrapper. `read_result` requires exact task/root/directory scope plus the opaque `resultCursor`, performs no scheduler mutation, and returns only the next `resultReference`. Malformed cursors use `invalid_result_cursor` (400), retained identity/payload changes use `result_reference_mismatch` (409), and existing scope/result 403/404 errors remain authoritative. Snapshots and UI routes remain eager.

## Persistence and recovery

Managed OpenCode retry status preserves optional structured action metadata. The shared executor treats the exact `action.reason: free_tier_limit` signal as immediate provider exhaustion, falls back to normalized usage-limit message wording for compatibility, and never waits for the provider's multi-hour `next` timestamp before exposing Model Recovery.

`atomic-ledger.js` writes `OPENCHAMBER_DATA_DIR/orchestration/ledger.json` through a private mode-0600 temp file, file sync, atomic rename, and best-effort directory sync. Saves are serialized and every load, save, and quarantine verifies the immutable owner token in `orchestration/owner.lock`. The lock is created with an atomic hard-link claim, heartbeats through file timestamps, and is released only after exact-token verification. A lock whose recorded process is confirmed dead is recovered immediately, even when its heartbeat is still fresh. A live owner is never stolen, including when the heartbeat looks stale. Unreadable locks are never stolen automatically. Shutdown drops the lock before waiting for an in-flight ledger save, and a process-exit handler unlinks the file only when this runtime still holds the matching token. Losing the token fences the former owner before further ledger access. Pre-barrier tasks missing `dispatchGroupId` and tasks predating exact dispatch correlation missing `dispatchCallId` hydrate to `null`; tasks predating plan-mode propagation hydrate with `readOnly: false`. Invalid JSON, oversized input, duplicate identity, and task/result contradictions are moved to a timestamped `.corrupt-*` file before the scheduler starts from an explicit empty state. Runtime diagnostics expose only sanitized ownership state, while the UI snapshot receives only a safe warning; ledger content, owner PID/token, and quarantine paths remain private.

The shared executor records a child session before sending one queue-time provider/model/agent/variant snapshot. Web transport routes normal providers to managed OpenCode and Cursor to the existing Cursor SDK owner. Scheduler checkpoints confirm that the launch still owns its durable lease before prompting and after provider acceptance; a stale fresh child is aborted and deleted through OpenCode, with Cursor state cleaned through its SDK owner as well. Provider `busy` and transient `retry` status remains live, while definite usage/quota exhaustion, including an exhausted provider session allowance, settles as an immediately user-recoverable failure and starts bounded retry-loop cleanup. Transient status/message polling failures retry against the same child while retaining the last successful preview and references. A terminal assistant request, response-header, stream-idle, or connection transport failure receives one idempotent fixed continuation in the same child with the captured execution snapshot, without replaying the original task; restart reconciliation preserves the first failure for that recovery and a repeated transport failure settles normally. A managed `resume` observes a still-live canonical child or sends one transcript-marked continuation when it is already terminal; restart reconciliation relaunches only a missing continuation and never duplicates a recorded one. A temporary managed-port transition is typed as HTTP-style 503 unavailability; restart reconciliation keeps the task active and retries the same canonical child under its existing lease and deadline instead of emitting an interruption or replaying the prompt. Non-retryable observation failures become resumable interruptions instead of provider failures. The same shared prompt-tool policy used by the UI is applied to managed children, including both OpenCode names for Copilot's optional Resend MCP namespace. Every OpenCode-backed managed child prompt explicitly disables provider-native `task`, including initial execution and ordinary retry, resume, manual same-child model recovery, restart, and automatic continuations, so delegation remains root-owned even when an agent definition or task record is writable. A plan-mode parent turn additionally marks the private task read-only before admission and disables every mutation surface on each prompt. Cursor read-only managed dispatch fails before child creation because its SDK cannot enforce the required per-prompt tool policy.

Normal-provider status reads are single-flighted only while pending, using the exact fully resolved status URL as the per-executor key. Overlapping observers of the same port and normalized directory share one parsed status map without mutation; directory or port changes and every post-settlement poll create a new request. Cursor status never enters this path.

Plan-safe starts resolve the parent turn before provider selection. Designer is implementation-only, so the provisioned plugin rejects it from a read-only parent with `MANAGED_READ_ONLY_AGENT_UNSUPPORTED` before provider resolution or RPC. Both host owners and the shared scheduler repeat that guard before persistence, including recovery agent overrides, and the executor fails closed before child creation or same-child prompting. Other read-only specialists configured for Cursor preserve their agent identity and prompt while using the active non-Cursor parent execution first or the configured non-Cursor Plan-agent execution second. If neither execution is available, the plugin rejects with `MANAGED_READ_ONLY_PROVIDER_UNSUPPORTED`.

Every managed child start privately resolves the requested agent against the
root session's durable owner before plan-safe provider checks. Admission repeats
that resolution before persistence. Precedence is the owner's personal
single-model default, then the live host agent configuration; administrators
inherit the host directly. Retry/resume agent changes are re-resolved. An
already selected plan-safe fallback remains authoritative for that read-only
attempt, while explicit same-child Model Recovery choices are never replaced
or persisted. Council bypasses the account overlay and retains its shared host
roster. Missing ownership or assignment evidence fails closed instead of
guessing from the current browser.

## Contracts

- Private tool RPC methods: `resolve_agent_execution`, `submit`, `status`, `wait`, `read_result`, `wait_result_action`, `list_provider_recovery_continuations`, `barrier`, `barrier_status`, `handoff`, `cancel`, `snapshot`, and `acknowledge`. `resolve_agent_execution` is owner/directory scoped and returns only provider/model/variant plus safe source metadata. `wait` accepts an optional positive-safe-integer `waitTimeoutMs`, clamps it to 25 seconds, and forwards that polling slice without changing the task's execution deadline; omission preserves the legacy unbounded terminal wait. `read_result` returns a stateless page from the retained immutable preview and never acknowledges or mutates the task. `wait_result_action` remains a task/root/directory-scoped compatibility primitive that can observe a durable UI acknowledgement, but ordinary model-facing waits do not call it. `list_provider_recovery_continuations` retains its compatibility name and is private-host-only; it reports unacknowledged terminal grouped results as collectable `collect` entries. Parked Model Recovery results are omitted so the plugin cannot wake the parent to narrate or collect them; the envelope stays unacknowledged for the UI recovery card. It exposes only the identity fields needed by the packaged plugin. `barrier` is root-scoped, abortable, and remains unbounded while it waits for grouped children to become terminal before reporting result IDs that still need disposition. `barrier_status` is the non-blocking plugin gate, while `handoff` inspects or confirms the Orchestrator-to-Builder cleanup under a temporary root lock.
- Authenticated UI routes: `GET /api/orchestration/snapshot`, `GET /api/orchestration/task/:taskId`, `POST /api/orchestration/task/:taskId/cancel`, `POST /api/orchestration/task/:taskId/acknowledge`, and `POST /api/orchestration/handoff`. The handoff route is inspection-first, requires an idempotency key for confirmed cleanup, returns valid operation states with HTTP 200, and exposes only safe task projections and generic per-task cleanup failures. Confirmed cleanup never abandons active work unless provider abort is authoritatively confirmed; rejection, timeout, and an explicitly declined abort remain blocked and retryable. Grouped Orchestrator tasks allow one ordinary agent `retry` or `resume`; a resumable failure after that attempt, like a first provider-limit failure, rejects every ordinary agent disposition with `manual_model_recovery_required` and HTTP 409 without acknowledging the envelope. A separately confirmed handoff may abandon that parked result through the scheduler's private cleanup capability so Builder can take ownership without weakening normal Model Recovery. A `provider_prompt_rejected` result instead rejects every same-child recovery and requires its single `retry` to provide a different prompt for a fresh child; a second rejection remains dispositionable but cannot create attempt 3. Only UI `retry_in_place` may acknowledge ordinary manual recovery, with an explicit provider/model/variant selection, and it reuses the canonical child. Non-resumable extra retry/resume attempts retain `managed_retry_limit_reached`. New `recover_in_place` acknowledgements are rejected while historical records remain readable. Web/Electron and VS Code map both prompt-rejection policy errors to HTTP 409.
- Events: safe `openchamber:managed-task` projections omit prompt, idempotency key, the private dispatch-group value, private read-only policy, and lease token while retaining the originating `dispatchCallId`, a non-secret `dispatchGrouped` policy boolean, live-policy `agentRetryAvailable`, and derived `failureKind`. Definite usage, session, quota, or rate-limit exhaustion projects the flag as false on the initial terminal attempt. Verified prompt rejection projects `provider_prompt_rejected`; scheduler-owned timeouts project `deadline_exceeded`. Identity-only `openchamber:managed-task-removed` events mirror durable compaction so connected UIs release history immediately.
- Packaged OpenCode surface: one `devryan_task` tool multiplexes start/status/wait/cancel/continue/retry/resume/abandon to minimize provider tool-count pressure. On start its pre-execution hook captures the exact OpenCode `callID`, keeps parallel calls isolated even when execution order differs, and submits it as `dispatchCallId`; the scheduler projection can therefore replace a still-pending tool row even if the terminal tool-part update is missed. It also resolves the invoking assistant message and its exact parent user record; a synthetic plan-mode marker or authoritative plan metadata sets the private `readOnly` submit field, while an available message API that cannot resolve the parent fails closed. Every ordinary tool-driven wait stays attached while the plugin repeats 25-second private polling slices; live snapshots remain internal and only a terminal result returns to the parent model. A result requiring manual model recovery returns immediately with `manualRecoveryRequired: true` and remains unacknowledged while the UI presents Model Recovery. Parked results do not send a parent notice if a wait detaches; idle scans wake only collectable recovered work. Immediately before a synthetic wake, the plugin re-reads the candidate and skips it if its envelope was acknowledged or its task was compacted. After the user selects a model and thinking level, the durable `retry_in_place` lineage runs in the same child; once it settles, the plugin double-checks that the root is idle and sends one marker-bearing synthetic continuation using the root's latest authoritative execution. Child idle/error edges start a bounded trailing-scan window so the observer and durable terminal commit cannot lose either notification; overlapping triggers coalesce without becoming a permanent poller. Start timeouts are constrained to 1,800–86,400 seconds and web/Electron and VS Code clamp Designer, Fixer, and Oracle attempts to at least 60 minutes while other ordinary specialists retain the 30-minute floor. Recovery attempts inherit at least the source task's original window; `timeout_seconds` on retry/resume may extend it but cannot reduce the agent floor. A hard timeout preserves its deadline cause, bounds provider-abort cleanup, and leaves an existing canonical child resumable when immediate recovery cannot read it. Council retains its private three-minute deadline. Runtime agent-catalog provider/model/variant choices remain authoritative over model-supplied IDs.
- Parent-model tool serialization keeps terminal task identity and lifecycle metadata but removes `recoverablePreview`, `failureReason`, and `canonicalRefs` from the task copy when they exactly match the result envelope. The complete envelope remains authoritative for acknowledgement and recovery. Divergent fields are retained fail-safely; `dispatchCallId` is the only additive task-correlation field in the scheduler, ledger, private RPC, UI event, and snapshot shapes. Because the bundled plugin is provisioned into managed web/Electron and VS Code runtimes, this context reduction and correlation contract are shared across providers and shells.

The packaged orchestrator alone receives `devryan_task`. Builder, Council, Plan, and specialists explicitly deny it. Packaged Orchestrator sessions are managed-only: their prompt tool overlay sends `task: false`, their agent permission unconditionally denies provider-native `task`, and the managed plugin rejects any stray native-task execution before child creation or scheduler mutation. Project-defined non-Orchestrator agents retain their existing native-task contracts. Orchestrator starts carry the parent assistant message as a private dispatch group. The plugin's `tool.execute.before` gate permits `skill` alongside `devryan_task`, `todowrite`, and `todoread` until the scheduler barrier clears; synchronous pending-start registration prevents a start and work tool emitted in one assistant response from racing. A registration normally settles in the start tool's `finally`; if a later OpenCode pre-execution hook aborts the call before DevRyan's tool runs, the plugin settles the orphan only when OpenCode emits the authoritative `session.idle` lifecycle event. Known Orchestrator ownership remains gated, Builder direct tools bypass stale Orchestrator barriers without receiving graph mutation access, and unknown ownership under a locked barrier fails closed. Every result must be collected through `wait` before disposition, and successful results require `continue`. A known local or recovered barrier fails closed if its private bridge cannot be verified, while direct work remains available when no managed dispatch has ever been found. The orchestrator may consume partial managed output and perform at most one ordinary managed retry or resume when resumable. A provider-limit result or a resumable failure after that agent recovery leaves the barrier awaiting user acknowledgement and returns `manualRecoveryRequired` to the parent; the parent cannot discard it with `abandon` or truthfully report it as still running. The UI asks the user to select a model/thinking level and click Try Again; the recovered same-child terminal result then wakes the idle root exactly once for normal collection and disposition. Council's locally owned fanout stays ungrouped while using the private RPC when present, so all of its parallel children receive the same durable lifecycle and immediate admission without entering the primary-agent barrier. Without bridge environment, Council retains its existing direct behavior for external compatibility, and its separate three-minute councillor timeout is unchanged.

The packaged plugin adds `read_result` to that model-facing surface. Unset `DEVRYAN_MANAGED_RESULT_MODE` selects reference mode for `submit`, `status`, `wait`, `cancel`, and `acknowledge`; exact `eager` omits the parameter and preserves the previous eager serialization. The override is read when the plugin starts, so operators must restart managed OpenCode after changing it, and the override remains supported for at least one release. A terminal wait registers only its expected next cursor in process memory. Each `read_result` must match exactly, advances only after a valid page, never acknowledges the envelope, and leaves the collected result available for normal disposition. Reads before a terminal wait, repeated/reordered cursors, and reads after completion fail with `DEVRYAN_TOOL_INPUT_INVALID`; after plugin restart, another wait recreates the ephemeral cursor state from the retained terminal result. Internal recovery scans do not request reference mode.

If `status`, `wait`, or acknowledgement encounters `task_not_found`, the plugin reads both the root-scoped `snapshot` and `barrier_status`. Only an available, bridge-ready snapshot with no recovery warning and a well-formed clear barrier produces `state: "stale_task_reference"`, `dispositionRequired: false`, and a direction to continue from confirmed parent state without recreating the child. A retained terminal envelope whose action is already set produces `state: "already_dispositioned"` after restart and reports the current barrier rather than requiring a second acknowledgement. Active or unacknowledged tasks remain blocking and identify their current task IDs; unavailable ownership, warnings, bridge failures, and malformed responses preserve fail-closed `task_not_found` behavior. Successful `continue`, `retry`, `resume`, and `abandon` calls remove their local collected-result cache entries.

Managed OpenCode launches intentionally omit `--pure` and do not set `OPENCODE_DISABLE_DEFAULT_PLUGINS`: either switch suppresses the bundled managed tool itself. The generated runtime overlay remains the plugin allowlist owner, while prompt-scoped provider rules bound only the reproduced provider-specific tool surface.

During context-mode fallback recovery, both web/Electron and VS Code apply the
same named admission hold before OpenCode accepts more work. New `submit` and
work-launching result actions (`retry`, `resume`, `retry_in_place`, and
`recover_in_place`) return HTTP 503 with `CONTEXT_MODE_RECOVERY_PENDING` and
`Retry-After: 1`; status, wait, cancellation, successful-result `continue`,
abandonment, and shutdown remain available so active work can drain. A
successfully completed result supplied with any action other than `continue`
returns `DEVRYAN_TOOL_INPUT_INVALID` together with the completed state and the
exact required next action. `retry` remains reserved for eligible failed
results.

## Testing

Run the module files under `packages/web/server/lib/orchestration/*.test.js`, the packaged managed-tool and Council plugin tests, the OpenCode lifecycle/shutdown tests, and `bun test packages/orchestration-runtime`. Runtime tests cover immediate one/three/five admission without a concurrency cap, root/barrier scope, result-action waiting and recovered lineage delivery, inspection and confirmed handoff cleanup, idempotent retries, grouped retry-limit conflicts, manual retry-in-place exemption, partial failure, bounded same-child transport continuation, ordinary 30-minute and Designer/Fixer/Oracle 60-minute start/follow-up deadlines, safe projection, legacy hydration, corrupt-ledger quarantine, atomic overlapping saves, exclusive two-process ownership, dead-process owner recovery, lost-token fencing, process-exit lock release, second-runtime recovery suppression, bearer/body rejection, normal/Cursor transports, same-turn plugin races, idle recovery for starts abandoned between pre-hook and execution, authoritative agent gating, fail-closed unknown ownership, external-runtime unavailability, and deterministic cleanup.
