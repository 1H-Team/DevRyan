# packages/native

The product's Cargo workspace. It pins Rust in `rust-toolchain.toml`, tracks `Cargo.lock`, and has five crates: `crates/front` ([devryan-front](#devryan-front)), `crates/config-text` ([devryan-config-text](#devryan-config-text)), `crates/route-magic-prompts` ([devryan-route-magic-prompts](#devryan-route-magic-prompts)), and `crates/client-engine` with `crates/client-engine-runner` ([devryan-client-engine](#devryan-client-engine-and-its-runner)). Nothing here ships in the app, and nothing in the product starts or calls it.

## devryan-front

`devryan-front` is a loopback pass-through front for `devryan serve`. **It is off by default and not shipped. Only tests and QA lanes use it.** It does two things:

1. **Pass-through.** It listens on a loopback port and forwards every connection to the JavaScript server on another loopback port. It adds, removes and rewrites nothing.
2. **Supervision.** With `--spawn` it starts the server as a child in its own process group, with an environment taken only from a file, and waits for health. It stops the child cleanly, and it makes sure the child goes away if the front dies for any reason.

This is part of row B1 of the refactor plan: the pass-through and the supervision. It does not yet run the startup contract or the QA isolated host through the front, and it does not shadow-compare reads.

Recording and comparing traffic is not in this package. It will be a separate package with its own design. Its recordings will be verification-time files that are made and compared within one run and never leave that run's scratch folder. The earlier attempt is not in the tree.

### Loopback only, and why

The front binds and connects only to `127.0.0.0/8` or `::1`. It refuses any other `--listen` or `--upstream` address, and `--listen` takes port 0 only (a fixed loopback port can bind beside a wildcard socket on the same port and shadow it; the bound address is printed). Five checks in the server read the socket's remote address (research file 25, section 6, which also listed the since-removed `runtime-service/routes.js`: `security/direct-local-request.js`, `multi-user/runtime.js`, `preview/proxy-runtime.js`, `browser-cdp/discovery-runtime.js`, `browser-cdp/lease-runtime.js`). Behind any front, every request reaches the server from 127.0.0.1 and looks local. For a loopback-bound server, whose peers are local anyway, that classification does not change, because the front keeps `Host`, `Origin` and every other header as sent and adds no forwarding header. For a LAN-bound server it would turn a remote peer into the local owner. That is why the front must never face a network, and why it is used only by tests and QA lanes for now.

### How transparency is guaranteed

Each client connection gets its own upstream connection, opened when the client connects and closed when it closes. Each direction is a plain copy loop: bytes are written on as soon as they arrive. Nothing is parsed in order to forward, so nothing can be added, removed, rewritten, merged or reordered, and the front cannot disagree with the server about where a message ends. This holds for request and response heads, fixed, chunked and close-delimited bodies, interim responses, pipelined requests, upgrades and WebSocket frames, and for heads a parser would reject or read two ways (an obsolete folded header, a head over 2 MiB, `Content-Length` beside `Transfer-Encoding`, two `Content-Length` headers that disagree, bare LF line ends). An orderly end is passed on as a half-close and a reset as a reset. A refused upstream connection becomes a reset of the client's connection with no bytes (the client's `connect()` itself succeeds, because the front accepted it). `crates/front/tests/transparency.rs` runs each case directly and through the front, and requires identical bytes on both sides of both runs.

A connection holds two descriptors, one per socket, and two threads, one per direction; both directions and the stop list share each socket. At start `serve` raises its soft limit on open files the way Node does: to the hard limit, or to the highest value the kernel accepts (macOS starts processes from a terminal or launchd with a soft limit of 256 and caps it at `kern.maxfilesperproc`). Without that, two descriptors per connection would stop the front near 120 concurrent connections under that default. The child inherits the raised limit, as a child of Node inherits Node's. If the limit cannot be raised, `serve` prints `open-file-limit-not-raised` on stderr and goes on. When `accept` fails for lack of descriptors, the connection waits in the listen backlog and `serve` prints `accept-failed` on stderr, at most once a second. `transparency.rs` holds 300 connections open at once through the binary started with a soft limit of 256.

### Commands

```
devryan-front serve --listen 127.0.0.1:0 --upstream 127.0.0.1:<port>
devryan-front serve --listen 127.0.0.1:0 --spawn --child-env-file <json> [--child-cwd <dir>] [--child-log <file>]
                    [--health-path /api/health] [--ready-field isOpenCodeReady] [--ready-timeout-ms N] [--stop-grace-ms N]
                    -- <program> <args with {port}>...
```

`serve` refuses an option it does not take, so a misspelt option cannot silently turn something off, and `--child-env-file` fails on a value that is not a string. It prints one JSON object per line on stdout: `ready` (listen and upstream addresses, child and watchdog pids), `child-exited` (the child died; the front then stops), `watchdog-exited` (the watchdog died; the front stops the child, since a `kill -9` of the front would otherwise leave it), `connections-still-open` (a connection had not ended 10 s after the stop) and `stopped` (how the child ended and how many connections were accepted). SIGTERM or SIGINT once it is serving stops it cleanly (code 0). SIGTERM or SIGINT while it waits for the child's health stops the child and exits with code 2, because it never served. SIGHUP is not a stop signal: it ends the front at once, without a clean stop, and the watchdog then stops the child as after a `kill -9` (below). It never prints the child's environment. `watchdog` is the same binary's internal watchdog mode (below).

| Code | When |
|---|---|
| 0 | `serve` stopped cleanly on SIGTERM or SIGINT after its `ready` line |
| 2 | Refused: a bad or unknown option or command (all are read before the child starts), an address that is not loopback, a fixed listen port, a child that could not start, exited before it was healthy or was not healthy within `--ready-timeout-ms`, or SIGTERM or SIGINT before it was healthy (the child is stopped first) |
| 3 | `serve --spawn`: the child or its watchdog died |

`crates/front/tests/transparency.rs` checks the refusals and `crates/front/tests/supervision.rs` checks codes 0, 2 and 3.

### Supervision

`--spawn` starts `<program>` with `env_clear()` plus exactly the variables in `--child-env-file`, in a new process group, with stdin closed. `{port}` in the arguments is replaced by a free loopback port. The front waits until `GET <health-path>` answers 200 and, with `--ready-field`, until that JSON field is `true` (`crates/front/src/http.rs` reads the probe's response head and chunked body; nothing else parses HTTP). A stop sends SIGTERM to the group, then SIGKILL to anything left after `--stop-grace-ms` (default 20 s, because the server's own shutdown can take its full 10 s). When the child dies, its upstream connections end, the front passes that on to each client (an end or a reset), prints `child-exited`, stops accepting, ends the rest of the child's group and exits with code 3; it does not restart the child.

A watchdog process (the same binary, `watchdog`, in its own group) holds the read end of a pipe whose write end only the front holds. When the front dies, `kill -9` included, the kernel closes that pipe. The watchdog then checks that the group leader's whole command line (`ps -ww`) still holds the child's, sends SIGTERM to the group, and sends SIGKILL after the grace period. A clean stop releases the watchdog first. The server's own parent-death watchdogs end its OpenCode host when the server goes. The server is not changed.

`crates/front/tests/supervision.rs` runs the real binary with its own test executable as the child (a small HTTP server with a grandchild): a clean stop on SIGTERM leaves no child, grandchild or watchdog; a `kill -9` of the front leaves none; a child that dies is reported (`child-exited`, exit code 3) and its group goes; a child that never gets healthy is stopped and refused (code 2).

Known limits, left as they are:

- The free port is found before the child binds it, a race another process could win. The child then fails its health check and the front reports it. An `--upstream` port that another server already holds can answer the first health probe before the child fails to bind it; the child usually exits first and the front refuses with code 2.
- The watchdog stops the child's group only if the group leader's command line, as `ps -ww -o command=` shows it, still contains `<program's file name> <arguments>`. A child that replaces itself with another program, or rewrites its process title, no longer matches. The watchdog then touches nothing, so after a `kill -9` of the front, or a SIGHUP (which also ends the front without a clean stop), that child and its group keep running. Homebrew's `python3`, which re-executes `Python.app/Contents/MacOS/Python`, is such a child. The JavaScript server started as `node …/cli.js serve --foreground` or through `bun` is not affected: neither re-executes or rewrites its title, and after a `kill -9` of the front the watchdog stopped the child and its grandchild in under 6 s with either runtime. A clean stop (SIGTERM or SIGINT, or the child's own death) does not depend on the check.
- A stop signals the group by the leader's id after the leader was reaped, which is safe while the group has members.

### Real-server lane

`node scripts/qa/front-lane.mjs [--result <file>] [--keep-artifacts]` builds the front in release mode with the pinned toolchain, into its run's scratch folder, and prepares one private runtime-fixture profile (run root, HOME, XDG folders, TMPDIR, data directory and state root, with the loopback provider fixture, the way `scripts/qa/native-backend-ui-diagnostic.mjs` does), in its run's scratch folder under the OS temp dir. It starts `devryan serve --foreground` under `devryan-front serve --spawn`, with the front inside a private environment the test isolation guard creates for it (`createTestIsolation`). It then sends the same request bytes through the front and directly to the server (directly twice, interleaved):

- `GET /api/health`, a static asset from `packages/web/dist/assets`, and the owner enrolment page `GET /auth/local-owner-bootstrap`. Each must answer 2xx both ways with the same status line and header names. A response is deterministic when the two direct answers agree byte for byte apart from `Date`; then the front's answer must equal them. The asset is compared that way. The enrolment page is compared byte for byte with its per-response nonce and the hash part of its `ETag` masked; its 200 through the front also shows the server's direct-local check passing behind the front. The health body changes between calls, so it is compared by status and header names only.
- the SSE stream `GET /api/global/event`, through the front and directly: the same status and content type, and the same events up to `devryan.subscription-ready`.
- a WebSocket upgrade on `/api/global/event/ws` with a fixed key: the same `101` head byte for byte, the server's `ready` message, a client ping answered by a pong with the same payload, and a close answered by a close.

Last, with an SSE stream open through the front, it kills the child with SIGKILL and checks the behaviour above: `child-exited` with `signal 9`, the open stream ends, `stopped`, exit code 3, the listen port and the server's port refuse connections, the child and the watchdog are gone, and no process the front started is left within 10 s.

The lane records every process it starts, directly or not, while it runs: its descendants by pid and start time, and their process groups other than its own, read from the process table every 400 ms, so a process reparented after its parent died is still found. It ends the same way on success, failure, SIGINT, SIGTERM and SIGHUP: it stops the front (SIGTERM, which stops the server), a running build and the profile, then any recorded process or group still running (SIGTERM, then SIGKILL), and reports in its result what it had to stop and anything that survived. A process it had to stop after a completed run fails the run. It then removes everything it created: its run folder under the OS temp dir (`devryan-qa/front-lane-*`), the test isolation guard's root (`devryan-test/run-*`), and the runtime clone the profile preparation requires under the repository's `.cache` (`.cache/front-lane/<run>`, with the folders it had to create for it). A signal that arrives during that ending does not cut it short; if it is handled before the lane exits, the lane exits with 128 plus its number. On failure the result keeps the end of the server's log and the front's stderr, and both whole logs are kept outside the run folder, beside the result file (`<file>.server.log`, `<file>.front.log`), or without `--result` in `devryan-qa/front-lane-failed-logs-*` under the OS temp dir; the lane prints where. `--keep-artifacts` keeps the whole run folder instead. The build runs with the caller's environment (cargo reads its registry from there); git and the front run with the guard's.

A lane killed with SIGKILL cannot clean up, and nothing bounds what it leaves: the front keeps running and keeps the server running, and the two scratch folders and the runtime clone under `.cache/front-lane` (about 300 MB) stay. Stop the `devryan-front` process (its SIGTERM stops the server) and delete `.cache/front-lane` by hand; until then `validate` fails on the leftover folder. Sweeping stale runs at the next start, and a front that stops when its parent is gone, are left for the package that reworks this lane.

What it does not prove: that every route, body or stream is forwarded faithfully (the Rust tests carry that, on scripted peers), anything about a session, a prompt or the OpenCode host's channels, or the delay the front adds. It uses no credential and never touches the owner's app, data or ports. It is in no gate.

### Gates

- `node scripts/check-native.mjs` runs `cargo fetch --locked`, the licence check, `cargo fmt --all --check`, `cargo clippy --locked --offline --workspace --all-targets -- -D warnings` and `cargo test --locked --offline --workspace` with the pinned toolchain. Without that toolchain it fails with the command that installs it. `--deny` adds `cargo deny check licenses advisories sources` offline, against the advisory database already on the machine (cargo-deny 0.20.2, policy in `deny.toml`).
- `node scripts/check-native.mjs --advisories` runs only `cargo fetch --locked` and `cargo deny --locked check licenses advisories sources` with a freshly fetched RustSec database. It needs cargo-deny `CARGO_DENY_VERSION` (0.20.2): with `CARGO_DENY_ROOT=<dir>` it uses `<dir>/bin/cargo-deny` and installs it there with `cargo install cargo-deny --version 0.20.2 --locked --root <dir>` when it is missing; otherwise it must be on PATH. Advisories ignored on purpose are listed in `deny.toml`'s `[advisories] ignore`, each as `{ id = "RUSTSEC-…", reason = "…" }`; the contract refuses an entry without a reason.
- The licence check (`scripts/check-native-licenses.mjs`) needs nothing beyond cargo: it reads `cargo metadata --locked --format-version 1 --all-features` and fails on any package of the locked graph, the workspace's own included, whose SPDX expression the `[licenses] allow` list of `deny.toml` does not satisfy, or that has no expression. That list is the only policy; cargo-deny reads the same one.
- `bun run validate` runs that check, and the script tests that read this workspace, for any change under `packages/native/`, to `scripts/check-native.mjs` or to `scripts/check-native-licenses.mjs` (`scripts/validate.mjs`, `TREE_READERS` in `scripts/test-select.mjs`). A change only to Markdown here, this file included, runs the contract test without cargo.
- `scripts/check-native.test.mjs` is the contract and needs no Rust. It checks the pin (equal to the ledger core's), the check steps, the missing-toolchain message, exact `=x.y.z` dependency pins taken through the workspace, the tracked lockfile from crates.io only, the licence policy and the licence evaluator (with planted violations), CI's advisory steps, and that every crate is named below. It also holds the config-text vector contract (below): the tracked vectors must be what the generators write with the installed `jsonc-parser` and `yaml`, and every planted bug must still have its planting site. That part regenerates all five files in the test's own process: about 1.7 s of CPU (wall time 5.6 s at load average 37, 8 cores), most of it `yaml.parse` of the parse rows. The JavaScript half skips the second `parseDocument` unless a source holds `%` or `!`: the two refusals that pass reads (a `%YAML 1.1` directive, an explicit tag) need one of them.
- `scripts/toolchain-pins.test.mjs` requires every CI Rust install to be the ledger core's or this workspace's install command.
- CI's `static` job runs `node scripts/check-native.mjs`, licence check included, and then the advisory check, on every push, and on a pull request that changes this workspace, its check scripts or `ci.yml`. cargo-deny is built once with the pinned Rust into `~/.cache/devryan-cargo-deny` and kept by `actions/cache`, pinned to the commit of release v6.1.0, under a key that names the cargo-deny release and the Rust; a cache hit restores it in seconds. A new advisory fails the job. The contract (`scripts/check-native.test.mjs`) checks the steps, their order and condition, the pin, the key and the ignore list, so none of it can be dropped silently.
- The packaged app holds nothing from here: this folder is not a workspace package, and the packaging rules forbid Rust sources and Cargo files anywhere (`scripts/packaged-app.config.mjs`).

### Adding a crate that cannot build on Linux

The gate checks the whole workspace (`--workspace`) in CI's Ubuntu job, and the contract requires every member to take its dependencies from the workspace and every workspace dependency to be named below. A throwaway spike (`refactor/2026-11-native-spike`) keeps a different `packages/native/` with the same root files (`Cargo.toml`, `Cargo.lock`, `deny.toml`, `rust-toolchain.toml`, `.gitignore`) and macOS-only GPUI crates. Recorded decision: such a crate joins this workspace without breaking the gate this way:

1. The gate names the crates it checks. `scripts/check-native.mjs` gains a list of members per platform (for example `linux: ['devryan-front']`, `darwin: [...all]`) and passes `-p <crate>` for each to clippy and test instead of `--workspace`; the licence check keeps reading the whole locked graph on every platform, because licences do not depend on the platform.
2. The new crate's platform-only dependencies go under `[target.'cfg(target_os = "macos")'.dependencies]` in its own manifest, taken from `[workspace.dependencies]` like every other, so `cargo metadata` and the lockfile stay one for the workspace.
3. The contract's sentence "nothing here ships, nothing starts it" becomes per crate: each crate's section says whether it ships, and the packaging rule is restated for a shipped one.
4. The merge takes this branch's root files and adds the spike's members and dependencies to them; the spike's own root files are not merged.

## devryan-config-text

`crates/config-text` (`devryan-config-text`) reproduces, byte for byte, the text operations the server performs with the npm packages `jsonc-parser` 3.3.1 and `yaml` 2.9.0 (the versions `bun.lock` resolves for `packages/web`), so that the server's configuration group can later be ported without changing one byte of what it writes. **Nothing in the product calls it, and it is not shipped.** It has no dependencies and no `unsafe` code.

### Entry points

They are exactly the operations the server uses, with the options it passes; anything else in the two packages (other options, `parseTree` or `visit` for callers, `format` of a whole document, number path segments, array insertion, YAML documents, the CST and visitor APIs, `parseAllDocuments`, replacers and revivers) is deliberately absent.

| Rust | JavaScript, as the server calls it | Server sites |
|---|---|---|
| `jsonc::parse` | `parse(text, errors, { allowTrailingComma: true })`: the value and every `{ error, offset, length }` | `lib/opencode/jsonc-config.js` (`parseConfigJsonc`), `legacy-cursor-plugin.js`, `user-profile-provisioning.js` |
| `jsonc::strip_comments` | `stripComments(text)` | `jsonc-config.js` (the empty-document test) |
| `jsonc::modify`, `jsonc::apply_edits` | `modify(text, path, value, { formattingOptions: { insertSpaces: true, tabSize: 2, eol } })`, `applyEdits` | all three, with string paths |
| `jsonc::remove_key_paths` | `removeJsoncKeyPaths` of `jsonc-config.js`: one removal after another on the same text, `eol` from the source | `slim-config.js`, `shared.js`, `user-profile-provisioning.js`, the native provider configuration |
| `jsonc::set_key_path` | `applyEdits(source, modify(source, path, value, …))` with `eol` from the source | `legacy-cursor-plugin.js`, `user-profile-provisioning.js` (`plugin`) |
| `yaml::parse` | `yaml.parse(source)`: the value, each warning it emits (code and prettified message) and what it throws (name, code, message) | `shared.js`, `packaged-agent-sync.js`, `runtime-agent-overlays.js`, `harness-skill-discovery.js`, `skills-catalog/scan.js`, `cloudflare-tunnel.js` |
| `yaml::stringify` | `yaml.stringify(value)` | `shared.js`, `packaged-agent-sync.js`, `runtime-agent-overlays.js` |
| `front_matter::split`, `front_matter::split_skill` | the two front-matter regular expressions those files match before `yaml.parse` | as above |
| `js::trim`, `js::from_utf8`, `js::to_utf8` | `trim()`, `readFileSync(file, 'utf8')`, `writeFileSync(file, text, 'utf8')` | |

Texts are JavaScript strings: UTF-16 code units, lone surrogates included, and every offset is a unit offset. Values are a `value::Graph`: an arena of arrays and objects with V8's property order (array-index keys ascending, then insertion order), each object's prototype (jsonc-parser assigns a `"__proto__"` key with `=`, which sets the prototype), and identity, so a YAML alias keeps sharing (and cycles) and `yaml.stringify` writes them back as anchors.

### What it leaves to JavaScript

Every public result keeps a refusal apart from the package's own outcome by type: `devryan_config_text::Refused` (with the reason) means "run the JavaScript package instead", and is never an error the package throws. `jsonc::parse` returns `Err(Refused)`; the edits return `ModifyError::Refused`, while what `modify` or `applyEdits` throws is `ModifyError::Thrown` with `String(error)`; `yaml::parse` returns `Parsed::Refused`, while what it throws is `Parsed::Thrown`; `yaml::stringify` returns `Err(Refused)`.

`yaml::parse` refuses instead of guessing where the package builds a value the graph does not hold or where Node's own limits decide: a `%YAML 1.1` document (the yaml-1.1 schema), an explicit `!!binary`, `!!timestamp`, `!!merge`, `!!set`, `!!omap` or `!!pairs` tag (a Uint8Array, Date, merge, Set or Map), a scalar tag named like an `Object.prototype` member (the package then resolves through the prototype), a collection used as a mapping key (stringified with a warning), and collections nested deeper than `yaml::MAX_DEPTH` (64) in any document of the source (`yaml::TOO_DEEP`). `yaml::stringify` refuses values nested deeper than 64. `jsonc::parse` and the edits refuse texts nested deeper than `jsonc::MAX_DEPTH` (512, `jsonc::TOO_DEEP`), and the edits refuse a value `JSON.stringify` would meet a cycle in or that nests deeper than 512 (`value::CYCLIC_VALUE`, `value::DEEP_VALUE`); the server passes only arrays of strings, so it meets neither.

Stack: the parsers recurse with the nesting, which the bounds above cap. A debug build needs 1 MiB of stack for the deepest accepted input (the fuzz test runs on exactly that) and fails at 512 KiB; a release build needs 128 KiB and fails at 64 KiB (measured by the review). Rust's main thread has 8 MiB and a spawned thread 2 MiB by default, so a caller on a default thread has room; a caller that sets a smaller stack must leave at least that much. A stack overflow aborts the whole process: it is not a panic and cannot be caught.

Behaviours of the packages that look like defects are reproduced on purpose: `modify` fails with `TypeError: Cannot read properties of undefined (reading 'length')` when the formatter needs exactly 200 spaces of indentation (its line-break cache has 200 entries, 0 to 199), says "Can not add index" when it means a property, and edits the first of duplicate keys while `parse` keeps the last; `parse` turns a `"__proto__"` key into the object's prototype (only while the lookup reaches `Object.prototype`: under a null prototype, or one with its own `"__proto__"`, it is an own property); `yaml.parse` treats an empty verbatim tag (`!<x` cut short) as no tag. The 200-space message is V8's wording, not the package's: it is the one part of the vectors that depends on Node, so a Node release that rewords it changes those rows (the version line in each file's header says so) although neither package changed.

### How equality is proven

The generators under `crates/config-text/tests/` call the installed packages exactly as the server does (resolved from `packages/web`) and write the tracked vectors, seeded and deterministic on Linux and macOS. Each row is one operation: name, operation, arguments and the result, every field base64 of WTF-8. `crates/config-text/tests/config-text-format.mjs` is the JavaScript half of that format and the crate's `vector` module the Rust half; values are compared through one canonical description (`Graph::describe`). Inputs are the repository's own product configuration (a snapshot in `config-text-repo-fixtures.tsv`, plus a hand-written project `opencode.json` stand-in with placeholder values, since no person's own configuration is copied into the vectors; refreshed by hand with `generate-config-repo-fixtures.mjs` and never compared with the live files, so editing an agent prompt stales nothing; the front-matter rows keep 120 units of each body, since both expressions take the body whole), generated documents and mutated, mostly malformed, ones.

|---|---|---|---|
| `config-jsonc.tsv` | 1012 | 0.57 MB | `parse` and `stripComments`: comments of both kinds everywhere, trailing commas, every line ending, a byte-order mark, prototype and duplicate keys (and `__proto__` under null prototypes), edge numbers, every escape, lone surrogates, nesting at 511 to 513, malformed texts |

## devryan-route-magic-prompts

`crates/route-magic-prompts` (`devryan-route-magic-prompts`) is the web server's `magic-prompts` route group (`packages/web/server/lib/magic-prompts/`) as a standalone candidate for the backend conformance harness ([testing guide](../../docs/TESTING.md), "Backend route-group conformance harness"). **Nothing in the product starts, calls or ships it.** There is no forwarding seam that could send it traffic; the harness is its only client, and it judges the binary against the real JavaScript group on the group's scenarios.

### What it reproduces

Today's behaviour at the group's boundary, quirks included, as the harness's JavaScript candidate adapter composes the group (the product's request decoding, the principal envelope, then the four routes):

- **The candidate protocol** (`candidate.rs`): `--listen`, `--control`, `--data-root`, `--home`, `--stub` (accepted: the group has no outbound call), one ready line, the two harness headers removed before the group reads headers, the envelope checked as the adapter checks it (version 1, naming the exchange, or 400 with the adapter's text), `GET /quiescent?seq=n` once exchange n is answered (every effect of an exchange is made before its answer is written), `POST /stop`; SIGTERM, SIGINT, SIGHUP and the end of stdin stop it with code 0; a refused command line exits 64.
- **Request decoding** (`body.rs`, `qs.rs`, `inflate.rs`, `json.rs`): the shared JSON parser's limit chosen by the path as written (so `/api/Magic-Prompts/<id>` is left unparsed, while `/API/MAGIC-PROMPTS/<id>` gets 50 MB), then the extended URL-encoded parser; body presence, type matching and charset as type-is, content-type and body-parser decide them, from the head alone (`body::plan`); `deflate`, `gzip` and `br` inflated as the body arrives, with Node's rules around zlib: after a gzip member, nothing or a zero byte ends the body (the rest is ignored) and any other byte must start a valid member; inflate ignores what follows its stream; output is counted in Node's 16 KiB pieces, so a stream that fails is refused 413 only when the pieces handed on before the failing call already pass the limit (a stream cut short hands on everything it decoded first), and decoding stops one piece past the limit; the charset decoded as iconv-lite decodes it (UTF-8 with replacement characters, UTF-16 and UTF-32 with their byte-order and guessing rules, ISO-8859-1), a leading byte-order mark dropped; an empty body is `{}`; JSON must start with `{` or `[`; `JSON.parse` with lone surrogates, repeated keys (first place, last value), an own `"__proto__"` and V8's key order (a UTF-8 JSON body is checked on its bytes and only the top-level `text` is decoded, `json::text_of_utf8`, which tests compare with decoding then parsing); `qs.parse` with body-parser's options, so `req.body?.text` is a string exactly when it is today. A body is never held beyond its limit: one no parser reads is not kept at all, a plain one over its limit (declared or counted) is read off and refused once it ends, as body-parser drains it.
- **The listen port** (`candidate.rs`, `http.rs`): one reader thread on kqueue (macOS) or epoll (Linux), level-triggered as libuv's watchers, taking ready sockets in the kernel's order and new connections from the next wait on; llhttp's strict framing (a Content-Length of digits only, given once, not with Transfer-Encoding; `chunked` last and once; hex chunk sizes that fit in 64 bits, CRLF after each chunk; every size and count in checked arithmetic) with Node's bare 400; Node's 16 KiB header limit counted as Node counts it (the target, header names and values) with 431; 408 for a head incomplete after 60 s or a request incomplete after 300 s (Node's `headersTimeout` and `requestTimeout`, checked every 30 s); a thread per answered request, a thread per compressed body. Nothing a request holds can stop the reader: a thread that cannot be made drops its connection, and a step that panicked would drop only its own (a fuzz test shows none does).
- **Routing** (`group.rs`): Express's matching of the four routes: case-insensitive, one optional trailing slash, the query ignored, HEAD by the GET route, the `:id` segment through `decodeURIComponent` (a segment it cannot decode is refused whatever the method, as Express's router refuses it while matching).
- **The runtime** (`runtime.rs`): the data file read again on every request and sanitised as the JavaScript sanitises it (a `"__proto__"` entry is dropped, because assigning it reaches `Object.prototype`'s setter); the id checks (`trim` with JavaScript's whitespace, the pattern, the deprecated ids, empty visible text, more than 200 000 UTF-16 units) and their messages; a write that opens the file with truncation (mode 0666 before the umask, no temporary file, the inode kept), writes `JSON.stringify(state, null, 2)` with no final newline, and is made even when nothing changed; a PUT of `"__proto__"` answers and writes the key that the next read drops.
- **The answer** (`answer.rs`): `Content-Type: application/json; charset=utf-8`, `Content-Length`, Express's weak ETag, fresh's 304 for a GET or HEAD (without Content-Type and Content-Length), no body for HEAD, no `X-Powered-By` and no `Vary`; the 400 and 500 statuses chosen by the error message's text, as the routes choose them; Node's `Date` and `Connection: close`.
- **Error texts** (`uv.rs`, `uv-errors.tsv`): a failed write answers Node's `<code>: <message>, open '<path>'`, with libuv's names and messages as Node gives them, and `UNKNOWN: unknown error` for a number libuv does not map.
- **The order of writes** (`order.rs`): the order in which the JavaScript's handlers call `persist`. A handler runs, and its write takes its place, when the loop has what the request decoding waits for: the head when no parser reads the body, the end of the body when a parser reads it plainly, the end of inflation (zlib's last thread-pool call reporting back) when it is compressed; events of one turn in the order the kernel reports them. The reader gives each request its ticket at that point; a write waits for every earlier ticket; a request that does not write releases its ticket as soon as that is known; a read never waits for its turn, but keeps its place until it has read, so a write whose handler ran after it never truncates the file under it (in Node the read is on the thread pool before that write has read, parsed and truncated the file). The scenario `magic-prompts.write-order` judges each case exactly against the reference (a DELETE with a body no parser reads, on a type and on a path spelling; a GET with such a body; a 40 MiB gzip PUT and a plain one after it; two PUTs readable in one turn, the second connection's written first; a GET during a slow write). Before fix round 1 tickets were given when a request was read in full, in accept order, which differs from the JavaScript in the first four (the review's O1 to O4 and same-tick probes). Where two such points fall within microseconds of each other, the order is a matter of timing on the reference as on the candidate; the scenario's timelines keep them apart by the client's own writes and reads, with no clock.

### How equality is proven

- **Vectors made by the JavaScript itself.** `crates/route-magic-prompts/tests/generate-vectors.mjs` runs the group's own runtime module (600 operation sequences on generated data files, among them malformed, prototype-keyed, index-keyed and byte-order-marked ones: each result and the file's bytes after each operation), the product's request decoding under Express (1 200 requests over paths, types, charsets, encodings and bodies: what `req.body?.text` is, or the status the edge refuses with), 1 500 compressed bodies through the same decoding (gzip followed by zero bytes, junk, a stray `1f` or another member, members cut short or with a wrong CRC, length or header CRC, every optional header field; deflate followed by bytes or with a wrong Adler-32; brotli cut short or followed by bytes; bits flipped; output around the 16 KiB and 50 MB limits and their pieces) and Express's ETag and fresh (300 rows), and writes `crates/route-magic-prompts/tests/runtime.tsv`, `crates/route-magic-prompts/tests/bodies.tsv`, `crates/route-magic-prompts/tests/encodings.tsv` and `crates/route-magic-prompts/tests/answers.tsv` (about 1.4 MB). `crates/route-magic-prompts/tests/vectors.rs` runs every row through the crate. `--check` recomputes each stored row's output from its stored input with the installed packages, and `scripts/check-native.test.mjs` runs that check, so a package or Node change that alters an output fails without Rust.
- **The harness.** The conformance command with `--candidate=rust` judges the binary, built with the command below, against the reference on every scenario of the group; `scripts/backend-conformance/rust-plants.mjs` switches on each planted change of `crates/route-magic-prompts/src/plant.rs` (a build with the `plants` feature; the default build has no `--plant` option) and requires the named row to catch it. Both are commands, not test files: they need a release build, which only a shell with the caller's own cargo can make (the harness runs under the test isolation guard, whose HOME has no registry and no toolchain).
- **Fuzz tests.** `crates/route-magic-prompts/tests/fuzz.rs` and `crates/route-magic-prompts/tests/fuzz_limits.rs` (seeded, bounded: about 50 000 cases, seconds in a debug build) feed heads and framing in random pieces (sizes near 2^64 among them), mutated compressed and plain bodies under every type, charset and encoding, mutated JSON (whose byte path must agree with decoding then parsing), mutated data files, and the router; nothing may panic, and a counting allocator holds each decode to a bound of its limit. One test starts the binary and sends it the requests that killed it in the review (chunk sizes `fffffffffffffffe` and `ffffffffffffffff`: no answer, as Node gives none, and the process lives) and malformed framing (400), then requires an answer.
- `cargo test -p devryan-route-magic-prompts` runs the unit tests, the vectors and the fuzz tests; `scripts/check-native.mjs` runs them with the workspace's tests, and `scripts/backend-conformance/rust-candidate.test.mjs` checks the wiring without Rust (the command line, the build inputs, the plant table against the crate's switch list, `uv-errors.tsv` against the running Node).

### Named limits

- **Observed from outside.** Like any candidate, it is judged by its answers, its trees and what the harness's PATH shim, stubs and process-group look see (`LIMIT candidate-effects-unseen`); a child started by absolute path that exits between two looks, a connection to an address the harness did not hand out, and hub events would go unseen. The crate makes none of them.
- **Its own branches are not counted.** The census counts the JavaScript group's items through rows that passed on the candidate; the crate's own code paths have no coverage of their own.
- **What the edge answers is not reproduced to the byte.** A request the reference's edge refuses (a malformed or `null` JSON body, `charset=latin1`, an unknown encoding, a body over the limit, a `%` the router cannot decode) is never sent to a candidate; the crate refuses it with the same status (the vectors check the statuses) but not with Express's error page and stack.
- **Node's HTTP server is not reproduced beyond framing**: one request per connection (no keep-alive or pipelining; the harness sends `Connection: close`), no `100-continue` or `417`, no `Host` requirement, llhttp's method list and its chunk-extension syntax not checked. Under a seam whose edge is Node none of these reaches the group.
- **Brotli padding.** brotli-decompressor 5.0.0 decodes a stream whose last byte has non-zero padding bits, which Node's decoder refuses (400): its `BROTLI_STATE_DONE` overwrites the padding error the C decoder returns. The vectors hold no such body; the review's fuzz met one in 4 000.
- **Compressed bodies read in pieces.** Node also ends a zlib call at the end of each socket read, so for a compressed body that reaches it in several reads and fails within one 16 KiB piece above the limit, 413 or 400 depends on how the bytes arrived; the crate answers as for a body read at once.
- **UTF-7 and UTF-7-IMAP bodies** (`charset=utf-7`), which iconv-lite decodes, are refused with 415. **A request target in absolute form** (`http://host/path`), or one with `#` or another character that sends parseurl to Node's full URL parser, is cut at `?` or `#` only (an absolute-form target routes nowhere); the harness sends origin-form targets only.
- **The UTF-16 and UTF-32 guesses** are made on the whole body; body-parser makes them on what has arrived when the first 16 or 32 bytes are there, which differs only for a body without a byte-order mark whose first socket read is shorter than 200 bytes.
- **Timing.** The crate answers in microseconds where Node takes about a millisecond, so a kill right after the request is sent (the restarts scenario's `kill-during-write`) can meet a finished write where the reference's would not have begun; every recorded run so far saw the kill first. A GET that overlaps a write can read a truncated file, as in the JavaScript; the write-order scenario's read during a slow write finishes its read long before the write truncates the file, on both.
- **One principal.** Only the local administrator is judged (the reference cannot produce a managed principal); the crate never reads the envelope's principal, as the group never does.

## devryan-client-engine and its runner

`crates/client-engine` (`devryan-client-engine`) is the start of the client state engine of `packages/ui/src/sync` in Rust (refactor plan file 29, packages C1 to C12), and `crates/client-engine-runner` (`devryan-client-engine-runner`, binary `client-engine-runner`) is the process the client conformance harness judges it through (package C0i and its fix round; docs/TESTING.md, "The Rust runner"). **Nothing in the product calls, bundles or ships either.** The packaging rules already refuse every Rust source and Cargo file (`scripts/packaged-app.config.mjs`, `rust-source`), and this folder is no workspace package.

### What is ported

Eleven families of the product port map (`scripts/client-conformance/product/product-port-map.json`), all of the pure ones that have no port: `native-cursor-text`, `tool-status`, `sanitize`, `tool-output`, `message-order`, `session-diff-stats`, `session-working`, `live-aggregate`, `optimistic`, `revert-transactions` (its four committed-resend exports, which keep module state and which the map inlines, are not ported) and `materialization`. Each reproduces every case the TypeScript engine reproduces on the product recording, in file order and alone. The other fifteen families (the reducer, `part-delta` and `message-fetch`, which call the debug port, and every store, timer and transport family) are not ported: the runner refuses them as not ported, and a run that holds them is partial. One harness toy, `toy-relay` (`src/toys.rs`, the replayer's own toy family), is ported too, to prove on recorded cases what the next families need of the runner (below).

**The reference is V8.** The Rust engine replaces the one in the desktop app's renderer, so the port reproduces today's TypeScript as V8 runs it (the behaviour earlier reviews flagged included; it fixes nothing). Where V8 and JavaScriptCore (the engine the recordings are made with) agree, either is the reference; where they differ, the difference is a named rule (docs/TESTING.md, "Engine differences") and V8's answer is the port's. An error the JavaScript engine throws itself (a member read on `null`, a primitive written to) is thrown at the same point with the same class and a text of this engine's own, `client-engine: ...`: the harness compares the class of an engine-written error, never its message (V8 and JavaScriptCore write different sentences, and this engine writes neither); a message the module's code builds is compared exactly.

### One JavaScript implementation

The number layout (`Number::toString`) is the ledger core's: `src/js/number.rs` compiles `packages/harness-runtime/native/ledger-core/src/js/number.rs` in by `#[path]` (not formatted here, `#[rustfmt::skip]`), so the two workspaces have one implementation and cannot disagree (the C0i review's S1: the copy this crate had written ties wrongly, 44 of the ledger's 5,000 V8 vectors). It is no dependency on the ledger core's crate, and nothing of that crate changes: a path dependency would put it in this workspace's locked graph, whose licence gate (`scripts/check-native-licenses.mjs`, and cargo-deny with `[licenses.private] ignore = false`) requires every package to declare a licence, which `ledger-core` does not, and its `Cargo.toml` and sources are inputs of the provenance digest of its tracked WebAssembly module (`scripts/build-ledger-core.mjs --check` stays byte-identical). `crates/client-engine/tests/ledger_vectors.rs` (`numbers.tsv`) and `crates/client-engine-runner/tests/ledger_vectors.rs` (`json.tsv`: `JSON.stringify(JSON.parse(input))` through the runner's reader, the engine's values and member order, and the engine's `JSON.stringify`) runs the ledger core's tracked V8 vectors here, and the static job's filter for this workspace includes those three ledger files, so a change to them checks this workspace too. The rest of the overlap (array indices, JSON string quoting) is held to the same vectors by that test. Moving the shared semantics into a licensed crate of their own (plan file 29 §6, package C0-js) is the remaining step; it needs the ledger owner's sign-off, because it changes the ledger core's provenance inputs.

### Shape

- `js`: JavaScript values with identity (`Rc` plus a number of its own, so a freed object is never taken for a new one), V8's member order (integer-like keys first), arrays as a length and the members present (`Elements`: a hole costs nothing, so a codec tree's hole count is never an allocation; an operation that visits every index stops past 2^24 elements with a RangeError of its own), Map and Set order, Dates (their text in UTC, their JSON, their time for `<`), errors, functions and carried platform values; UTF-16 strings (lengths and slices in code units, lone surrogates kept); `trim` and white space as ECMAScript defines them; `toLowerCase` as full Unicode mapping without a locale (Rust's `to_lowercase` per well-formed run, Final_Sigma included); `Number::toString` (the ledger core's) and `StringToNumber`; `===`, SameValueZero, `<` (ToPrimitive with hint number), `+`, ToString with `OrdinaryToPrimitive` (a member `toString` that is no function, a prototype-less object: a TypeError), truthiness, `typeof`; spreads, `Object.keys`, `in` (`Object.prototype`'s members included) and `JSON.stringify` in member order; iteration of arrays, strings, Sets and Maps; `Array.prototype.sort` with a comparator as Electron's V8 sorts (`js/sort.rs`: binary insertion up to 15 elements, then natural runs, balanced minimum run lengths, powersort's merge policy and CPython's galloping, measured call for call against Electron's Node, `crates/client-engine/tests/sort-vectors.tsv`). No regular expression is needed by these families: the four the TypeScript uses (`/[\s_-]+/g`, `/\\/g`, `/^\.\//`, and `\s` through `trim`) are written out by hand.
- `ctx`: what a step hands a family besides its arguments (the C0i review's S6(a)): the step's time (`now`; the engine never reads a clock), a host that answers port calls and draws from the recording and records each as an effect when it is made (its values taken then), and a microtask queue for continuations. Everything observable goes through the host in the order made, so a delivery's observables are one ordered list.
- `families`: one module per family, each an export table and functions over those values, called with the context: arguments in, the result or what was thrown out, a draft argument changed in place where the TypeScript changes it. A family is made per unit (`Family::open`, an `Instance`), so module state lives as long as its unit, as a module does in file order. The eleven product families ignore the context: none has a port, a timer or module state.
- `toys`: `toy-relay`, ported to prove the runner's port calls (answered from the group's one env list, `effect-order` and `unanswered` halts), continuations after the return (a job four hops later), draws, the step's time as `Date.now()`, module state that only file order shows, and a TypeError the module builds itself; 9 of its 10 recorded cases reproduce under the candidate rules, the tenth is the replayer's hidden-state fixture, which must differ alone and does.
- `plant` and `plants`: planted differences (below), off unless the runner turns one on.
- The runner: `json` (JSON read and written with UTF-16 strings, `JSON.stringify`'s escapes, U+2028 and U+2029 as escapes), `codec` (the harness's value codec: trees rebuilt into values in the case's identity scope, known objects brought in place, a hole run a count bounded by the array bound, values taken when a slot is taken and written in one scope with `id` and `ref`; change sets by identity along paths, the recorder's rule), `protocol` (engine protocol 5: the families' context served from each group's env; continuations run once every member that came together was delivered; what they throw uncaught is the case's `outside`).

### Dependencies

None: neither crate uses a third-party crate, and the runner takes the engine through the workspace (`devryan-client-engine = { path = "crates/client-engine" }` in `[workspace.dependencies]`, a path with no version, which the contract's pin check does not read as a third-party crate). The ledger core's `number.rs` is compiled in as a source file (above), not as a package.
